## Goals / Non-Goals

**Goals:**

- AI 사서의 주제 요청이 실험이 잰 코드(`find_by_topic`)를 **그대로** 탄다. 제품 경로에서 순위 설정을 따로 고르지 않는다(결과 수만 tool 상한 10).
- 임베딩 서버가 없어도 AI 사서는 돈다. 내려가면 지금과 같은 키워드 순서다.
- 이용자 문장은 tool에 넘기지 않고 저장도 늘리지 않는다(설계 원칙 8).
- 바꾸기 전과 뒤를 같은 평가로 비교해 나빠지지 않았음을 보인다. 어린이 판단이 흔들리지 않는지 따로 본다.

**Non-Goals:**

- 주제로 찾기 REST API(검색창은 서명·저자 찾기다)
- 결과에 신호별 근거 문구(비슷한 책의 `basis_text` 같은 것). 키워드 근거 없음 표시 하나만 둔다(결정 4)
- 대화 추천 품질 라벨(어울림), Hit Rate·Recall, LLM 채점, 모델 비교(`add-recommendation-evals`)
- 임베딩 서버 상시 운영(재시작 정책, 헬스 체크, 배포)(`add-observability-deploy`)
- 질의 벡터 캐시를 제품에 두기(같은 낱말이 반복되면 이득이지만, 정확성과 상관없고 메모리·무효화 규칙이 필요하다. 시간이 문제가 되면 그때)

### 2. 벡터 질의 입력: 낱말 (확인 실험의 규칙으로 확정)

**제안: LLM이 tool에 넘긴 낱말을 띄어쓰기로 이어 벡터 질의로 쓴다.** 이용자 문장은 tool에 넘기지 않는다.

- 문장을 쓰면 생기는 문제(실험 세트에는 없던 경우)
  - 여러 턴: `에세이 추천해 주세요` → `더 가벼운 거요`. 둘째 문장의 벡터에는 에세이가 없다. 낱말은 LLM이 `가벼운`, `에세이`로 맥락을 담는다.
  - 다시 찾기: 프롬프트가 "결과가 없으면 다른 낱말로 한두 번 더 찾는다"인데, 문장 벡터는 다시 찾아도 같아서 벡터 순위가 그대로다.
  - 섞인 문장: `공룡 책 있어요? 그리고 토요일에도 열어요?`의 뒷부분, 서명이 든 문장(찾은 책)이 벡터에 섞인다.
  - 문장을 넘기려면 대화 코드가 가린 문장을 실행 값으로 tool에 넘겨야 한다. 저장은 늘지 않지만 tool이 이용자 문장을 다루는 첫 경로가 된다.
- 낱말의 위험: 실험의 낱말은 사람이 쓴 것이고 실제 LLM 낱말은 다를 수 있다. 실제 LLM 낱말은 `add-recommendation-evals`에서 다시 본다(이미 그 change의 일). 이번 평가(결정 11)는 주제 낱말 일치로만 본다.
- **확인 실험**(LLM 없음, 개발 DB 읽기만): 변형 `hybrid-vkw` = `hybrid-k60`에서 `vector_input="keywords"`만 바꾼 것. 조정 20·확인 10 세트, 세 출처 장서(지금 개발 DB).
  - `hybrid-k60`은 이번에 `vector_input="text"`를 변형 정의에 직접 적어, 기본값이 바뀌어도 옛 실행이 같은 값을 낸다. 제품 기본을 가리키는 `hybrid-best`(= `TopicSettings()`)를 더한다(`sim-best`와 같은 방식).
  - 낱말 질의 벡터는 `vec-kw` 실행 때 캐시돼 있을 것이다(`evals/recommendation/data/query_vectors.json`). 없는 것만 임베딩 서버로 인코딩한다.
  - 실행 전 라벨은 이미 있다. 실행 뒤 상위 5권 중 라벨 없는 책만 Claude가 보충하고(라벨 파일을 먼저 백업), 보충분 표본을 사용자가 본다(`review --sample --since <백업>`, 30% 이상 고치면 멈춤).
  - 남겨 둔 분야 세트는 정해 둔 변형만 돌리는 세트라 이번에 쓰지 않는다.
- **미리 정한 규칙**(조정 세트의 `hybrid-vkw` − `hybrid-k60` 짝 비교)
  - 나쁨(차이 < 0이고 95% 구간 상한 < 0): 문장을 쓴다. 대화 코드가 이번 턴의 가린 문장을 실행 값(`USER_TEXT`)으로 넘기고 tool이 벡터 질의로 쓴다. 실행 기록에는 남기지 않는다. 스펙 delta를 고치고 알린다.
  - 그 밖(차이 없음 또는 이김): 낱말을 쓴다. `TopicSettings.vector_input` 기본값을 `"keywords"`로 바꾸고, `docs/roadmap.md`의 확정된 기본값을 "벡터 질의는 낱말(이유: 여러 턴·다시 찾기, 합친 순위에서 차이 없음)"으로 고친다.
  - 확인 세트는 방향만 적는다.
- 안: (a) 문장 그대로(실험 기본값) — 위의 여러 턴 문제. (b) 지난 이용자 문장들을 이어 붙임 — 잰 적이 없고 문장을 다루는 범위가 커진다. (c) LLM이 벡터용 문장을 따로 씀(새 입력 칸) — 잰 적이 없고 LLM이 고를 것이 는다.

### 3. tool 모양: 같은 tool, 속만 바꿈

- `search_collection`과 `search_children_books`의 이름, 입력(`keywords`, 최대 5개)을 그대로 둔다. 낱말이 있으면 주제로 찾기, 비면 지금 둘러보기(`search.search_collection`)다.
- 새 tool을 두지 않는 이유
  - 실험에서 합친 순위가 주제어 질의(0.572 → 0.654)와 상황 질의(0.168 → 0.311) 모두에서 키워드 검색 이상이다. 키워드 검색이 나은 요청 종류가 없어 LLM에게 고를 길을 줄 이유가 없다.
  - tool이 늘면 어린이 tool도 늘고, 어린이 요청 판단의 tool 집합과 프롬프트 문구가 바뀐다. `add-related-books`에서 어린이 문구 두 줄이 판단을 흔들었다.
  - 키워드 신호는 지금과 같은 낱말이 필요하다. 입력이 같다.
- 결과 수: 최대 10권(지금과 같은 상한). 순위는 기본 설정(깊이 30, RRF)이고 앞 10권을 낸다. 실험은 앞 5권으로 쟀지만 Recall@10도 쟀고(0.576), LLM이 지금처럼 10권 중에서 고른다. `limit`은 결과 개수일 뿐 순서를 바꾸지 않는다.
- 결과 안 책의 값(`search_result`)은 그대로다. 대출 가능 여부는 순위에 넣지 않는다(실험과 같음. 키워드 검색은 같은 점수에서 대출 가능을 앞에 뒀지만, 합친 순위에서는 키워드 신호 안에서만 그렇다).
- `find_book`(서명·저자 찾기)은 바꾸지 않는다.

### 4. 결과 모양과 키워드 근거 없음 표시

- 결과를 관련 책 tool과 같은 `{"books": [...], "note": str | None}`으로 바꾼다. 둘러보기와 내려간 경우도 같은 모양이다.
- **키워드 근거 없음**: 낱말이 있는데 키워드 순위가 비고 벡터 순위만 있으면 `note`에 다음을 준다.
  - `낱말이 들어간 소장 도서가 없어 내용이 가까운 책만 찾았다. 소개를 보고 요청과 맞는 책만 추천하고, 맞는 책이 없으면 없다고 말하고 희망도서를 안내한다.`
  - 키워드 순위에 한 권이라도 있으면 표시하지 않는다. 그때는 상위에 낱말이 맞은 책이 함께 있다.
- 결과가 비면(둘 다 빔, 또는 내려간 뒤 키워드도 빔) `note`는 `맞는 소장 도서가 없다. 다른 낱말로 한 번 더 찾고, 그래도 없으면 없다고 말하고 희망도서를 안내한다.`
- **결과를 비우는 유사도 문턱은 두지 않는다.** 비슷한 책에서 코사인이 0·2 라벨을 가르지 못했고(0.35 ~ 0.52 좁은 띠), 상황 질의의 이득(0.168 → 0.31)은 키워드가 맞지 않는 질의에서 벡터가 낸 것이다. 키워드 순위가 빌 때 결과를 비우면 그 이득을 버린다. 판단은 소개를 읽는 LLM에 맡기고, 키워드 근거 없음을 코드가 알려 준다(설계 원칙 7: 애매한 매칭 판단은 LLM). 진단은 결정 12.
- 어느 신호에서 왔는지(신호별 순위)는 tool 결과에 넣지 않는다. LLM이 순위 숫자를 이유로 쓰지 않게 한다.

### 5. 제품 service

- `app/library/services/topic.py`의 `search_by_topic(session, library_id, keywords, *, encoder, within) -> TopicResult`
  - `TopicResult(candidates: list[Candidate], keyword_matched: bool, vector_used: bool)`
  - 낱말이 비면 `search.search_collection`(둘러보기)을 부르고 `keyword_matched=True`로 둔다(표시 없음).
  - `find_by_topic(..., settings=TopicSettings(limit=SEARCH_LIMIT))`으로 순위를 만들고 `get_candidates`로 같은 순서의 후보를 만든다. 결과의 `ranks`에 `keyword`가 하나라도 있으면 `keyword_matched`다.
  - `encoder`가 `None`이면 처음부터 키워드만(`vector_weight=0`)이다.
- 내려가기는 `find_by_topic` 안이 아니라 이 service가 한다. `find_by_topic`은 실험이 그대로 부르는 함수라, 실험 중 인코딩 실패가 조용히 키워드만으로 바뀌면 안 된다(실험은 실패하면 멈춘다).
  - 인코딩에서 `EmbeddingError`가 나면 같은 낱말로 `TopicSettings(vector_weight=0, limit=…)`를 다시 부른다. 키워드 순위는 인코딩 전에 이미 계산되므로, 다시 부르지 않고 키워드 순위만 쓰도록 `find_by_topic`에 `keyword_ranking` 결과를 재사용할 방법은 구현에서 정한다(성능만의 문제).
  - 키워드만일 때 순서는 키워드 검색 순서와 같다(`keyword_ranking`이 `ranked_query`를 쓴다). 따라서 **내려간 결과는 지금 제품의 결과와 같다.**
- `get_candidates`는 추천 가능 조건을 다시 보지 않는다. `find_by_topic`의 신호가 이미 추천 가능한 책만 낸다.

### 6. 질의 인코더: 시간 제한, 쉬기, 모델 확인

- **`GuardedEmbedder`**(`app/central/embedding.py`, 인코더 일반이라 운영자 층의 접점 옆에 둔다. 기관을 모른다): `Embedder`를 감싸고 `encode_queries`에만 다음을 더한다. 문서 인코딩은 막는다(제품은 문서를 인코딩하지 않는다).
  - 시간 제한: 설정 `embedding_query_timeout_seconds`(기본 2.0). 넘으면 `EmbeddingError(TIMEOUT)`. 질의 하나는 CPU에서 약 0.2초이고, 한 턴에 검색이 두세 번이라 최악 약 6초를 넘지 않게 한다.
  - 쉬기: 실패하면 설정 `embedding_query_pause_seconds`(기본 30) 동안 서버를 부르지 않고 바로 `EmbeddingError(PAUSED)`를 낸다. 서버가 꺼진 동안 요청마다 연결을 시도하거나 시간 제한을 기다리지 않게 한다. 시계는 `app/core/clock`(테스트에서 고정).
  - 모델 확인: 처음 쓸 때 한 번 `check()`를 부르고 성공을 기억한다. `MODEL_MISMATCH`면 쉬기와 같이 다룬다(30초 뒤 다시 확인). 다른 모델의 벡터로 저장된 벡터와 비교하면 순위가 조용히 틀리기 때문이다.
  - 동시 요청: 쉬는 상태와 확인 결과만 공유한다. 잠금은 두지 않는다(확인이 두 번 불려도 결과는 같다).
- `EmbeddingFailure`에 `TIMEOUT`, `PAUSED`를 더한다. 지금 `TeiEmbedder`의 `httpx.TimeoutException`은 `SERVER_ERROR`("응답 시간 초과")인데 `TIMEOUT`으로 바꾼다. 적재 CLI는 종류 이름만 출력하므로 영향이 없다(확인 테스트).
- **조립**: `app/library/api/librarian.py`의 `get_query_encoder`(LLM과 같은 방식, `app.state`에 처음 쓸 때 만든다)가 `GuardedEmbedder(TeiEmbedder(httpx.AsyncClient(base_url=…, timeout=query_timeout)))`를 만든다. lifespan 끝에 클라이언트를 닫는다. 설정 `embedding_query_enabled`(기본 `True`)가 `False`면 `None`이다(임베딩 서버를 쓰지 않는 기관 장비).
- **실행 값**: 대화(`stream_turn`)가 `tool_values`에 `QUERY_ENCODER`(`app/library`의 상수)로 인코더를 넘긴다. tool은 `ctx.values.get(QUERY_ENCODER)`로 받는다. 실행기는 뜻을 모른다(`add-related-books` 결정 9와 같은 길).
  - 안: tool factory가 인코더를 붙잡음(모듈 상수 tool이 앱 상태를 알아야 한다), `ToolContext`에 인코더 칸(실행기가 AI 사서의 개념을 알게 된다).
- **띄우기**: 임베딩 서버는 지금처럼 `docker compose --profile embedding up -d embedder`다(메모리 약 4GB). 프로필을 기본으로 바꾸지 않는다. 개발 중 `db`만 띄우는 일이 많고, 서버가 없어도 AI 사서는 키워드로 돈다. 서비스 장비의 상시 운영은 `add-observability-deploy`.

### 7. 내려갈 때 로그와 이용자 답

- 로그: `logger.warning("topic search without vectors: %s", failure.value)` 하나. 낱말, 이용자 문장, 기관 이름을 넣지 않는다. 쉬는 동안(`PAUSED`)은 `debug`로 둬 로그가 요청마다 쌓이지 않게 한다.
- 이용자 답에는 드러내지 않는다. tool 결과에도 넣지 않는다. 이용자에게 할 일이 없고, LLM이 "검색 서버가 꺼져서"를 답에 쓸 수 있다. 결과는 지금 제품과 같은 키워드 순서다.
- 실행 기록에는 남기지 않고 **로그만** 남긴다. 단계 기록(`agent_steps.detail`)은 입력 중 `record_fields`로 고른 값만 담고, 결과 쪽 값을 남기려면 실행기를 바꿔야 한다. 내려간 비율은 로그로 센다. 평가는 실행 전에 인코더 상태를 출력하고(결정 9), 쉬기가 걸리면 그 실행을 다시 돌린다.

### 8. 시리즈 묶기·MMR: 끈 채로

- 실험에서 `series1` -0.001(0·19·1), `mmr0.7` -0.004(4·12·4)로 품질은 같고 겹침만 줄었다(0.35 → 0.20 / 0.15).
- 제품은 10권을 LLM에 주고 LLM이 최대 5권을 고른다. 같은 시리즈가 몰려도 LLM이 고를 수 있고, 비슷한 책에서 시리즈 상한을 켜지 않은 결정과도 맞는다.
- 다시 열 조건: `add-recommendation-evals`의 대화 추천 평가에서 같은 시리즈만 추천하는 답이 문제로 나오면.

### 9. 평가 표본에 벡터 적재

- `evals/librarian/catalog.py`의 `load_catalog`에 `embedder: Embedder | None`을 더한다. 있으면 표본을 넣은 뒤 같은 트랜잭션에서 두 층 적재(`embed_official_books`, 기관 도서 `embed_library_books`, 종류 `full`, 지금 텍스트 버전)를 부른다. 적재 코드는 운영자 실행과 같다.
- **문서 벡터 캐시**: `CachedEmbedder`(`evals/recommendation/cache.py`)를 문서에도 쓸 수 있게 넓힌다. 키는 모델 이름 + 문서 텍스트의 해시(질의와 다른 접두어로 구분). 파일은 `evals/librarian/data/doc_vectors.json`, 질의는 `evals/librarian/data/query_vectors.json`(둘 다 `.gitignore`의 데이터 폴더 안).
  - 처음 한 번만 임베딩 서버로 87권 문서를 인코딩한다(CPU 약 2분). 두 번째부터는 캐시만으로 적재해 서버가 필요 없다.
  - 질의는 LLM 낱말이 실행마다 달라 LLM 평가 동안 서버가 필요하다. 같은 낱말은 캐시에서 나온다.
- `uv run python -m evals.librarian`에 `--no-vectors`를 둔다(바꾸기 전과 같은 표본으로 돌릴 때, 서버 없이 돌릴 때). 기본은 벡터 적재다. 시작할 때 벡터 적재 권수와 캐시 적중 수를 출력한다.
- 표본 테스트(pytest)는 가짜 인코더로 적재 경로만 확인한다.
- 관련 책 시나리오 4개는 벡터가 있는 표본에서 다시 본다(결정 11의 두 실행 모두 벡터 적재). 이번에는 "추천이 tool 결과 안에 있음"을 실제 결과로 확인한다.

### 10. 주제 시나리오

`evals/librarian/scenarios.py`에 더한다. 주제 낱말 기대(`topic`)는 표본에 그 주제가 있을 만한 것으로 고르고, 표본을 보고 정한다(지금 시나리오와 같은 방식).

| id | 턴 | 보는 것 |
| --- | --- | --- |
| `situation-commute` | `출퇴근 지하철에서 가볍게 읽을 책 있어요?` | 상황 질의(키워드가 약함), 추천이 하나 이상 |
| `follow-up-lighter` | `에세이 추천해 주세요` → `좀 더 가벼운 거요` | 둘째 턴에도 `search_collection`을 부르고 추천에 에세이 낱말 |
| `topic-retry` | 표본에 드문 낱말의 주제(표본을 보고 정함) | 같은 턴의 검색 호출 수, 없는 책을 지어내지 않음 |
| `not-held-near` | 표본에 비슷한 분야는 있으나 그 주제는 없는 요청(예: `반도체 공정 기술서 있나요?`) | 키워드 근거 없음 표시 뒤 추천이 비거나, 추천마다 소개가 그 주제를 담음. 희망도서 안내 |
| `child-topic-vector` | `초등학생이 읽을 우주 이야기 책 있어요?` | 어린이 판단, 어린이 도서만(벡터 1위가 일반 도서여도) |

- 기존 `dinosaur`, `after-work-essay`, `cooking`, `history`, `not-held`, `child-dinosaur`, `elementary-science`, `parenting`, `guide-mixed`가 그대로 전후 비교의 주제 시나리오다.
- `not-held-near`의 기대는 새 기대 종류 `NO_MATCH_OR_ON_TOPIC`(추천이 없고 희망도서 표시, 또는 추천 서지 모두에 `topic` 낱말)로 둔다.

### 11. 전후 비교와 판정 규칙

- **순서**: 평가 표본 벡터(결정 9)와 새 시나리오(결정 10)를 먼저 넣는다 → **기준 실행**(지금 코드, 프로필 v5) 두 번 → 제품 코드를 바꾼다 → **바꾼 뒤 실행**(v6) 두 번. 네 실행 모두 같은 표본, 같은 벡터, 같은 시나리오다.
- 비교 출력: `uv run python -m evals.librarian.compare <run> <run> ...`(새 모듈, LLM 없음). 시나리오별로 기대 일치, 규칙 위반, 어린이 판단, 주제 낱말 일치, 검색 tool 호출 수, 턴 걸린 시간(단계 `duration_ms` 합), 토큰을 실행마다 나란히 낸다.
- **판정**(바꾼 뒤가 나빠지지 않음)
  - 규칙 위반: 두 실행 모두 0
  - 기대 불일치: 두 실행의 합이 기준 두 실행의 합 이하
  - 주제 낱말 일치(`topic`이 있는 시나리오): 두 실행의 합이 기준 이상
  - 어린이 판단 불일치: 기준 이하. 어린이 시나리오와 `parenting`·`guide-mixed`를 따로 적는다
  - 넘지 못하면 멈추고 결과를 알린다. 프롬프트를 고칠지, 되돌릴지 사용자가 정한다. 고치면 그 시나리오만 다시 돌리지 않고 전체를 두 번 돌린다(`add-related-books`에서 일부만 다시 돌려 흔들림을 가르지 못했다).
- 두 번씩인 이유: 같은 시나리오의 실행 사이 흔들림(`add-related-books`의 `parenting`·`guide-mixed`)을 바꾼 효과와 가르기 위해서다. 그래도 두 번이라 작은 차이는 "차이 없음"으로 적는다.
- **LLM 추정**(`gpt-6-luna`, 입력 $0.10/1M, 캐시 입력 $0.01/1M, 출력 $0.50/1M)
  - 시나리오 32개(27 + 5), 턴 약 35개. 마지막 실행은 턴 29개에 입력 159,656, 출력 3,780토큰이었다. 턴당 입력 약 5,500 → 실행당 입력 약 195,000, 출력 약 4,600토큰. 검색 결과가 10권으로 같아 tool 결과 크기는 비슷하다고 본다.
  - 실행당 LLM 호출(응답 요청)은 턴당 2~4회, 약 100회.
  - 네 실행: 입력 약 780,000, 출력 약 18,400토큰, 호출 약 400회. 캐시 없이 약 $0.087, 마지막 실행 비율(약 $0.018/실행)로는 약 $0.08. **상한 $0.15로 승인을 요청한다.** 실제 사용량이 추정을 넘으면 결과에 그대로 적는다.
  - 판정을 넘지 못해 다시 돌리면 두 번(약 $0.04)을 다시 승인받는다.
- 평가가 도는 동안 pytest를 돌리지 않는다(같은 테스트 DB).

### 12. 소장 도서가 없는 주제 요청: 있는 라벨로 진단

- 대상: 조정·확인 세트(세 출처 장서)의 `hybrid-best` 결과 중 **키워드 순위가 빈 질의**. 새 라벨을 달지 않는다.
- 낼 것: 그런 질의 수, 그 질의들의 nDCG@5와 상위 5권의 라벨 분포(0·1·2), 키워드 순위가 있는 질의와의 비교. `evals/recommendation/threshold.py`처럼 `runs/<run>/keyword-empty.md`로 쓴다.
- 읽기: 키워드 순위가 빈 질의의 상위에 2 라벨이 흔하면 결과를 비우면 안 된다는 근거다(결정 4). 0 라벨만이면 `add-recommendation-evals`에서 빈 결과 규칙을 다시 본다. **이 진단으로 이 change의 동작(표시만, 비우지 않음)을 바꾸지 않는다**. 표시 문구의 효과는 `not-held`·`not-held-near` 시나리오로 본다.
- 실험 세트는 모든 질의에 어울리는 소장 도서가 있게 만든 세트라 "소장 도서가 정말 없는 요청"은 없다. 그래서 문턱을 정할 데이터가 아니라 진단이다.

### 13. 테스트

- 질의 인코더: 시간 제한 → `TIMEOUT`, 실패 뒤 쉬기 동안 서버를 부르지 않음, 쉬기가 끝나면 다시 부름, 모델 확인 한 번(성공 기억), 다른 모델 → 쉬기, 문서 인코딩 막음, 오류 메시지에 질의 없음
- service: 낱말 없음 → 둘러보기와 같음, 인코더 없음 → 키워드 검색과 같은 순서, 인코딩 실패 → 키워드 검색과 같은 순서·로그에 종류만, 기본 설정의 `find_by_topic` 앞 10권과 같은 순서, 키워드 근거 없음 판정, 기관 분리(다른 기관의 벡터 1위 책), 추천할 수 없는 책, `within`
- tool: 결과 모양(`books`, `note`), 세 가지 `note`, 실행 값의 인코더 사용, 실행 기록에 낱말 없음, 어린이 tool의 범위(벡터 1위 일반 도서가 없음)
- 대화: `stream_turn`이 인코더를 실행 값으로 넘김, 인코더가 없을 때도 답이 나감
- 실험: `hybrid-vkw`·`hybrid-best` 변형 정의, `hybrid-k60`의 결과가 이전 실행과 같음(`vector_input` 고정), 키워드 순위 빈 질의 진단 표
- 평가: 표본 적재의 벡터(가짜 인코더), 캐시 적중이면 인코더를 부르지 않음, 새 기대 종류 채점, 비교 출력
- 기존 동작: `evals.catalog_search` 기준과 같음, similar·history 기준 실행이 같음(이 change는 그 코드를 바꾸지 않는다)
- 대량 삽입·롤백 뒤 테스트 DB `VACUUM ANALYZE`

## Risks / Trade-offs

- **[LLM 낱말이 실험 낱말과 다름]** 사람이 쓴 낱말보다 짧거나 넓을 수 있다 → 결정 11의 주제 낱말 일치, `add-recommendation-evals`에서 실제 낱말로 다시.
- **[벡터가 관련 없는 책을 채움]** 키워드가 맞지 않아도 10권이 나온다 → 키워드 근거 없음 표시(결정 4), 소장하지 않은 주제 시나리오 둘.
- **[어린이 판단이 흔들림]** 결과 모양과 프롬프트가 바뀐다 → 어린이 프롬프트 문구는 고치지 않는다. 기본 프롬프트의 검색 줄만 고친다. 판정에 어린이 판단을 따로 둔다.
- **[응답 시간]** 검색마다 인코딩 약 0.2초가 늘고 최악은 시간 제한 2초 × 검색 수 → 쉬기, 결과에 턴 걸린 시간을 적는다.
- **[임베딩 서버 메모리]** 약 4GB를 계속 쓴다 → 작은도서관 PC 한 대에 앱·DB·임베딩 서버를 함께 둘 수 있는지는 배포 change에서 본다. 서버 없이도 지금 품질(키워드)로 돈다.
- **[적재 안 된 새 책]** 벡터가 없는 책은 벡터 신호에 없고 키워드로만 오른다 → 지금과 같다. 증분 적재(`--incremental`)를 운영 절차에 둔다.
- **[평가 두 번]** 흔들림을 다 가르지 못한다 → 작은 차이는 차이 없음으로 적고, 판정은 나빠지지 않음만 본다.
