# Spec Delta

## MODIFIED Requirements

### Requirement: 기존 API만 사용
화면은 화면 전용 API 없이 기존 API만 MUST 쓴다. 화면이 부르는 경로는 다른 클라이언트도 쓰는 일반 API이고, 화면 때문에 `/ui` 아래에 API 경로를 두지 않는다.
- 로그인 화면: 로그인, 내 정보
- 이용자 화면: 내 정보, 자동완성, 검색, 주제 검색, 비슷한 책, AI 사서 대화, 대화 종료, 도서관 안내, 회원 로그인·로그아웃, 담은 책(불러오기·담기·빼기·비우기), 대출, 반납, 희망도서 신청
- 관리자 화면: 내 정보, 로그아웃, 기관 정보, 운영 에이전트 대화와 대화 종료, 큐레이션·연체 안내문 틀·구매 요청서의 목록·상세·승인·반려(큐레이션은 내리기도), 희망도서 목록과 닫기, 오늘의 연체 안내 목록, 장서 가져오기(올리기, 기록 목록·단건, 행 목록, 적용, 미리 보기 삭제), 장서(사본 찾기·상태 바꾸기, 반납, ISBN으로 기관 도서 확인, 기관 도서·사본 등록), 회원(목록·찾기, 등록, 고치기, 삭제), 임시 휴관일(목록, 더하기, 지우기)

#### Scenario: 서버 경로
- **WHEN** 서버의 경로 목록을 읽으면
- **THEN** `/ui` 아래에는 정적 파일 경로 하나만 있고 API 경로가 없다

#### Scenario: 화면이 부르는 경로
- **WHEN** 화면 스크립트에서 서버에 요청하는 경로를 모두 모으면
- **THEN** 모두 `/auth/login`, `/auth/me`, `/auth/logout`, `/auth/member-login`, `/auth/member-logout`, `/catalog/suggest`, `/catalog/search`, `/catalog/topic`, `/catalog/books/{id}/similar`, `/librarian/messages`, `/librarian/sessions/{id}`, `/library`, `/library/guide`, `/library/closures`, `/library/closures/{id}`, `/basket`, `/basket/{id}`, `/loans`, `/loans/return`, `/book-requests`, `/book-requests/{id}`, `/admin-agent/messages`, `/admin-agent/sessions/{id}`, `/curations`, `/curations/{id}`, `/curations/{id}/approve`, `/curations/{id}/reject`, `/curations/{id}/unpublish`, `/overdue-notice-templates`, `/overdue-notice-templates/{id}`, `/overdue-notice-templates/{id}/approve`, `/overdue-notice-templates/{id}/reject`, `/purchase-requests`, `/purchase-requests/{id}`, `/purchase-requests/{id}/approve`, `/purchase-requests/{id}/reject`, `/overdue-notices/today`, `/holding-imports`, `/holding-imports/{id}`, `/holding-imports/{id}/rows`, `/holding-imports/{id}/apply`, `/holdings`, `/holdings/{id}`, `/library-books`, `/members`, `/members/{id}` 중 하나다

#### Scenario: 부르는 경로가 서버에 있음
- **WHEN** 화면 스크립트가 요청하는 경로와 메서드를 서버의 경로 목록과 맞춰 보면
- **THEN** 모두 서버에 있는 경로와 메서드다

### Requirement: 관리자 화면의 탭과 운영 방식
관리자 화면은 한 페이지에 탭 여덟(운영 대화, 승인 목록, 희망도서, 오늘의 연체, 장서 가져오기, 장서, 회원, 휴관일)을 SHALL 둔다. 열린 탭은 주소 hash로 기억한다. 기관 정보(`GET /library`)의 `loan_mode`가 `internal`일 때만 [오늘의 연체] 탭, 승인 목록의 연체 안내문 틀 묶음, [장서] 탭을 보이고, `external`일 때만 [장서 가져오기] 탭을 보인다. 기관 정보를 읽지 못하면 운영 방식에 따른 것을 모두 숨긴다. [회원]과 [휴관일]은 두 방식 모두 보인다. 숨긴 탭의 주소로 열면 운영 대화를 연다. 최종 판단은 서버(409)가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 관리자 화면 HTML을 읽으면
- **THEN** [오늘의 연체] 탭, 연체 안내문 틀 묶음, [장서 가져오기] 탭, [장서] 탭은 숨김 상태로 시작하고 [회원]·[휴관일] 탭은 숨기지 않는다

#### Scenario: 보이는 조건
- **WHEN** 관리자 화면 스크립트에서 위 네 가지를 보이게 하는 곳을 검사하면
- **THEN** 기관 정보의 `loan_mode`를 한 곳에서 읽고, 연체 탭·틀 묶음·[장서] 탭은 `internal`일 때만, [장서 가져오기] 탭은 `external`일 때만 보인다

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관의 관리자로 관리자 화면을 열면
- **THEN** [장서 가져오기]·[회원]·[휴관일] 탭이 보이고 [오늘의 연체]·[장서] 탭과 연체 안내문 틀 묶음은 보이지 않는다(브라우저 확인)

#### Scenario: 자체 대출 기관
- **WHEN** 자체 대출 기관의 관리자로 `#imports` 주소를 열면
- **THEN** [장서 가져오기] 탭은 보이지 않고 운영 대화가 열린다(브라우저 확인)

#### Scenario: 외부 대출 기관의 장서 주소
- **WHEN** 외부 대출 기관의 관리자로 `#collection` 주소를 열면
- **THEN** [장서] 탭은 보이지 않고 운영 대화가 열린다(브라우저 확인)

### Requirement: 관리자 화면의 회원 값
관리자 화면은 회원 값(회원번호, 이름, 전화번호, 채운 안내 문안)을 [희망도서], [오늘의 연체], [회원] 탭에서만 MUST 보인다. 그 탭에 들어올 때마다 서버에서 다시 읽는다(연체·신청·회원은 그사이 바뀌므로 지난 목록을 다시 쓰지 않는다). 회원 값을 복사·출력·내려받는 버튼을 두지 않고, 브라우저 콘솔에 쓰지 않는다. 확정한 안내문 틀이 없어 오늘의 연체 목록이 409면 서버 문구와 함께 운영 대화에서 틀을 만들어 승인하라고 안내한다.

#### Scenario: 회원 값을 읽는 곳
- **WHEN** 관리자 화면 스크립트에서 `member_number`, `phone`을 읽는 곳을 모두 모으면(이름 `name`은 기관 이름과 겹쳐 브라우저 확인으로 본다)
- **THEN** 희망도서 목록, 오늘의 연체 목록, 회원 목록·입력을 그리는 곳뿐이다

#### Scenario: 콘솔 출력 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `console.` 호출이 없다

#### Scenario: 탭에 돌아오면 다시 읽음
- **WHEN** [오늘의 연체] 탭을 연 뒤 다른 탭에서 대출을 반납하고 돌아오면
- **THEN** 서버에서 다시 읽은 목록이 보이고 반납한 줄은 없다(브라우저 확인)

## ADDED Requirements

### Requirement: 장서 화면의 사본 찾기
관리자 화면의 [장서]는 들어오면 `GET /holdings`(찾기 글자 없음)로 최근에 등록한 사본부터 표로 SHALL 보인다. 찾기 칸 하나(서명·저자·등록번호)로 `GET /holdings?q=`를 불러 찾은 사본을 같은 표로 보이고, 찾은 동안에는 [전체 보기]가 있어 누르면 칸을 비우고 처음 목록으로 돌아간다. 칸을 비우고 [찾기]를 눌러도 처음 목록이다. 열은 등록번호, 서명, 저자, 청구기호, 상태이고 20줄씩 [더 보기]로 더 읽는다. 찾은 사본이 없으면 짧게 알린다. 탭에 다시 들어오면 지난 화면(처음 목록이나 찾기)을 서버에서 다시 읽는다. 서명·저자 같은 서버 값은 글자로만 넣는다.

#### Scenario: 찾기 요청
- **WHEN** 장서 화면 스크립트를 검사하면
- **THEN** 사본 목록과 찾기는 `GET /holdings`에 `q`(찾을 때만), `limit`, `offset`만 보내고 `status`를 보내지 않는다

#### Scenario: 처음 목록과 전체 보기
- **WHEN** 자체 대출 기관 관리자가 [장서] 탭을 열고, 서명으로 찾은 뒤 [전체 보기]를 누르면
- **THEN** 처음에는 최근에 등록한 사본부터 보이고, 찾으면 [전체 보기]가 생기며, 누르면 칸이 비고 처음 목록으로 돌아가 [전체 보기]가 사라진다(브라우저 확인)

#### Scenario: 읽는 필드
- **WHEN** 장서 화면 스크립트가 읽는 사본 필드를 응답 스키마와 맞춰 보면
- **THEN** 모두 `HoldingRead`에 있는 필드다

#### Scenario: 분실한 책 다시 찾기
- **WHEN** 자체 대출 기관 관리자가 한 권뿐인 책을 분실로 바꾼 뒤 그 서명으로 다시 찾으면
- **THEN** 그 사본이 분실 상태로 보인다(브라우저 확인)

#### Scenario: 등록번호로 찾기
- **WHEN** 등록번호를 그대로 쳐서 찾으면
- **THEN** 그 사본이 맨 위에 보인다(브라우저 확인)

### Requirement: 장서 화면의 상태 바꾸기
[장서]의 사본 줄은 대출 중이 아니면 상태 고르기(이용 가능, 분실, 훼손, 제적)를 SHALL 둔다. 고르면 `PATCH /holdings/{id}`에 상태만 보내고, 제적일 때만 확인을 한 번 더 받는다. 성공하면 문구 없이 응답 값으로 그 줄을 고친다. 실패하거나 확인을 취소하면 고르기를 이전 값으로 되돌리고, 실패는 서버 문구를 글자로 보인다. 대출 중인 줄은 고르기 대신 "대출 중"과 [반납]을 두고, 확인 한 번 뒤 그 등록번호로 `POST /loans/return`을 부른 다음 그 줄을 다시 읽는다.

#### Scenario: 고를 수 있는 상태
- **WHEN** 장서 화면 스크립트의 상태 고르기 값을 검사하면
- **THEN** `available`, `lost`, `damaged`, `withdrawn` 넷뿐이고 `on_loan`은 없다

#### Scenario: 제적만 한 번 더 묻기
- **WHEN** 장서 화면 스크립트의 상태 바꾸기를 검사하면
- **THEN** `withdrawn`을 보내기 전에만 확인을 받고 취소하면 요청하지 않는다

#### Scenario: 분실 처리와 되돌리기
- **WHEN** 이용 가능 사본을 분실로 고른 뒤 다시 이용 가능으로 고르면
- **THEN** 문구 없이 상태가 바뀌고 다시 찾아도 이용 가능이다(브라우저 확인)

#### Scenario: 대출 중인 사본 반납
- **WHEN** 대출 중인 줄의 [반납]을 누르고 확인하면
- **THEN** 그 줄이 이용 가능이 되고 상태 고르기가 생긴다(브라우저 확인)

### Requirement: 장서 화면의 책 등록
[장서]의 [책 등록]은 ISBN, 서명·저자, 사본 정보를 받아 기존 REST로 SHALL 등록한다. ISBN이 있으면 먼저 `GET /library-books?isbn=`으로 확인해, 있는 책이면 서명만 보이고 사본 칸만 받는다. 없거나 ISBN이 비면 `POST /library-books` 뒤에 `POST /holdings`를 부른다. 사본 칸은 등록번호(필수), 청구기호, 입수 구분(매입·기증), 매입이면 구입가(필수), 기증이면 기증처다. 필수 칸이 비면 요청하지 않는다. 실패는 서버 문구를 글자로 보인다. 성공하면 문구 없이 칸을 닫고 그 등록번호로 찾은 결과를 보인다.

#### Scenario: 이미 있는 책
- **WHEN** 장서 화면 스크립트의 책 등록을 검사하면
- **THEN** ISBN이 있으면 기관 도서 등록 전에 `GET /library-books`를 `isbn`으로 부르고, 찾은 책이 있으면 `POST /library-books` 없이 `POST /holdings`만 부른다

#### Scenario: 사본 등록이 실패한 뒤 다시 누르기
- **WHEN** 기관 도서는 만들어지고 사본 등록이 실패한 뒤 같은 칸에서 [등록]을 다시 누르면
- **THEN** 화면은 만든 기관 도서로 `POST /holdings`만 부른다(스크립트 검사와 브라우저 확인)

#### Scenario: 보내는 값
- **WHEN** 장서 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 기관 도서는 `LibraryBookCreate`, 사본은 `HoldingCreate`에 있는 키만 보낸다

#### Scenario: 새 책 등록
- **WHEN** 자체 대출 기관 관리자가 새 ISBN, 서명, 저자, 등록번호, 매입, 구입가로 등록하면
- **THEN** 칸이 닫히고 그 사본이 이용 가능으로 보이며, 이용자 화면에서 그 서명을 찾을 수 있다(브라우저 확인)

#### Scenario: 겹친 등록번호
- **WHEN** 이미 쓰는 등록번호로 사본을 등록하면
- **THEN** 서버 문구가 보이고 칸은 입력한 값과 함께 열려 있다(브라우저 확인)

### Requirement: 회원 화면
관리자 화면의 [회원]은 회원 목록을 SHALL 보이고 등록·고치기·삭제를 한다. 들어오면 `GET /members` 첫 20명(회원번호 순)을 읽고, 찾기 칸(이름·회원번호)으로 거르며, [더 보기]로 더 읽는다. 열은 회원번호, 이름, 휴대폰 번호(없는 기존 회원은 `-`)다. 등록은 회원번호·이름·휴대폰 번호(셋 다 필수)다. [고치기]는 이름과 휴대폰 번호만 바꾼다. 번호가 있는 회원의 번호 칸을 비우면 요청하지 않고 번호를 넣으라고 알린다. 번호 없는 기존 회원은 번호 칸을 비운 채 이름만 고칠 수 있다(번호를 보내지 않는다). [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패는 서버 문구를 글자로 보인다. 입력칸은 브라우저 자동 완성을 끈다.

#### Scenario: 보내는 값
- **WHEN** 회원 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 등록은 `MemberCreate`, 고치기는 `MemberUpdate`에 있는 키만 보낸다

#### Scenario: 번호는 필수
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** 등록은 번호 칸이 비면 요청하지 않고, 고치기는 번호를 `null`로 보내지 않는다

#### Scenario: 삭제는 확인 뒤
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** `DELETE /members/{id}` 앞에 확인이 있고 취소하면 요청하지 않는다

#### Scenario: 입력칸
- **WHEN** 관리자 화면 HTML의 회원 입력칸을 검사하면
- **THEN** 모두 `autocomplete="off"`다

#### Scenario: 등록한 회원으로 로그인
- **WHEN** 자체 대출 기관 관리자가 휴대폰 번호와 함께 회원을 등록한 뒤 이용자 화면에서 그 번호로 로그인하면
- **THEN** 로그인되고 빌리기를 할 수 있다(브라우저 확인)

#### Scenario: 겹친 번호
- **WHEN** 다른 회원이 쓰는 휴대폰 번호로 고치면
- **THEN** "이미 쓰는 전화번호입니다"가 보이고 목록의 값은 그대로다(브라우저 확인)

### Requirement: 휴관일 화면
관리자 화면의 [휴관일]은 오늘부터 1년의 임시 휴관일을 SHALL 보이고 더하기와 지우기를 한다. 들어오면 `GET /library/closures`를 `from`(오늘)과 `to`(오늘부터 365일)로 읽는다. 줄은 날짜와 사유(없으면 비움)와 [삭제]다. 더하기는 날짜(필수)와 사유(100자까지)를 `POST /library/closures`로 보낸다. [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패(같은 날짜 409 등)는 서버 문구를 글자로 보인다.

#### Scenario: 읽는 기간
- **WHEN** 휴관일 화면 스크립트를 검사하면
- **THEN** 목록 요청에 `from`과 `to`를 보내고 `to`는 `from`부터 365일 뒤다

#### Scenario: 사유 길이
- **WHEN** 관리자 화면 HTML의 사유 칸을 검사하면
- **THEN** 최대 길이가 서버 스키마의 상한(100자)과 같다

#### Scenario: 휴관일 더하기
- **WHEN** 자체 대출 기관 관리자가 오늘 날짜를 사유 `소독`으로 더하면
- **THEN** 목록에 그 날짜가 보이고, 같은 관리자의 `GET /library/guide`에서 오늘이 임시 휴관이고 사유가 `소독`이다(브라우저 확인. 시드 기관은 안내를 등록하지 않아 이용자 화면 위 띠에는 나오지 않는다)

#### Scenario: 같은 날짜
- **WHEN** 이미 있는 날짜를 다시 더하면
- **THEN** 서버 문구가 보이고 목록은 그대로다(브라우저 확인)

### Requirement: 휴대폰 번호의 하이픈
화면은 휴대폰 번호를 하이픈을 넣어 SHALL 보인다. 관리자 화면의 회원 목록과 오늘의 연체 목록이 그렇고, 번호를 치는 칸(관리자 회원 등록·고치기, 이용자 화면 회원 로그인)은 치는 대로 하이픈을 넣는다. 규칙은 공통 스크립트 한 곳에 둔다: `02`로 시작하면 2-3-4(9자리)·2-4-4(10자리), 그 밖은 3-3-4(10자리)·3-4-4(11자리)이고, 이 꼴이 아닌 값은 받은 그대로 보인다. 서버는 하이픈을 지운 숫자로 저장하므로 요청에는 하이픈이 있어도 된다. 번호 칸은 숫자와 하이픈만 남기고 13자를 넘지 않는다.

#### Scenario: 보이는 꼴
- **WHEN** 하이픈 규칙 함수에 `01012345678`, `0101234567`, `021234567`, `0212345678`, `0311234567`, `12`를 넣으면
- **THEN** `010-1234-5678`, `010-123-4567`, `02-123-4567`, `02-1234-5678`, `031-123-4567`, `12`가 나온다

#### Scenario: 한 곳의 규칙
- **WHEN** 관리자 회원·연체 스크립트와 이용자 화면 로그인 스크립트를 검사하면
- **THEN** 번호를 보이거나 칸에 넣을 때 모두 공통 스크립트의 함수를 쓴다

#### Scenario: 치는 대로 하이픈
- **WHEN** 이용자 화면 회원 로그인 칸에 `01099990001`을 치면
- **THEN** 칸에 `010-9999-0001`로 보이고 그대로 로그인된다(브라우저 확인)

#### Scenario: 관리자 목록
- **WHEN** 자체 대출 기관 관리자가 [회원] 탭과 [오늘의 연체] 탭을 열면
- **THEN** 번호가 `010-1234-5678` 꼴로 보인다(브라우저 확인)
