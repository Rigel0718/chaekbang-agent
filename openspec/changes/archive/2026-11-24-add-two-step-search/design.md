## Context

동기는 proposal의 Why를 본다. 지금 코드에서 이 설계를 정한 사실은 아래와 같다.

- `app/library/services/topic.py`의 `search_by_topic(session, library_id, keywords, encoder=, within=)`은 제품 경로다. 낱말이 있으면 기본 설정으로 앞 10권(`SEARCH_LIMIT`)을 내고, 인코더가 없거나 실패하면 키워드 순위로 내려간다. 낱말이 없으면 둘러보기(`search_collection`)다. AI 사서의 소장 도서 검색 tool만 이 함수를 부른다.
- 질의 인코더는 `app/library/api/librarian.py`의 `get_query_encoder`(`QueryEncoder` 의존성)가 `app.state`에 처음 쓸 때 만든다. 테스트는 이 의존성을 덮어쓴다(`tests/library/chat_helpers.py`).
- `app/library/api/catalog.py`의 `/catalog/search`는 `find_books` → `build_summaries`로 `list[BookSummary]`를 낸다. 질의 상한은 `MAX_QUERY_LENGTH = 100`이다.
- `find_books`의 맞춤은 서명 전체 → 서명 앞부분 → 서명 포함 → 저자 포함 → 오타 순이다. 문장으로 친 질문은 거의 걸리지 않고, 한두 글자 질의는 넓게 걸린다(roadmap의 미룬 일).
- 이용자 화면: Enter는 `suggest.js`의 `onSubmit` → `main.js`의 `submit()` → `chat.sendText`(AI 사서 대화)다. `chat.showSearch(query)`(자동완성의 "'질의'로 책 모두 찾기")는 `/catalog/search` 결과를 `summary` 카드 줄 블록으로 대화 줄에 넣고 서버 세션을 건드리지 않는다. 카드(`shared/card.js`)는 누르면 비슷한 책을 펼치고 [이 책 물어보기]·[담기]가 있다.
- 입력칸은 500자까지 받는다. `/catalog/search`는 100자를 넘으면 422다.

## Goals / Non-Goals

**Goals:**
- 아는 책을 친 이용자에게 LLM 없이 그 책과 관련된 책을 바로 보인다.
- 질문을 친 이용자는 지금처럼 AI 사서로 간다. 바뀐 흐름이 대화로 가는 길을 막지 않는다.

**Non-Goals:**
- 주제로 찾기의 순위·기준값을 바꾸지 않는다.
- 서명·저자 찾기(`catalog/book-lookup`)의 응답과 맞춤 규칙을 바꾸지 않는다.
- 카드 동작(누르기 = 비슷한 책 펼치기)을 바꾸지 않는다. 카드 누르기 = 담기는 24e에서 다시 본다.

## Decisions

### 1. 주제 검색 REST: `GET /catalog/topic?q=`

- 같은 `catalog` 라우터에 둔다. 인증(`CurrentStaff`)과 질의 규칙(`QueryText`, 1~100자)은 `/catalog/search`와 같다. 키오스크·관리자가 쓴다.
- 응답은 `list[BookSummary]`, 카드는 `build_summaries`다. 화면이 같은 카드 코드를 쓴다.
- `services/topic.py`에 작은 함수 하나(가칭 `search_topic_text(session, library_id, text, *, encoder)`)를 둔다. 질의를 공백으로 나눠 낱말로 만들고, 글자·숫자가 하나도 없는 낱말(`·`, `!?`)은 뺀다(`match_key`가 빈 값). 남는 낱말이 없으면 `search_by_topic`을 부르지 않고 빈 결과를 낸다. 그 밖에는 남은 낱말 그대로 `search_by_topic(..., encoder=encoder)`를 부른다. `clean_keywords`(`compact`)는 문장부호를 지우지 않아서(서명의 `C++`처럼 뜻이 있다) 빈 판정에 쓰지 않는다. 라우터는 이 함수와 `build_summaries`만 부른다(라우터를 얇게).
- 벡터 질의 입력은 지금 규칙대로 낱말을 이은 것이다. 이용자가 친 글이 곧 낱말이라 "이용자 문장을 넘기지 않는다"는 제품 경로 규칙과 어긋나지 않는다. 화면은 100자를 넘는 글을 이 경로로 보내지 않는다.
- 인코더는 `api/librarian.py`의 `QueryEncoder`를 가져다 쓴다(옮기지 않음).
- 응답에 벡터 사용 여부·키워드 근거 없음 표시를 넣지 않는다. 내려가도 모양이 같고, 위 단이 있을 때만 부르므로 키워드가 맞는 때가 대부분이다.
- 위 단 책 제외는 화면이 한다. 위 단 id를 화면이 이미 갖고 있고, 서버 `exclude` 인자는 id 검증과 시나리오가 늘어난다. 아래 단은 최대 8~10권이다.
- 다른 안: `/catalog/search`에 주제 결과를 붙이기 → 서명 찾기의 스펙·응답이 바뀌고 자동완성과 성격이 섞여 버림. LLM 경로를 고치기(`요리` 덧붙임을 막는 프롬프트) → 결정적이지 않고 평가가 필요해 버림.

### 2. Enter 갈림 (화면)

```
Enter (자동완성 후보를 고른 때는 빼고)
  |-- 100자 초과 --------------------------------> AI 사서 대화
  v
GET /catalog/search
  |-- 0권 / 실패(401 빼고) ----------------------> AI 사서 대화 (지금처럼)
  |-- 401 ---------------------------------------> 로그인 화면
  v 1권 이상
두 단계 결과 (결정 3)
```

- 상한 100은 화면 상수로 두고 서버 `MAX_QUERY_LENGTH`와 같은지 소스 검사가 본다.
- 찾기 요청 중에는 Enter를 무시한다(플래그 하나). 입력칸은 보낼 때 비운다(지금과 같음).
- 답을 받는 중(`chat.busy`)이면 지금처럼 Enter를 무시한다.

### 3. 두 단계 결과 블록 (화면)

```
+-------------------------------------------+
| 이 책을 찾으시나요?                         |
|  [카드] [카드]           <- 찾기 앞 2권      |
| '채식'과 관련된 책                          |
|  [카드][카드]...         <- 주제, 위 단 제외 |
|  [사서에게 물어보기]                        |
+-------------------------------------------+
```

- `chat.js`의 `showSearch` 옆에 두 단계 블록 함수(가칭 `showTwoStep(query, found)`)를 둔다. 찾기 결과를 받은 뒤 블록을 대화 줄에 넣고, 위 단을 바로 그리고, 아래 단에 "관련된 책을 찾는 중…"을 둔 뒤 `/catalog/topic`을 부른다.
- 위 단 권수는 상수 2(1권뿐이면 1권). 찾기 결과의 3번째부터는 보이지 않는다(전체는 자동완성의 "모두 찾기"). 응답에 맞은 방식이 없어 규칙으로 1·2권을 나누지 않는다.
- 아래 단: 주제 결과에서 위 단 id를 뺀다. 비거나 실패하면 아래 단을 제목째 지운다. 401이면 로그인 화면으로 간다.
- 카드는 두 단 모두 `summary` 카드이고 저절로 펼치지 않는다(아래 단이 비슷한 책 역할).
- [사서에게 물어보기]: 블록 끝 버튼 하나. `chat.sendText(query)`가 받아들이면(`busy`가 아니면) 버튼을 끈다.
- 이용자 말풍선은 없다(`showSearch`와 같음). 블록은 서버 세션을 건드리지 않고 `resetAll`의 `chat.reset()`이 대화 줄과 함께 지운다.
- 부르는 순서는 차례로다(찾기 → 1권 이상이면 주제). 0권일 때 인코더를 부르지 않고, 위 단이 주제 검색(보통 약 0.2초, 최대 2초)을 기다리지 않는다.

### 4. 테스트

- 서버 pytest(새 `tests/library/test_topic_api.py`, 이름·docstring에 요구사항 "주제로 찾기 API"):
  - 제품 경로와 같은 결과: 같은 `FakeEmbedder`로 `search_by_topic(["채식","소설"])`과 REST의 id 목록 비교
  - 인코더 실패: `EmbeddingError`를 내는 가짜 인코더 → 키워드 순위 id와 같음
  - 낱말 없음: `q=" · "` → `[]`, 인코더 호출 0번
  - 토큰 없음 401, 빈 질의·101자 422
  - 다른 기관: `library_id=B`를 붙여도 B의 id 없음
  - 기록 없음: agent_runs, chat_messages, recommendation_events 행 수
  - service: 여러 공백으로 나뉜 질의가 낱말 목록으로 넘어감
- 화면 소스 검사(`tests/platform/test_web_ui.py`):
  - `ALLOWED_CALLS`에 `/catalog/topic`(기존 "화면이 부르는 경로", "부르는 경로가 서버에 있음" 테스트가 확인)
  - 두 단계 상한 상수 = `app.library.api.catalog.MAX_QUERY_LENGTH`
  - 위 단 권수 상수 = 2
  - 새 코드도 기존 `textContent`·`safeUrl`·카드 필드 검사에 걸린다
- 그 밖의 화면 동작은 아래 브라우저 확인 항목으로 본다. evals 시나리오는 없다(에이전트 동작이 바뀌지 않는다).

### 5. curl 확인 (apply 때 Claude)

- 키오스크 토큰으로 `GET /catalog/topic?q=채식`(실험 기관 id 7): 200, 채식주의자 포함. 임베딩 서버를 켠 상태와 끈 상태 둘 다.
- 토큰 없이 401.
- LLM 호출 0회, 외부 API 호출 0회.

## Risks / Trade-offs

- [한두 글자 질의(`책`, `나`)가 넓게 걸려 두 단계로 간다] → [사서에게 물어보기]로 대화에 닿는다. 빼는 규칙은 미룬 일.
- [서명에 흔한 낱말이 든 질문형 입력이 두 단계로 간다] → 같은 버튼으로 대화에 닿는다. 써 보고 걸리면 규칙을 본다.
- [위 단이 2권으로 고정돼 서명 전체 일치일 때도 다른 책이 붙는다] → 맞은 방식을 응답에 넣는 개선으로 미룬다.
- [주제 검색이 위 단과 거의 같은 책만 내면 아래 단이 빈다] → 아래 단을 숨기고 버튼을 남긴다.
- [Enter에서 요청이 하나 늘어 대화로 가는 길이 찾기 한 번만큼 늦어진다] → 찾기는 LLM이 없고 짧다. 실패하면 대화로 간다.

## Migration Plan

- DB 변경 없음. 배포는 서버 재시작과 화면 파일 교체뿐이다. 되돌리기는 이전 커밋으로.

## 사용자 확인 항목 (브라우저)

개발 DB 실험 기관(id 7) 키오스크 계정으로 사용자가 직접 확인한다. 네트워크 탭을 열어 둔다. LLM 호출은 B3·B4·B5·B10의 약 4회다.

- **B1** `채식` + Enter → 위 단 "이 책을 찾으시나요?"에 채식주의자, 아래 단 "'채식'과 관련된 책", [사서에게 물어보기]가 보인다. `/librarian/messages` 요청이 없다.
- **B2** B1의 아래 단에 위 단의 책이 다시 나오지 않는다.
- **B3** `요즘 읽을 만한 가벼운 에세이 추천해 줘` + Enter → 지금처럼 AI 사서가 답한다.
- **B4** 100자를 넘는 글 + Enter → `/catalog/search` 없이 AI 사서 대화로 간다.
- **B5** B1에서 [사서에게 물어보기] → 같은 글이 대화로 한 번 가고 버튼이 꺼진다. 다시 눌러도 요청이 없다.
- **B6** 입력 중 자동완성 후보를 화살표로 고르고 Enter → 지금처럼 그 책 카드(`/catalog/search`·`/catalog/topic` 없음).
- **B7** 자동완성의 "'질의'로 책 모두 찾기" → 기존 검색 결과 블록이 그대로다.
- **B8** 임베딩 서버를 끈 채 B1 → 아래 단이 키워드 결과로 나오고 오류 문구가 없다.
- **B9** 개발자 도구에서 `/catalog/topic`을 막고 B1 → 아래 단이 제목째 숨고 위 단과 버튼은 남는다.
- **B10** 개발자 도구에서 `/catalog/search`를 막고 Enter → 지금처럼 AI 사서 대화로 간다.
- **B11** 네트워크를 느리게(Slow 3G) 두고 Enter를 빠르게 두 번 → 두 단계 블록이 하나만 생긴다.
- **B12** 위·아래 단 카드의 누르기(비슷한 책), [담기], [이 책 물어보기]가 지금처럼 동작한다.
- **B13** [새 대화]와 무입력 비우기(`?idle_seconds=20`) 뒤 두 단계 블록이 지워진다.

## 미룰 것 (archive 때 roadmap "`add-two-step-search`에서 미룸"으로)

1. 서명·저자 찾기 응답에 맞은 방식(stage)을 넣고 위 단을 1권·2권으로 나누기(서명 전체 일치면 1권)
2. 위 단에서 빠진 찾기 결과 3~10번째를 "더 보기"로 보이기
3. 서명 찾기와 주제 검색을 동시에 부르기
4. 한두 글자 질의를 두 단계에서 빼기(`catalog/book-lookup`의 한두 글자 문제와 함께)
5. 주제 검색 REST의 `exclude` 인자(위 단 제외를 서버가)
6. 벡터만으로 나온 결과(키워드 근거 없음) 표시
7. `get_query_encoder`를 `app/library/deps.py`로 옮기기
8. 화면 동작의 Playwright 테스트(이미 24b 뒤로 적힌 줄에 합침)

## 결과

- 시작 전 기준(0.1): pytest 2040 통과·7 건너뜀, ruff 통과(DB를 `docker compose up -d db`로 띄운 뒤)
- 끝난 뒤(5.1): pytest 2055 통과·7 건너뜀(+15: `test_topic_api.py` 12, `test_web_ui.py` 3), ruff check·format 통과
- curl(5.2, 실험 기관 키오스크 토큰, LLM 0회·외부 API 0회):
  - 임베딩 서버 꺼짐: `/catalog/topic?q=채식` 200, 2권(채식주의자 1위, 소년이 온다). `/catalog/search?q=채식`은 채식주의자 1권. 토큰 없음 401, `q=" · "` 200 `[]`, 101자 422
  - 임베딩 서버 켜짐: `q=채식` 200, 10권(채식주의자 1위), `q=채식 소설` 200, 10권(채식주의자 1위). 서버 오류 로그 없음
- 구현 중 정한 것: 낱말이 없는 판정은 `clean_keywords`가 아니라 `match_key`로 한다(`compact`는 문장부호를 지우지 않아서 `·`가 낱말로 남았다). 결정 1의 서비스 함수 설명을 고쳤고 스펙 시나리오는 그대로다
- 아래 단 제목의 조사는 마지막 글자의 받침으로 `과`·`와`를 고른다(`relatedTitle`)
- B1~B13(5.3, 2026-11-24 사용자 확인): 모두 통과. 단, B11(느린 망에서 Enter 두 번)은 지연을 주지 않고 일반 3G로만 해 봤고, 지연 조건은 확인하지 않았다. 일반 3G에서는 첫 찾기 응답이 먼저 와서 두 번째 Enter가 새 검색이 돼 블록이 둘 생겼다(진행 중 중복만 막는 `searching` 가드의 의도된 동작이고, 코드로 확인함)
- 확인 중 알게 된 것: `채식`의 아래 단 첫 책이 소년이 온다인 이유는 저자가 아니라 소개글의 `채식주의자` 언급이다(키워드 순위가 소개 일치에 점수 1을 줌, 임베딩 서버가 꺼져도 나옴). 임베딩 텍스트는 저자를 뺐다. 주제 검색의 원래 동작이라 고치지 않는다
