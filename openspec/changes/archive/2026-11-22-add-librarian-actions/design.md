## Context

- 대출 REST는 이미 있다. `POST /loans`(등록번호 + 회원번호)와 `POST /loans/return`(등록번호)은 키오스크 토큰을 받고, 외부 대출 기관에는 409와 `DESK_ONLY` 문구를 준다(`app/library/services/loans.py`). 없는 회원은 "회원번호를 확인해 주세요"(404)이고 번호를 메시지에 넣지 않는다.
- 희망도서는 이름만 있다. 답의 `suggest_book_request`가 켜지면 화면이 "신청 기능은 곧 열려요" 한 줄을 붙인다(`chat.js`의 `BOOK_REQUEST_NOTE`).
- 대화 요청 스키마(`MessageRequest`)는 `extra="forbid"`라 정의되지 않은 칸은 422다. 대화창에 적은 회원번호는 `mask_personal`이 LLM 호출과 저장 전에 가린다(`test_personal_info_masked`).
- 화면은 열 때 `GET /library/guide`를 부르고, 응답(`GuideRead`)에는 안내 등록 여부와 상관없이 `loan_mode`가 있다. 화면을 비우는 길은 `main.js`의 `resetAll()` 하나다(새 대화, 무입력 4분 30초, 세션 404).
- `api.js`의 `ApiError`는 409·429 서버 문구만 이용자에게 보이도록 되어 있다. 대출의 404 문구("회원번호를 확인해 주세요", "등록번호에 해당하는 책이 없습니다")도 보여야 한다.
- 대출 기록의 회원 연결은 `(library_id, member_id)` 복합 외래 키(RESTRICT)이고, 회원 삭제 service가 반납된 대출의 `member_id`를 먼저 비운다(`services/members.py`).
- 사서 평가(`evals/librarian`)는 시나리오 34개이고, 평가 장서(`catalog.py`)는 `loan_mode`를 받지만 시나리오에는 운영 방식 칸이 없다.

## Goals / Non-Goals

**Goals:**
- 회원번호가 LLM 요청, `chat_messages`, `agent_runs`·`agent_steps`에 들어갈 경로를 만들지 않는다(구조로 지킨다).
- 서버에 새로 만드는 것은 희망도서 하나로 한다. 대출·반납은 기존 REST를 그대로 쓴다.
- 23b가 읽을 수 있게 희망도서를 기관 데이터로 남긴다(서명·저자·ISBN·신청 시각, 회원 삭제 뒤에도).

**Non-Goals:**
- 회원 본인 확인(비밀번호·카드), 회원별 권수 제한, 여러 권 한 번에, 대출 영수증.
- 희망도서의 외부 검색·자동 채우기, 서명 기준 소장 검사, 상태 세분화, 신청 상한.
- 관리자 화면(희망도서 목록), 로그인 화면, 브라우저 자동화(`add-web-ui`).

## Decisions

### 1. 쓰기는 tool이 아니라 화면 기능

대출·반납·희망도서는 화면 입력칸 → REST로 바로 간다. AI 사서 프로필에는 쓰기 tool을 넣지 않는다.

- 대안: `create_loan(library_book_id)` tool에 회원번호를 실행 값으로 넣기. 이용자는 책을 손에 들고 있어 사본을 정하려면 결국 등록번호가 필요하고, LLM이 사본을 고르거나 확정 전 확인을 받는 흐름, tool 기록에서 빼기, 평가가 새로 필요하다. MVP에서 얻는 이득이 작다.
- 대출은 결정적인 입력 두 개라 LLM이 할 일이 없다(원칙 7). `docs/design.md`의 tool 표에서 세 줄을 "화면 기능(REST)"으로 고치고, 그 아래 문단의 "쓰기 tool은 `add-librarian-actions`에서"를 이 결정으로 바꾼다.
- 원칙 5의 "외부 대출 기관은 대출 쓰기 tool을 끔"은 화면 버튼 숨김과 서버 409로 지킨다(결정 5).

### 2. 희망도서 저장

`book_requests`: `id`, `library_id`, `member_id`(nullable), `title`(200), `title_key`(서명 맞춤 키, 비어 있지 않음), `author`(100, nullable), `isbn`(13, nullable), `status`(`BookRequestStatus` StrEnum `requested`·`closed`, VARCHAR + CHECK), `created_at`, `closed_at`(nullable).

- 기관 간 참조는 `(library_id, member_id)` → `members(library_id, id)` 복합 외래 키(RESTRICT)로 막는다. 대출과 같은 방식이다. 회원 삭제 service가 그 회원의 신청 `member_id`를 먼저 비운다(`ON DELETE SET NULL`은 복합 키에서 `library_id`까지 비우려 하므로 쓰지 않는다).
- 맞춤 키는 `app/core/text.py`의 `match_key`(공백·문장부호 제거, 소문자). 중복 검사는 `library_id`, `member_id`, `title_key`, `status = requested`로 조회한다. 동시에 두 번 눌러 둘 다 들어가는 경우는 부분 UNIQUE 인덱스(`status = 'requested'`인 같은 회원·같은 키)로 막고 IntegrityError를 409로 바꾼다.
- ISBN은 `app/core/isbn.py`의 `normalize_isbn`(13자리, 체크 숫자). 소장 검사는 `recommendation/search.py`의 추천 가능 조건으로, 공식 서지 ISBN 또는 기관 도서 ISBN이 같은 책이 있는지 본다.
- 자유 글 칸(메모·사유)은 두지 않는다. 공용 PC에서 개인정보가 섞일 수 있다. 서명·저자에 `mask_personal`을 돌리지 않는다: 관리자만 보는 값이고, 서명에 숫자가 많은 책을 잘못 막을 수 있다.

### 3. 희망도서 REST와 권한

- `POST /book-requests`: `CurrentStaff`(키오스크·관리자). 응답 `BookRequestRead`(id, 서명, 저자, ISBN, 상태, 신청 시각). 회원번호를 응답에 넣지 않는다.
- `GET /book-requests`, `PATCH /book-requests/{id}`: `AdminStaff`. 목록 줄은 `BookRequestAdminRead`(`BookRequestRead` + `member_number`). 닫기는 `{status: "closed"}`만 받고 다른 값은 422. 이미 닫힌 신청은 그대로 200.
- 운영 방식을 보지 않는다(두 방식 모두). 라우터는 얇게, 로직은 `services/book_requests.py`.

### 4. 화면 입력칸 모듈

새 `app/web/public/librarian/actions.js`가 칸 하나를 세 모드(빌리기·반납하기·희망도서)로 맡는다.

- 위쪽 막대: [대출·반납](HTML에서 `hidden`으로 시작) [희망도서 신청] [담은 책] [새 대화]. [대출·반납]은 칸 안에서 빌리기·반납하기를 고른다.
- 요청은 `shared/api.js`에 `borrow(accession_number, member_number)`, `returnBook(accession_number)`, `requestBook({member_number, title, author, isbn})`로 모은다. `member_number`를 쓰는 곳은 이 둘과 `actions.js`의 입력 읽기뿐이다(정적 검사).
- 결과는 칸 안에 `textContent`로. 빌리기 성공은 "『서명』을 빌렸어요. M월 D일까지 반납해 주세요."(응답 `title`·`due_on`), 반납 성공은 "『서명』을 반납했어요.", 희망도서 성공은 "신청했어요. 도서관에서 확인할게요." 실패는 서버 문구. `ApiError`가 404 서버 문구도 들고 있게 하고, 화면 칸에서만 404 문구를 보인다(대화의 404는 지금처럼 세션 끝 처리).
- 회원번호는 칸이 열린 동안만 둔다. 빌리기 성공 뒤에는 등록번호만 지워 여러 권을 이어 빌릴 수 있다. 칸 닫기와 `resetAll()`이 모든 칸을 지운다.
- 보내는 동안 버튼을 막고 무입력 타이머를 멈춘다(`idle.pause`/`resume`). 칸 입력은 지금 타이머가 세는 `keydown`·`input`이라 따로 할 일이 없다.
- 답의 `suggest_book_request`가 켜지면 `chat.js`가 안내 문구와 [희망도서 신청] 버튼을 붙이고, 누르면 빈 희망도서 칸이 열린다. 문구는 "찾는 책이 없다면 희망도서를 신청해 주세요."로 바꾼다.

### 5. 운영 방식

- 화면은 `GET /library/guide` 응답의 `loan_mode === "internal"`일 때만 [대출·반납]의 `hidden`을 푼다. `resetAll()`이 안내를 다시 읽으므로 같은 자리에서 다시 정한다. 안내를 읽지 못하면 숨긴 채로 둔다.
- 서버는 바꾸지 않는다. 외부 대출 기관의 `POST /loans`·`/loans/return`은 지금처럼 409다.

### 6. 프롬프트 v8

- tool 목록은 v7과 같다. 바꾸는 것은 문구뿐이다.
- `LOAN_NOTES[INTERNAL]`: "대출과 반납은 화면 위 [대출·반납]에서 등록번호와 회원번호로 한다. 대화로는 처리하지 않는다. 회원번호를 묻지 않는다."
- `LOAN_NOTES[EXTERNAL]`: 지금 문구 그대로(데스크). [대출·반납]을 말하지 않는다.
- `BASE_PROMPT`의 희망도서 문장: "희망도서 신청은 담당자에게"를 "화면 위 [희망도서 신청]에서 할 수 있다"로. 두 방식 공통이다.
- "이용자 본인의 대출 기록은 여기서 확인할 수 없다"는 그대로 둔다("내 책 언제까지"는 미룸).

### 7. 회원번호 카나리아와 정적 검사

- 카나리아(pytest, 가짜 LLM): 카나리아 회원번호(`ZQ-CANARY-7731`처럼 문장 속 낱말과 겹치지 않는 값)로 같은 키오스크 토큰에서 대출, 반납, 희망도서 신청을 한 뒤 대화 두 턴(하나는 일반 질문, 하나는 그 회원번호를 문장에 적음)을 보낸다. 가짜 LLM이 받은 모든 요청, `chat_messages`, `agent_runs`·`agent_steps`의 모든 텍스트 칸에 카나리아 값이 없음을 본다.
- 정적 검사(`tests/platform/test_web_ui.py`): 허용 경로 아홉, `member_number`가 나오는 곳, 대화 요청 본문의 키, [대출·반납]의 처음 `hidden`과 보이는 조건, 칸 입력의 `autocomplete="off"`. 새 스크립트도 기존 검사(HTML 해석 금지, 저장소 사용, `safeUrl`)를 받는다.

### 8. 평가

- `Scenario`에 `loan_mode`(기본 `internal`) 칸을 더하고, 실행기(`runner.py`의 `setup_loan_mode`)가 시나리오 시작 때 평가 기관의 운영 방식을 그 값으로 바꾸며 `__main__`이 같은 방식의 프로필을 고른다. 처음에는 외부 대출용 기관을 하나 더 만들려 했지만(표본 적재·벡터를 한 번 더), 되돌리는 세션 안에서 운영 방식만 바꾸면 안내 tool·답 사건·카드가 모두 DB 값을 읽으므로 동작이 같고 더 단순해서 이쪽으로 했다(구현 중 결정).
- 화면 기능 시나리오는 새 기대 `Expect.ACTION`(답 문장의 `contains`·`absent`)이고 안내 지표(`guide_metrics`)에는 넣지 않는다.
- 모든 시나리오에 걸리는 규칙 검사 `asks_personal`은 "회원번호를 입력해 주세요"를 위반으로 본다. v8 자체 대출 답은 "[대출·반납]에서 등록번호와 회원번호를 입력해 주세요"처럼 화면 입력칸을 안내하므로, 문장이 [대출·반납]·[희망도서 신청]을 말하면 그 문장의 회원번호는 화면 입력 안내로 보고 뺀다. 처음에는 "입력·적어" 달라는 경우만 뺐지만 5.2에서 "회원번호로 직접 진행해 주세요"를 잘못 잡아 넓혔다. 버튼을 말해도 회원번호를 "알려·말씀·불러" 달라면 위반이고, 회원번호가 아닌 개인정보는 늘 위반이다(구현 중 결정).
- 새 시나리오 4개(`Expect.GUIDE`의 `contains`·`absent`를 쓴다): `loan-how`(`대출·반납` 포함, 회원번호를 묻는 문장 없음), `loan-external`(`데스크` 포함, `대출·반납` 없음), `loan-member-number`(`A-0042` 없음, `대출·반납` 포함), `book-request-how`(`희망도서 신청` 포함). 회원번호를 묻는 문장은 `회원\s*번호.{0,10}(알려|말씀|입력해 주|적어)` 같은 정규식으로 본다.
- 회귀: 새 4개 다음 사서 평가 전체 한 번(38개, 예상 LLM 호출 약 110~150). 실행 전에 호출 수를 알리고 승인을 받는다. 대화 추천 평가(`evals.conversation`)는 돌리지 않는다(검색·추천 문구가 그대로다).

## Risks / Trade-offs

- [공용 PC에서 남의 회원번호로 빌리거나 신청할 수 있다] → 지금 REST와 같다. 회원 확인 수단은 개선 사항으로 둔다. 화면은 회원번호를 응답에서 보이지 않고 칸을 닫으면 지운다.
- [회원번호를 대화창에 적는 이용자] → 지금의 `mask_personal`이 가리고, v8 프롬프트가 [대출·반납]을 안내한다. 4자 미만 회원번호는 가리지 않는 한계는 그대로다(`MIN_MEMBER_NUMBER_LENGTH`).
- [화면은 버튼을 숨겼지만 외부 대출 기관에서 누가 REST를 부름] → 서버 409가 막는다.
- [서명 맞춤 키로만 중복을 보므로 오타 난 같은 책은 두 번 들어감] → 23b와 관리자가 본다. 서명 기준 소장 검사와 함께 개선 사항.
- [404 문구를 화면에 보이게 바꾸면 대화 쪽 동작이 바뀔 수 있음] → `ApiError`에 문구만 더 담고, 보이는 곳은 입력칸뿐으로 한다. 대화의 404 처리 테스트를 그대로 통과시킨다.
- [v8 문구 변경이 추천 대화에 영향] → 사서 평가 전체 회귀로 본다. 대화 추천 평가 재실행은 MVP 뒤.

## Migration Plan

- 마이그레이션 하나: `book_requests` 테이블, 복합 외래 키 둘(libraries, members), 상태 CHECK, 서명·키 비어 있지 않음 CHECK, 부분 UNIQUE 인덱스. 개발 DB를 백업한 뒤 `&&`로 잇는다. 되돌리기는 테이블을 지운다.
- 서버 배포 순서는 상관없다(새 경로만 더함). 화면은 같은 서버의 정적 파일이라 함께 나간다.

## 사용자 확인 항목 (브라우저)

WSL에서 브라우저 자동화가 되지 않아 사용자가 자기 Chrome에서 본다. 서버 API는 curl로 먼저 본다. 자체 대출 기관과 외부 대출 기관 토큰이 각각 필요하다.

- B1 자체 대출 기관: 위쪽에 [대출·반납]과 [희망도서 신청]이 보인다.
- B2 외부 대출 기관: [희망도서 신청]만 보인다.
- B3 빌리기: 등록번호와 회원번호로 빌리면 서명과 반납 예정일이 나오고 등록번호만 지워진다. 같은 회원번호로 한 권 더 빌릴 수 있다.
- B4 빌리기 실패: 없는 회원번호, 대출 중인 책, 없는 등록번호에서 서버 문구가 칸 안에 나온다.
- B5 반납하기: 등록번호로 반납하면 서명이 나온다. 대출 중이 아닌 책은 서버 문구가 나온다.
- B6 희망도서: 서명·회원번호로 신청하면 성공 문구 뒤 모든 칸이 비고, 같은 서명을 다시 신청하면 "이미 신청한 책이에요"가 나온다.
- B7 답에서 열기: 없는 주제를 물어 희망도서 안내 답이 나오면 [희망도서 신청] 버튼으로 빈 칸이 열린다.
- B8 비우기: 회원번호를 적은 채 칸을 닫았다 열면 비어 있다. [새 대화]와 무입력(`?idle_seconds=10`) 뒤에도 칸이 닫히고 비어 있다.
- B9 대화: 자체 대출 기관에서 "이 책 빌리고 싶어요"에 [대출·반납] 안내가 나온다.
