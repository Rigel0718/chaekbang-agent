## ADDED Requirements

### Requirement: 화면 용어
로그인·이용자·관리자 화면의 문구는 한 대상을 한 이름으로 SHALL 부른다. 책 제목은 관리자 화면에서 "도서명"이고, 이용자 화면에서는 칸 이름만 "도서명", 문장 속은 "책 제목"이다. 책 단위는 "책"과 "권"이고 도서관이 가진 책 전체는 "책 목록"이다. 관리자 AI는 "AI 도우미", 이용자 AI는 "AI 사서", 연체 안내에 쓰는 문장은 "연체 안내 양식", 대출할 수 있는 상태는 "대출 가능"이다. 기록을 없애는 동작은 "삭제"이고 담은 책에서 빼는 동작은 "빼기"다. "제적"은 그대로 쓴다. 로그인 화면의 이름은 "직원 로그인"이다.

#### Scenario: 쓰지 않는 말
- **WHEN** 로그인·이용자·관리자 화면의 HTML과 스크립트에서 주석을 뺀 글자를 모으면
- **THEN** "사본", "장서", "소장", "서명", "운영 대화", "운영 에이전트", "안내문 틀", "책방", "책 이름", "이용 가능", "지울까요"가 없고, "사서"는 모두 "AI 사서"로만 나온다

#### Scenario: 탭과 로그인 화면 이름
- **WHEN** 관리자 화면 HTML의 탭과 로그인 화면 HTML의 제목을 읽으면
- **THEN** 탭은 [AI 도우미], [승인 목록], [희망도서], [오늘의 연체], [책 가져오기], [책 목록], [회원], [휴관일]이고, 로그인 화면의 문서 제목과 큰 제목은 "직원 로그인"이다

#### Scenario: 가져오기 열 이름
- **WHEN** 서버의 가져오기 열 이름 표를 읽으면
- **THEN** 서명 열의 이름은 "도서명"이고, 머리글이 "서명"인 파일도 그 열로 인식한다

### Requirement: 화면 버튼
화면 버튼은 짧게 SHALL 쓴다. 관리자 화면은 명사형(승인, 반려, 보내기, 적용, 삭제, 등록, 수정, 저장, 닫기, 처리 완료), 이용자 화면은 동사형(빌리기, 반납하기, 신청하기, 담기, 빼기)이다. 같은 동작은 화면 어디서나 같은 이름이고, 다른 동작은 다른 이름이다. [대출·반납]과 [희망도서 신청]은 AI 사서가 안내하는 이름이라 바꾸지 않는다.

#### Scenario: 바뀐 버튼
- **WHEN** 관리자·이용자 화면의 HTML과 스크립트에서 버튼 글자를 모으면
- **THEN** [더하기], [반려하기], [고치기], [사서에게 물어보기]가 없고 [등록], [보내기], [수정], [처리 완료], [AI 사서에게 묻기]가 있다

#### Scenario: 희망도서 처리
- **WHEN** 관리자가 [희망도서] 탭에서 신청 줄의 [처리 완료]를 누르고 확인하면
- **THEN** 그 신청이 목록에서 사라진다(브라우저 확인)

#### Scenario: AI 사서가 안내하는 버튼
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** [대출·반납]과 [희망도서 신청] 버튼 글자가 그대로다

### Requirement: 화면 문장의 말투와 마침표
화면에 보이는 문장은 서버가 준 문구까지 해요체로 SHALL 쓴다. 오류·요청 문장의 명령형은 "~해 주세요"로 쓴다(시작 화면·칸 설명 같은 안내의 "~하세요"는 둔다). 알림·오류·빈 화면·확인창·안내 문장은 마침표로 끝내고, 한 줄 표시(위 띠, 카드, 표의 상태 글)·진행 문구·버튼·탭·칸 이름·입력칸 안내에는 마침표를 붙이지 않는다. 빈 화면은 무엇이 없는지 밝히는 "~이 없어요." 한 줄이고 옆 버튼과 같은 안내를 되풀이하지 않는다. 성공은 알리지 않는다.

#### Scenario: 화면 문구의 말투
- **WHEN** 로그인·이용자·관리자 화면 스크립트와 HTML에서 주석을 뺀 글자를 모으면
- **THEN** "니다"로 끝나는 문장이 없다

#### Scenario: 빈 화면 문구
- **WHEN** 담은 책이 없는 회원이 담은 책 칸을 열고, 관리자가 승인 대기가 없는 [승인 목록]과 찾은 결과가 없는 [책 목록]을 보면
- **THEN** 각각 "담은 책이 없어요.", "승인할 초안이 없어요.", "찾은 책이 없어요."가 보인다(브라우저 확인)

#### Scenario: 이용자 검색 결과 없음
- **WHEN** 이용자 화면 스크립트에서 검색 결과가 없을 때의 문구를 읽으면
- **THEN** "찾은 책이 없어요."이고 AI 사서에게 물어보라는 문장은 없다

### Requirement: 실패 안내
연결 오류와 알 수 없는 실패의 화면 문구는 "잠시 뒤 다시 해 주세요." 하나로 SHALL 쓴다. 서버가 문구를 주면 그 문구만 보이고 화면이 같은 안내를 덧붙이지 않는다. 서버가 문구를 주지 않아도 상태 번호를 보이지 않는다.

#### Scenario: 실패 문구 하나
- **WHEN** 로그인·이용자·관리자 화면 스크립트에서 실패 문구를 모으면
- **THEN** 일반 실패 문구는 "잠시 뒤 다시 해 주세요." 하나이고 "시도해 주세요", "다시 눌러 주세요", "다시 열어 보세요"가 없다

#### Scenario: 상태 번호 없음
- **WHEN** 공통 요청 스크립트가 문구 없는 실패 응답으로 오류를 만들면
- **THEN** 오류 문구는 "잠시 뒤 다시 해 주세요."이고 상태 번호가 들어가지 않는다

#### Scenario: 정가 조회 장애
- **WHEN** 정가 조회를 쓸 수 없을 때 구매 요청서를 승인하면
- **THEN** 상세 안에 "지금 정가를 조회할 수 없어요. 잠시 뒤 다시 해 주세요."가 한 번만 보인다(브라우저 확인. 스크립트 검사로 503 갈래가 서버 문구에 글을 덧붙이지 않는지도 본다)

#### Scenario: 연체 안내 양식이 없음
- **WHEN** 승인한 연체 안내 양식이 없는 자체 대출 기관 관리자가 [오늘의 연체] 탭을 열면
- **THEN** "승인한 연체 안내 양식이 없어요. [AI 도우미]로 양식을 만들어 승인해 주세요."처럼 안내가 한 번만 보인다(브라우저 확인)

### Requirement: 확인창
확인창은 질문을 먼저 SHALL 쓰고, 되돌릴 수 없거나 이용자가 보게 되는 일일 때만 결과를 짧게 덧붙인다. 질문의 동사는 누른 버튼의 이름과 같다. 다만 [적용]처럼 버튼 이름만으로 무슨 일인지 알 수 없는 확인창은 바뀌는 것을 묻는다. 브라우저 버튼을 설명하는 말("확인을 눌러 주세요")은 쓰지 않는다.

#### Scenario: 질문 먼저
- **WHEN** 관리자 화면 스크립트에서 확인창 문구를 모두 모으면
- **THEN** 모두 첫 문장이 "까요?"로 끝나고 "확인을 눌러"가 없다

#### Scenario: 버튼과 같은 동사
- **WHEN** [휴관일], [회원], [책 가져오기]의 [삭제] 확인창 문구를 읽으면
- **THEN** 모두 "삭제할까요?"를 쓴다

### Requirement: 화면에 나오는 서버 문구
화면이 그대로 보이는 서버 문구(401·403·404·409·429·503의 `detail`)는 해요체 문장으로 끝에 마침표를 SHALL 붙인다. 내부 id, 영어 값(상태 값 등), 따옴표로 감싼 원래 입력, "을(를)"·"이(가)"·"은(는)" 같은 겸용 조사를 넣지 않는다. 조사는 앞말의 받침을 보고 코드가 고른다. 사람이 넣은 값(등록번호, 회원번호, ISBN, 날짜)은 넣을 수 있고 휴대폰 번호는 넣지 않는다. 대상 이름은 화면 말(책, 연체 안내 양식 등)로 쓴다.

#### Scenario: 없는 대상
- **WHEN** 관리자가 다른 기관의 휴관일 id로 삭제를 부르면
- **THEN** 404와 "휴관일을 찾을 수 없어요."이고 그 id가 문구에 없다

#### Scenario: 빌릴 수 없는 책
- **WHEN** 분실 상태 사본의 등록번호로 빌리면
- **THEN** 409와 "지금 빌릴 수 없는 책이에요."이고 문구에 `lost`가 없다

#### Scenario: 승인 흐름 문구의 조사
- **WHEN** 승인 대기가 아닌 큐레이션과 구매 요청서를 각각 반려하면
- **THEN** 409 문구는 "큐레이션이 …", "구매 요청서가 …"처럼 받침에 맞는 조사를 쓰고 "(가)"가 없다

#### Scenario: 서버 문구의 말투
- **WHEN** 화면에 나오는 서버 문구를 만드는 코드(`app/core`, `app/library`의 오류 문구)를 검사하면
- **THEN** "니다"로 끝나는 문장이 없고, "세요"는 "주세요"로만 나온다

#### Scenario: 겸용 조사 없음
- **WHEN** 화면에 나오는 서버 문구를 만드는 코드(`app/core`, `app/library`의 오류 문구)를 검사하면
- **THEN** "을(를)", "이(가)", "은(는)", "과(와)", "으로(로)"가 없다

#### Scenario: 조사 고르기
- **WHEN** 조사 함수에 "큐레이션"·"구매 요청서"·"휴관일"·"기록"과 을/를, 이/가, 은/는, 으로/로를 넣으면
- **THEN** "큐레이션을", "구매 요청서를", "휴관일이", "구매 요청서는", "휴관일로", "기록으로"처럼 받침에 맞게 붙는다(받침 ㄹ에는 "로")

#### Scenario: 사람이 넣은 값
- **WHEN** 이미 쓰는 등록번호로 사본을 등록하면
- **THEN** 409와 "이미 쓰는 등록번호예요: (그 등록번호)"이다


## MODIFIED Requirements

### Requirement: 이용자 화면의 무입력·이용 상한 비우기
이용자 화면은 두 시계로 화면을 MUST 비운다. 시계가 하는 일은 로그인 여부에 따라 다르다.
- **무입력**: 마지막 입력에서 1분이다. 45초에 알림을 띄우고, 입력하면 알림을 닫고 다시 센다. 답을 받는 동안에는 세지 않는다. 로그인하지 않았으면 화면을 비우고 시작 화면을 보인다(대화 종료, 담은 책·입력칸 지움). 로그인 중이면 **회원만 로그아웃하고 바로 시작 화면**을 보인다(키오스크 토큰은 그대로).
- **이용 상한**: **로그인한 순간부터** 3분이다. 2분 30초에 알림을 띄운다. 입력해도 늘어나지 않고, 답을 받는 중에도 멈추지 않는다. 끝나면 회원만 로그아웃하고 바로 시작 화면을 보인다. 로그인하지 않았으면 이용 상한은 없다.

회원 로그아웃은 서버 회원 세션을 끊고 **대화(대화 종료, 검색 결과, 자동완성), 화면의 담은 책, 입력칸을 모두 비운다.** 서버에 보관한 담은 책은 지우지 않는다(다시 로그인하면 나온다). 그리고 **바로 시작 화면**을 보인다(로그아웃을 알리는 문구도, 대화 화면으로 돌아오는 일도 없다). 버튼, 무입력, 이용 상한이 모두 같다. 서버 회원 세션 오류(403)만 시작 화면 없이 화면을 로그아웃하고 로그인 칸을 연다. 답을 받는 중이었으면 그 답은 끊긴다. 시작 화면에서는 어떤 시계도 세지 않는다(시작 화면을 누른 뒤 첫 입력부터 익명 무입력 시계가 센다). 알림은 화면 아래 띠에 문구와 남은 초를 글자로 보인다. 로그인 중의 문구는 "N초 뒤 로그아웃해요."와 "N초 뒤 이용 시간이 끝나 로그아웃해요."다. 두 시계 모두 서버 AI 사서 세션의 무입력 시간(5분)보다 짧다.

익명 상태에서 시간이 다 돼 비우거나 회원이 로그아웃하면 **시작 화면**("화면을 눌러 시작하세요")을 보이고, 누르면 대화 화면으로 간다. 시작 화면은 화면을 처음 열 때도 보인다. 두 시계 모두 키오스크 토큰은 그대로 두고 로그아웃하지 않는다(다음 이용자가 직원 계정 없이 쓸 수 있어야 한다). [새 대화]와 세션 끝(404)은 시작 화면 없이 대화만 비운다.

#### Scenario: 시간 값
- **WHEN** 이용자 화면 스크립트의 시간 값을 읽으면
- **THEN** 무입력은 60초·알림 45초, 이용 상한은 180초·알림 150초이고, 둘 다 서버 설정 `librarian_session_idle_minutes`(5분)보다 짧다. 서버 회원 세션 수명은 이용 상한과 같은 3분이다

#### Scenario: 무입력 비우기
- **WHEN** 로그인하지 않은 채 45초 동안 입력하지 않으면 알림이 뜨고, 입력 없이 1분이 되면
- **THEN** 화면이 비워지고 시작 화면이 보인다(브라우저 확인)

#### Scenario: 익명은 이용 상한이 없음
- **WHEN** 로그인하지 않은 채 3분이 넘도록 계속 입력하며 쓰면
- **THEN** 화면은 비워지지 않고 이용 상한 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 무입력 알림과 연장
- **WHEN** 이용 중 45초 동안 입력하지 않으면 알림이 뜨고, 그때 화면을 누르면
- **THEN** 알림이 닫히고 다시 1분을 센다. 로그인 중의 알림 문구는 "N초 뒤 로그아웃해요."다(브라우저 확인)

#### Scenario: 로그인 중 무입력 로그아웃
- **WHEN** 로그인한 뒤 알림에도 입력하지 않아 1분이 되면
- **THEN** 회원만 로그아웃되어 대화와 화면의 담은 책과 입력칸이 비고, 바로 시작 화면이 보인다(로그아웃 문구 없음). 같은 번호로 다시 로그인하면 담은 책이 나온다(브라우저 확인)

#### Scenario: 이용 상한
- **WHEN** 로그인한 뒤 계속 입력하며 쓰다가 2분 30초가 되면 알림이 뜨고, 입력을 이어 가도 3분이 되면
- **THEN** 회원만 로그아웃되어 대화가 비워지고 바로 시작 화면이 보이며, 답을 받는 중이었으면 그 답은 끊긴다(브라우저 확인)

#### Scenario: 쓰지 않는 화면
- **WHEN** 비운 화면에 아무도 입력하지 않으면
- **THEN** 어떤 시계도 시작하지 않고 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 로그아웃 뒤 익명 시계
- **WHEN** 회원 로그아웃으로 시작 화면이 보이는 채 아무도 입력하지 않으면
- **THEN** 시계가 다시 시작하지 않고 시작 화면 그대로다. 시작 화면을 눌러 입력하면 그때부터 익명 무입력 시계가 센다(브라우저 확인)

#### Scenario: 시작 화면
- **WHEN** 시작 화면을 누르면
- **THEN** 시작 화면이 사라지고 대화 화면이 보인다(브라우저 확인)

#### Scenario: 처음 열 때
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** 시작 화면이 숨김이 아닌 상태로 있다

#### Scenario: 로그아웃하지 않음
- **WHEN** 시간이 다 돼 비우거나 회원을 로그아웃하는 길(시계가 부르는 함수와 시작 화면을 보이는 함수)을 검사하면
- **THEN** 키오스크 토큰을 지우거나 로그인 화면으로 보내거나 `/auth/logout`을 부르는 곳이 없다

#### Scenario: 새 대화는 시작 화면 없이
- **WHEN** [새 대화]를 누르면
- **THEN** 대화가 비워지고 시작 화면은 보이지 않는다(브라우저 확인)

### Requirement: 관리자 화면의 탭과 운영 방식
관리자 화면은 한 페이지에 탭 여덟(AI 도우미, 승인 목록, 희망도서, 오늘의 연체, 책 가져오기, 책 목록, 회원, 휴관일)을 SHALL 둔다. 열린 탭은 주소 hash로 기억한다. 기관 정보(`GET /library`)의 `loan_mode`가 `internal`일 때만 [오늘의 연체] 탭, 승인 목록의 연체 안내 양식 묶음, [책 목록] 탭을 보이고, `external`일 때만 [책 가져오기] 탭을 보인다. 기관 정보를 읽지 못하면 운영 방식에 따른 것을 모두 숨긴다. [회원]과 [휴관일]은 두 방식 모두 보인다. 숨긴 탭의 주소로 열면 [AI 도우미]를 연다. 최종 판단은 서버(409)가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 관리자 화면 HTML을 읽으면
- **THEN** [오늘의 연체] 탭, 연체 안내 양식 묶음, [책 가져오기] 탭, [책 목록] 탭은 숨김 상태로 시작하고 [회원]·[휴관일] 탭은 숨기지 않는다

#### Scenario: 보이는 조건
- **WHEN** 관리자 화면 스크립트에서 위 네 가지를 보이게 하는 곳을 검사하면
- **THEN** 기관 정보의 `loan_mode`를 한 곳에서 읽고, 연체 탭·양식 묶음·[책 목록] 탭은 `internal`일 때만, [책 가져오기] 탭은 `external`일 때만 보인다

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관의 관리자로 관리자 화면을 열면
- **THEN** [책 가져오기]·[회원]·[휴관일] 탭이 보이고 [오늘의 연체]·[책 목록] 탭과 연체 안내 양식 묶음은 보이지 않는다(브라우저 확인)

#### Scenario: 자체 대출 기관
- **WHEN** 자체 대출 기관의 관리자로 `#imports` 주소를 열면
- **THEN** [책 가져오기] 탭은 보이지 않고 [AI 도우미]가 열린다(브라우저 확인)

#### Scenario: 외부 대출 기관의 장서 주소
- **WHEN** 외부 대출 기관의 관리자로 `#collection` 주소를 열면
- **THEN** [책 목록] 탭은 보이지 않고 [AI 도우미]가 열린다(브라우저 확인)

### Requirement: 운영 대화 화면
관리자 화면의 [AI 도우미]는 `POST /admin-agent/messages`의 사건을 읽어 답 문장을 글자로 SHALL 보이고, 답 아래에 결과 사건의 표와 [초안 보기]를 보인다(운영 대화의 표, 초안 보기). `status`는 답이 오기 전까지 한 줄로 보이고, `unsupported`인 답에는 못 하는 분석이라는 표시를 붙인다. [새 대화]는 대화 종료를 부르고 화면을 비운다. 세션이 끝나 404면 세션을 버리고 안내하며, 보낸 문장을 입력칸에 되돌린다. 답이 끝나면 승인 대기 수를 다시 세어 [승인 목록] 탭에 보인다.

#### Scenario: 대화 요청의 본문
- **WHEN** 관리자 화면 스크립트에서 운영 에이전트 대화 요청 본문을 만드는 곳을 검사하면
- **THEN** 본문의 키는 `session_id`, `message`뿐이다

#### Scenario: 답과 승인 대기 수
- **WHEN** [AI 도우미]에서 큐레이션 초안을 만들어 달라고 하고 답이 끝나면
- **THEN** 답 문장이 보이고 [승인 목록] 탭의 승인 대기 수가 하나 는다(브라우저 확인)

#### Scenario: 새 대화는 표도 비움
- **WHEN** 표가 보이는 대화에서 [새 대화]를 누르면
- **THEN** 답 문장과 표가 모두 사라진다(브라우저 확인)

### Requirement: 승인 목록
관리자 화면의 승인 목록은 큐레이션, 연체 안내 양식, 구매 요청서를 묶음별로 SHALL 보이고, 기본으로 승인 대기만 보인다. 줄을 누르면 상세를 보이고 상태에 맞는 동작만 보인다.
- 승인 대기: [승인](확인 한 번)과 [반려](누르면 사유 칸과 [보내기]가 열린다. 사유 필수, 비어 있으면 요청하지 않음)
- 게시한 큐레이션: [게시 내리기]
- 그 밖의 상태: 동작 없음. 반려된 것은 반려 사유를 보인다

구매 요청서의 확정 전 상세는 항목별 추정 단가·금액, 추정 총액과 조회 시각을 보인다. 가격 없는 항목은 "가격 없음"으로, 조회할 수 없으면 그렇다고 보인다. 확정본은 기록한 단가·금액·총액·조회 시각·출처를 보인다. 승인·반려·내리기가 409나 503이면 서버 문구를 상세 안에 글자로 보이고 상태를 바꾼 것처럼 보이지 않는다. 성공하면 상세와 목록을 서버에서 다시 읽는다. 초안 만들기·고치기·지우기·다시 제출은 화면에 두지 않는다.

#### Scenario: 상태별 동작
- **WHEN** 승인 대기, 게시, 반려 상태의 큐레이션 상세를 차례로 열면
- **THEN** 각각 [승인]·[반려], [게시 내리기], 반려 사유만 보인다(브라우저 확인)

#### Scenario: 빈 반려 사유
- **WHEN** [반려]로 연 사유 칸을 비운 채 [보내기]를 누르면
- **THEN** 요청을 보내지 않고 사유를 적으라고 보인다(브라우저 확인)

#### Scenario: 가격 없는 구매 요청서 승인
- **WHEN** 가격 없는 항목이 있는 구매 요청서를 승인하면
- **THEN** 서버의 409 문구(ISBN 포함)가 상세 안에 보이고 요청서는 승인 대기로 남는다(브라우저 확인)

#### Scenario: 확정본 표시
- **WHEN** 확정된 구매 요청서 상세를 열면
- **THEN** 기록한 단가·금액·총액·조회 시각·출처가 보이고 동작 버튼이 없다(브라우저 확인)

### Requirement: 관리자 화면의 회원 값
관리자 화면은 회원 값(회원번호, 이름, 전화번호, 채운 안내 문안)을 [희망도서], [오늘의 연체], [회원] 탭에서만 MUST 보인다. 그 탭에 들어올 때마다 서버에서 다시 읽는다(연체·신청·회원은 그사이 바뀌므로 지난 목록을 다시 쓰지 않는다). 회원 값을 복사·출력·내려받는 버튼을 두지 않고, 브라우저 콘솔에 쓰지 않는다. 승인한 연체 안내 양식이 없어 오늘의 연체 목록이 409면 서버 문구("승인한 연체 안내 양식이 없어요.") 뒤에 [AI 도우미]로 양식을 만들어 승인하라는 안내를 한 번만 붙인다.

#### Scenario: 회원 값을 읽는 곳
- **WHEN** 관리자 화면 스크립트에서 `member_number`, `phone`을 읽는 곳을 모두 모으면(이름 `name`은 기관 이름과 겹쳐 브라우저 확인으로 본다)
- **THEN** 희망도서 목록, 오늘의 연체 목록, 회원 목록·입력을 그리는 곳뿐이다

#### Scenario: 콘솔 출력 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `console.` 호출이 없다

#### Scenario: 탭에 돌아오면 다시 읽음
- **WHEN** [오늘의 연체] 탭을 연 뒤 다른 탭에서 대출을 반납하고 돌아오면
- **THEN** 서버에서 다시 읽은 목록이 보이고 반납한 줄은 없다(브라우저 확인)

### Requirement: 두 단계 결과
두 단계 결과는 위 단 "이 책을 찾으시나요?"(서명·저자 찾기 결과의 앞 2권), 아래 단 "'질의'와 관련된 책"(같은 질의의 주제 검색 결과에서 위 단의 책을 뺀 것), [AI 사서에게 묻기]로 SHALL 이루어진다. 위 단은 주제 검색을 기다리지 않고 먼저 보인다. 아래 단이 비거나 주제 검색이 실패하면 아래 단을 제목째 숨긴다. 카드는 다른 찾기 결과와 같은 카드다. [AI 사서에게 묻기]는 같은 글을 AI 사서 대화로 한 번 보내고 꺼진다. 두 단계 결과는 서버 대화 세션을 만들거나 바꾸지 않는다.

#### Scenario: 위 단과 아래 단
- **WHEN** `채식`으로 두 단계 결과가 보이면
- **THEN** 위 단에 채식주의자를 포함한 2권 이하가 있고, 아래 단에는 위 단의 책이 없다

#### Scenario: 위 단 권수
- **WHEN** 화면 스크립트의 위 단 권수를 읽으면
- **THEN** 2다

#### Scenario: 아래 단이 비거나 실패
- **WHEN** 주제 검색 요청이 실패하면
- **THEN** 아래 단과 그 제목이 보이지 않고 위 단과 [AI 사서에게 묻기]는 남는다

#### Scenario: 사서에게 물어보기
- **WHEN** [AI 사서에게 묻기]를 누르면
- **THEN** 같은 글이 AI 사서 대화로 한 번 가고 버튼이 꺼져 다시 눌러도 요청이 없다

#### Scenario: 화면 비우기
- **WHEN** 두 단계 결과가 있는 화면을 [새 대화]나 무입력으로 비우면
- **THEN** 두 단계 결과도 지워진다

### Requirement: 담은 책 화면
이용자 화면은 로그인한 회원의 담은 책을 서버(`/basket`)에 MUST 보관하고 불러온다. 카드의 [담기]는 로그인한 동안에만 있고, 로그인하면 담은 책을 자동으로 불러온다. 담기·빼기·비우기는 서버가 성공한 뒤에 화면에 반영한다. 로그아웃(버튼, 무입력, 이용 상한, 403)은 화면의 담은 책만 비우고 서버에는 남긴다. 성공이나 불러오기에는 문구를 띄우지 않고, 실패 문구는 둘뿐이다.
- 10권 상한(409): "담은 책은 10권까지예요." 그 밖의 실패(404, 연결 오류): "잠시 뒤 다시 해 주세요."
- 401은 키오스크 로그인 화면으로, 403은 회원 로그아웃과 로그인 칸으로 간다. 불러오기가 실패하면 문구 없이 빈 목록으로 시작한다.
- 담은 책 칸에 [모두 빼기]가 있고(담은 책이 없으면 숨김), 줄에는 도서명·서가·대출 상태가 있으며 외부 대출 기관에서는 "대출 상태 … 기준"을 함께 보인다.
- [새 대화]는 담은 책을 건드리지 않는다.

#### Scenario: 로그인 전에는 담기가 없음
- **WHEN** 로그인하지 않고 카드를 보면
- **THEN** 카드에 [담기]가 없고 위 띠에 담은 책 표시가 없다(브라우저 확인)

#### Scenario: 로그인·로그아웃이 카드에 바로 적용됨
- **WHEN** 카드가 떠 있는 채 로그인하면, 이어서 로그아웃하면
- **THEN** 이미 떠 있던 카드에 [담기]가 바로 나타나고, 로그아웃하면 바로 사라진다(브라우저 확인)

#### Scenario: 담고 빼기
- **WHEN** 카드의 [담기]를 누르면
- **THEN** 서버에 저장된 뒤 버튼이 [담김]으로 바뀌고 담은 책 숫자가 늘며, 다시 누르거나 줄의 ×를 누르면 빠지고 버튼이 [담기]로 돌아온다(브라우저 확인)

#### Scenario: 모두 빼기
- **WHEN** 담은 책 칸에서 [모두 빼기]를 누르면
- **THEN** 담은 책이 모두 비고 카드 버튼은 [담기]로 돌아오며, 담은 책이 없으면 [모두 빼기]는 보이지 않는다(브라우저 확인)

#### Scenario: 로그아웃하고 다시 로그인
- **WHEN** 책을 담고 로그아웃한 뒤 같은 번호로 다시 로그인하면
- **THEN** 담은 책이 문구 없이 숫자와 목록으로 그대로 나온다. 이 확인은 버튼, 이용 상한, 무입력, 새로 고침 네 경우에 한다(브라우저 확인)

#### Scenario: 10권 상한
- **WHEN** 10권을 담은 뒤 다른 책의 [담기]를 누르면
- **THEN** 담지 않고 "담은 책은 10권까지예요."를 보인다(브라우저 확인)

#### Scenario: 실패하면 화면이 바뀌지 않음
- **WHEN** 담기 요청이 연결 오류로 실패하면
- **THEN** 버튼은 [담기]로 남고 "잠시 뒤 다시 해 주세요."를 보인다(브라우저 확인)

#### Scenario: 외부 대출 기관의 담은 책 줄
- **WHEN** 외부 대출 기관에서 책을 담으면
- **THEN** 담은 책 줄에 대출 상태 기준 시각이 보인다(브라우저 확인)

#### Scenario: 회원 토큰 헤더와 저장소 검사
- **WHEN** 화면 스크립트에서 담은 책 요청을 만드는 곳을 검사하면
- **THEN** 모두 회원 토큰 헤더를 붙이고, 담은 책을 브라우저 저장소에 쓰는 곳이 없다

### Requirement: 장서 가져오기 화면
관리자 화면의 [책 가져오기]는 파일(xlsx, CSV)을 올려 미리 보기를 만들고, 요약(전체·새로·바뀜·그대로·건너뜀 행 수, 파일에서 빠진 책 수, 인식한 열)과 확인할 행을 SHALL 보인다. 확인할 행은 건너뛴 행과 표기 넷(`invalid_isbn`, `unknown_status`, `purchased_without_isbn`, `purchased_without_price`)이고 20줄씩 더 본다. 표기와 열 이름은 한국어로 보인다. 탭에 들어올 때마다 지난 가져오기 목록을 다시 읽고, 기록을 누르면 그 요약을 연다.

필수 열을 찾지 못한 응답(422)에 파일 머리글이 있으면 못 찾은 필수 열마다 머리글에서 고르게 하고, 고른 열을 `column_mapping`으로 같은 파일과 다시 보낸다.

#### Scenario: 화면이 읽는 값
- **WHEN** 가져오기 화면 스크립트가 읽는 기록과 행의 필드를 응답 스키마와 맞춰 보면
- **THEN** 모두 `HoldingImportRead`와 `HoldingImportRow`에 있는 필드다

#### Scenario: 열과 표기의 이름
- **WHEN** 가져오기 화면 스크립트의 열 이름·표기 이름 표를 서버의 열 정의·표기와 맞춰 보면
- **THEN** 열 키와 한국어 이름이 서버와 같고 표기 넷이 모두 있다

#### Scenario: 미리 보기 요약
- **WHEN** 정상 파일을 올리면
- **THEN** 행 수, 파일에서 빠진 책 수, 인식한 열이 보이고 책 목록은 바뀌지 않는다(브라우저 확인)

#### Scenario: 열 고르기
- **WHEN** 저자 열의 머리글이 인식되지 않는 파일을 올리고, 보이는 목록에서 그 머리글을 골라 다시 올리면
- **THEN** 처음에는 저자 열을 고르는 칸이 보이고, 다시 올리면 미리 보기 요약이 보인다(브라우저 확인)

#### Scenario: 읽을 수 없는 파일
- **WHEN** 예전 `.xls` 파일이나 빈 파일을 올리면
- **THEN** 열 고르기 없이 서버 문구가 보인다(브라우저 확인)

#### Scenario: 확인할 행
- **WHEN** 미리 보기에서 확인할 행의 종류를 누르면
- **THEN** 그 행의 행 번호, 등록번호, 도서명, 저자, 사유가 20줄까지 보이고 더 있으면 [더 보기]가 있다(브라우저 확인)

#### Scenario: 기증처
- **WHEN** 기증처 열이 있는 파일을 올려 요약과 행 목록을 보면
- **THEN** 화면에 기증처 값이 없다(브라우저 확인)

### Requirement: 운영 대화의 표
[AI 도우미]는 `result` 사건의 표를 모았다가 `answer`가 오면 답 말풍선 아래에 받은 순서대로 SHALL 보인다. `answer` 없이 끝나면 모은 표를 보이지 않는다. 표는 제목, 설명 줄, 열 이름과 행이다. 막대 열이 있으면 그 칸에 숫자와 함께 그 열의 가장 큰 값에 맞춘 막대를 그린다. 잘린 표에는 아래에 전체 수와 보인 수를 보인다. 빈 칸은 `-`다. 넓은 표는 그 표만 가로로 스크롤된다. 모르는 `kind`의 결과는 건너뛴다. 칸 값은 글자로만 넣는다.

#### Scenario: 사건 처리
- **WHEN** 관리자 화면의 [AI 도우미] 스크립트를 검사하면
- **THEN** `result` 사건을 받아 `answer`를 받은 뒤에만 그리고, 표는 `table`, 초안은 `draft` 종류만 처리한다

#### Scenario: 분야별 표와 막대
- **WHEN** 자체 대출 기관 관리자가 "분야별로 책이 몇 권씩 있어?"라고 물으면
- **THEN** 답 아래에 분야마다 한 줄인 표가 보이고 권수 칸에 막대가 있다(브라우저 확인)

#### Scenario: 목록 표
- **WHEN** "분실된 책 보여줘"라고 물으면
- **THEN** 도서명, 저자, 등록번호, 청구기호 표가 막대 없이 보인다(브라우저 확인)

#### Scenario: 합계만인 답
- **WHEN** "우리 도서관 책이 모두 몇 권이야?"라고 물으면
- **THEN** 표 없이 답 문장만 보인다(브라우저 확인)

#### Scenario: 좁은 창
- **WHEN** 열이 넷인 표가 보일 때 창을 좁히면
- **THEN** 그 표만 가로로 스크롤되고 대화 화면은 가로로 넘치지 않는다(브라우저 확인)

### Requirement: 초안 보기
[AI 도우미]는 초안 결과마다 답 아래에 [초안 보기] 버튼을 SHALL 둔다. 누르면 [승인 목록] 탭으로 바꾸고 그 종류 묶음에서 그 초안을 펼쳐 보이게 스크롤한다. 승인 대기 보기에 없으면 전체 보기로 바꿔 찾고, 그래도 없으면 승인 목록에 찾지 못했다는 짧은 문구를 보인다. [AI 도우미]의 대화는 탭을 바꿔도 남는다. 초안 종류 이름은 결과 사건의 값(`curation`, `template`, `purchase`)을 승인 목록의 묶음(큐레이션, 연체 안내 양식, 구매 요청서)에 맞춘다.

#### Scenario: 종류 이름 맞춤
- **WHEN** [AI 도우미] 스크립트의 초안 종류 표를 서버의 초안 결과 종류 값과 맞춰 보면
- **THEN** 셋이 모두 같고 각각 승인 목록의 묶음 하나로 간다

#### Scenario: 방금 만든 초안
- **WHEN** 큐레이션 초안을 만든 답 아래의 [초안 보기]를 누르면
- **THEN** [승인 목록] 탭의 큐레이션 묶음에서 그 초안이 펼쳐져 화면에 보인다(브라우저 확인)

#### Scenario: 대화로 돌아오기
- **WHEN** [초안 보기]로 승인 목록을 본 뒤 [AI 도우미] 탭을 누르면
- **THEN** 대화와 표가 그대로 있다(브라우저 확인)

#### Scenario: 이미 승인한 초안
- **WHEN** 승인한 초안의 [초안 보기]를 누르면
- **THEN** 승인 목록이 전체 보기로 바뀌고 그 초안이 펼쳐진다(브라우저 확인)

### Requirement: 장서 화면의 사본 찾기
관리자 화면의 [책 목록]은 들어오면 `GET /holdings`(찾기 글자 없음)로 최근에 등록한 사본부터 표로 SHALL 보인다. 찾기 칸 하나(도서명·저자·등록번호)로 `GET /holdings?q=`를 불러 찾은 사본을 같은 표로 보이고, 찾은 동안에는 [전체 보기]가 있어 누르면 칸을 비우고 처음 목록으로 돌아간다. 칸을 비우고 [찾기]를 눌러도 처음 목록이다. 열은 등록번호, 도서명, 저자, 청구기호, 상태이고 20줄씩 [더 보기]로 더 읽는다. 찾은 책이 없으면 "찾은 책이 없어요."로 알린다. 탭에 다시 들어오면 지난 화면(처음 목록이나 찾기)을 서버에서 다시 읽는다. 서명·저자 같은 서버 값은 글자로만 넣는다.

#### Scenario: 찾기 요청
- **WHEN** 장서 화면 스크립트를 검사하면
- **THEN** 사본 목록과 찾기는 `GET /holdings`에 `q`(찾을 때만), `limit`, `offset`만 보내고 `status`를 보내지 않는다

#### Scenario: 처음 목록과 전체 보기
- **WHEN** 자체 대출 기관 관리자가 [책 목록] 탭을 열고, 도서명으로 찾은 뒤 [전체 보기]를 누르면
- **THEN** 처음에는 최근에 등록한 사본부터 보이고, 찾으면 [전체 보기]가 생기며, 누르면 칸이 비고 처음 목록으로 돌아가 [전체 보기]가 사라진다(브라우저 확인)

#### Scenario: 읽는 필드
- **WHEN** 장서 화면 스크립트가 읽는 사본 필드를 응답 스키마와 맞춰 보면
- **THEN** 모두 `HoldingRead`에 있는 필드다

#### Scenario: 분실한 책 다시 찾기
- **WHEN** 자체 대출 기관 관리자가 한 권뿐인 책을 분실로 바꾼 뒤 그 도서명으로 다시 찾으면
- **THEN** 그 사본이 분실 상태로 보인다(브라우저 확인)

#### Scenario: 등록번호로 찾기
- **WHEN** 등록번호를 그대로 쳐서 찾으면
- **THEN** 그 사본이 맨 위에 보인다(브라우저 확인)

### Requirement: 장서 화면의 상태 바꾸기
[책 목록]의 줄은 대출 중이 아니면 상태 고르기(대출 가능, 분실, 훼손, 제적)를 SHALL 둔다. 고르면 `PATCH /holdings/{id}`에 상태만 보내고, 제적일 때만 확인을 한 번 더 받는다. 성공하면 문구 없이 응답 값으로 그 줄을 고친다. 실패하거나 확인을 취소하면 고르기를 이전 값으로 되돌리고, 실패는 서버 문구를 글자로 보인다. 대출 중인 줄은 고르기 대신 "대출 중"과 [반납]을 두고, 확인 한 번 뒤 그 등록번호로 `POST /loans/return`을 부른 다음 그 줄을 다시 읽는다.

#### Scenario: 고를 수 있는 상태
- **WHEN** 장서 화면 스크립트의 상태 고르기 값을 검사하면
- **THEN** `available`, `lost`, `damaged`, `withdrawn` 넷뿐이고 `on_loan`은 없다

#### Scenario: 제적만 한 번 더 묻기
- **WHEN** 장서 화면 스크립트의 상태 바꾸기를 검사하면
- **THEN** `withdrawn`을 보내기 전에만 확인을 받고 취소하면 요청하지 않는다

#### Scenario: 분실 처리와 되돌리기
- **WHEN** 대출 가능 사본을 분실로 고른 뒤 다시 대출 가능으로 고르면
- **THEN** 문구 없이 상태가 바뀌고 다시 찾아도 대출 가능이다(브라우저 확인)

#### Scenario: 대출 중인 사본 반납
- **WHEN** 대출 중인 줄의 [반납]을 누르고 확인하면
- **THEN** 그 줄이 대출 가능이 되고 상태 고르기가 생긴다(브라우저 확인)

### Requirement: 장서 화면의 책 등록
[책 목록]의 [책 등록]은 ISBN, 도서명·저자, 사본 정보를 받아 기존 REST로 SHALL 등록한다. ISBN이 있으면 먼저 `GET /library-books?isbn=`으로 확인해, 있는 책이면 도서명만 보이고 사본 칸만 받는다. 없거나 ISBN이 비면 `POST /library-books` 뒤에 `POST /holdings`를 부른다. 사본 칸은 등록번호(필수), 청구기호, 입수 구분(매입·기증), 매입이면 구입가(필수), 기증이면 기증처다. 필수 칸이 비면 요청하지 않는다. 실패는 서버 문구를 글자로 보인다. 성공하면 문구 없이 칸을 닫고 그 등록번호로 찾은 결과를 보인다.

#### Scenario: 이미 있는 책
- **WHEN** 장서 화면 스크립트의 책 등록을 검사하면
- **THEN** ISBN이 있으면 기관 도서 등록 전에 `GET /library-books`를 `isbn`으로 부르고, 찾은 책이 있으면 `POST /library-books` 없이 `POST /holdings`만 부른다

#### Scenario: 사본 등록이 실패한 뒤 다시 누르기
- **WHEN** 기관 도서는 만들어지고 사본 등록이 실패한 뒤 같은 칸에서 [등록]을 다시 누르면
- **THEN** 화면은 만든 기관 도서로 `POST /holdings`만 부른다(스크립트 검사와 브라우저 확인)

#### Scenario: 보내는 값
- **WHEN** 장서 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 기관 도서는 `LibraryBookCreate`, 사본은 `HoldingCreate`에 있는 키만 보낸다

#### Scenario: 새 책 등록
- **WHEN** 자체 대출 기관 관리자가 새 ISBN, 도서명, 저자, 등록번호, 매입, 구입가로 등록하면
- **THEN** 칸이 닫히고 그 책이 대출 가능으로 보이며, 이용자 화면에서 그 도서명을 찾을 수 있다(브라우저 확인)

#### Scenario: 겹친 등록번호
- **WHEN** 이미 쓰는 등록번호로 사본을 등록하면
- **THEN** 서버 문구가 보이고 칸은 입력한 값과 함께 열려 있다(브라우저 확인)

### Requirement: 회원 화면
관리자 화면의 [회원]은 회원 목록을 SHALL 보이고 등록·수정·삭제를 한다. 들어오면 `GET /members` 첫 20명(회원번호 순)을 읽고, 찾기 칸(이름·회원번호)으로 거르며, [더 보기]로 더 읽는다. 열은 회원번호, 이름, 휴대폰 번호(없는 기존 회원은 `-`)다. 등록은 회원번호·이름·휴대폰 번호(셋 다 필수)다. [수정]은 이름과 휴대폰 번호만 바꾼다. 번호가 있는 회원의 번호 칸을 비우면 요청하지 않고 번호를 넣으라고 알린다. 번호 없는 기존 회원은 번호 칸을 비운 채 이름만 수정할 수 있다(번호를 보내지 않는다). [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패는 서버 문구를 글자로 보인다. 입력칸은 브라우저 자동 완성을 끈다.

#### Scenario: 보내는 값
- **WHEN** 회원 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 등록은 `MemberCreate`, 수정은 `MemberUpdate`에 있는 키만 보낸다

#### Scenario: 번호는 필수
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** 등록은 번호 칸이 비면 요청하지 않고, 수정은 번호를 `null`로 보내지 않는다

#### Scenario: 삭제는 확인 뒤
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** `DELETE /members/{id}` 앞에 확인이 있고 취소하면 요청하지 않는다

#### Scenario: 입력칸
- **WHEN** 관리자 화면 HTML의 회원 입력칸을 검사하면
- **THEN** 모두 `autocomplete="off"`다

#### Scenario: 등록한 회원으로 로그인
- **WHEN** 자체 대출 기관 관리자가 휴대폰 번호와 함께 회원을 등록한 뒤 이용자 화면에서 그 번호로 로그인하면
- **THEN** 로그인되고 빌리기를 할 수 있다(브라우저 확인)

#### Scenario: 겹친 번호
- **WHEN** 다른 회원이 쓰는 휴대폰 번호로 수정하면
- **THEN** "이미 쓰는 전화번호예요."가 보이고 목록의 값은 그대로다(브라우저 확인)

### Requirement: 휴관일 화면
관리자 화면의 [휴관일]은 오늘부터 1년의 임시 휴관일을 SHALL 보이고 등록과 삭제를 한다. 들어오면 `GET /library/closures`를 `from`(오늘)과 `to`(오늘부터 365일)로 읽는다. 줄은 날짜와 사유(없으면 비움)와 [삭제]다. [등록]은 날짜(필수)와 사유(100자까지)를 `POST /library/closures`로 보낸다. [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패(같은 날짜 409 등)는 서버 문구를 글자로 보인다.

#### Scenario: 읽는 기간
- **WHEN** 휴관일 화면 스크립트를 검사하면
- **THEN** 목록 요청에 `from`과 `to`를 보내고 `to`는 `from`부터 365일 뒤다

#### Scenario: 사유 길이
- **WHEN** 관리자 화면 HTML의 사유 칸을 검사하면
- **THEN** 최대 길이가 서버 스키마의 상한(100자)과 같다

#### Scenario: 휴관일 더하기
- **WHEN** 자체 대출 기관 관리자가 오늘 날짜를 사유 `소독`으로 등록하면
- **THEN** 목록에 그 날짜가 보이고, 같은 관리자의 `GET /library/guide`에서 오늘이 임시 휴관이고 사유가 `소독`이다(브라우저 확인. 시드 기관은 안내를 등록하지 않아 이용자 화면 위 띠에는 나오지 않는다)

#### Scenario: 같은 날짜
- **WHEN** 이미 있는 날짜를 다시 등록하면
- **THEN** 서버 문구가 보이고 목록은 그대로다(브라우저 확인)
