# Design

## Context

- 소장 도서 검색(`recommendation/search.py`)은 키워드마다 양쪽 공백을 지운 `ILIKE` 부분 문자열 비교에 가중치를 더한다. 오타, 조합 중인 자모, 저자 일부 표기에서는 못 찾는다. 이 함수는 AI 사서의 `search_collection` tool만 쓴다.
- 추천 가능 조건(`recommendable_ids`)과 사본 수 집계(`_counts`)가 이 파일에 있고, 소장 검사와 카드가 함께 쓴다.
- 비교 규칙은 `app/core/text.py`의 `compact`(코드)와 `compact_sql`(SQL)이 짝을 이룬다.
- 대화 API는 `prepare_turn`(확인, 404·409·429는 응답 전) → `stream_turn`(SSE) 순서다. 답 메시지 행에는 코드가 `[추천한 책: #12 공룡 백과]`를 덧붙여 다음 턴 문맥으로 쓴다.
- 키오스크 계정은 이미 "도서·사본 조회"를 할 수 있다(`library/staff-auth`). 새 검색 API도 여기에 든다.
- DB 이미지는 `postgres:16`이다. `pg_trgm`은 기본 contrib에 있고 PostgreSQL 13부터 신뢰 확장이라 DB 소유자가 켤 수 있다.
- 지금 main에서 `tests/evals/test_librarian_eval.py::test_scenarios_cover_eval_requirements`가 실패한다. archive된 change 경로를 읽기 때문이다.

## Goals / Non-Goals

**Goals:**
- 아는 책은 LLM 없이 거의 즉시 찾는다. 오타와 입력 중 글자를 허용한다.
- 대화 화면 하나에서 검색과 대화가 이어지게 API 계약을 정한다(고른 책, 찾은 책 카드).
- 검색 품질을 수치로 내고, 지금 방식과 비교한다.

**Non-Goals:**
- 비슷한 책 추천, 임베딩, 저자 구조화(`add-related-books`).
- 문장이 "검색인지 추천인지" 코드로 분류하기. 찾기는 늘 먼저 돌리고, 거의 정확할 때만 카드를 먼저 보낸다.
- 화면.
- 검색 인덱스. 작은도서관 규모에서는 순차 탐색으로 보고, 느리면 그때 둔다.

## Decisions

### 1. 패키지 배치

```
app/core/text.py                      # jamo(): 자모 분해 규칙, jamo_sql(): 같은 규칙의 SQL 식
app/library/recommendation/lookup.py  # find_books, suggest_books, get_findable, found_in_text
app/library/api/catalog.py            # GET /catalog/search, GET /catalog/suggest
app/library/schemas/catalog.py        # BookSummary, Suggestion
app/library/schemas/librarian.py      # BookCard(BookSummary) + reason, MessageRequest 확장
app/library/services/chat.py          # 고른 책, 찾은 책 카드
app/library/tools.py                  # find_book
app/library/models/chat.py            # ChatMessage.note (책 표시 칸)
app/agent/runner.py                   # history가 Instruction도 받음
evals/catalog_search/                 # 검색 평가
```

- 찾기는 `recommendation/` 안에 둔다. 추천 가능 조건과 사본 집계를 같이 쓰기 때문이다. 다음 change의 "비슷한 책"도 여기서 찾은 책을 기준으로 출발한다.
- `BookSummary`는 카드에서 이유를 뺀 값이다. 카드 만들기 함수가 요약을 먼저 만들고 이유를 붙이게 나눈다. 검색 결과와 카드의 서지·대출 상태가 같은 코드에서 나온다.

### 2. 자모 분해 규칙

`jamo(value)`: `compact`와 같이 공백·보이지 않는 글자를 지우고 소문자로 바꾼 뒤, 완성형 한글 음절을 초성·중성·종성의 호환 자모로 푼다. 겹받침과 이중 모음도 나눈다(`ㄳ`→`ㄱㅅ`, `ㅘ`→`ㅗㅏ`). 이미 낱자인 자모(조합 중 입력)도 같은 방식으로 나눈다. 영문·숫자는 그대로 둔다.

- 조합 중 입력 `데미ㅇ`은 `ㄷㅔㅁㅣㅇ`이 되어 `데미안`(`ㄷㅔㅁㅣㅇㅏㄴ`)의 앞부분과 맞는다.
- 한 글자 오타 `데미얀`(`ㄷㅔㅁㅣㅇㅑㄴ`)은 자모 하나 차이라서 음절 비교보다 유사도가 높게 남는다. 한글 서명은 2~4음절이 많아 음절 단위로 비교하면 한 글자만 틀려도 겹치는 조각이 거의 없다.
- 이중 모음을 나누는 이유: 두벌식에서 `ㅘ`는 `ㅗ`,`ㅏ`를 차례로 쳐서 만든다. 조합 중에 `ㅗ`까지만 들어온 상태도 앞부분으로 맞아야 한다.
- **낱말 시작 키** `jamo_starts(value)`: 공백을 하나로 남겨(`clean_spaces`) 소문자로 바꾸고 자모로 푼 뒤, 낱말마다 그 낱말부터 끝까지를 공백 없이 이은 목록이다. `최소한의 한국사` → `[ㅊㅗㅣㅅㅗㅎㅏㄴㅇㅡㅣㅎㅏㄴㄱㅜㄱㅅㅏ, ㅎㅏㄴㄱㅜㄱㅅㅏ]`. 첫 값이 `jamo(value)`와 같다. 앞부분·낱말 앞부분·오타 비교가 모두 이 목록으로 된다.
- SQL 쪽은 마이그레이션이 만드는 `ko_jamo(text)`, `ko_jamo_starts(text)` 함수(`IMMUTABLE`, `PARALLEL SAFE`)다. 코드와 SQL의 결과가 같은지 테스트가 여러 문자열로 확인한다(`compact`/`compact_sql`과 같은 방식).
- **키는 생성 열로 저장한다** (3.4에서 바꿈). `books`와 `library_books`에 `title_jamo_starts`, `author_jamo_starts`(`text[]`, `GENERATED ALWAYS AS (ko_jamo_starts(title)) STORED`)를 둔다. 표시 값의 키는 `coalesce(공식 서지 키, 기관 도서 키)`이고, 표시 값 `coalesce(Book.title, LibraryBook.title)`과 같은 규칙이다.
  - 처음에는 질의마다 함수로 계산했다. 5,000권에서 찾기 7.7초, 자동완성 3.0초로 기준(200ms)을 크게 넘었다. 행마다 plpgsql로 자모를 푸는 비용이 원인이었다.
  - 열로 저장하면 채움·연결이 바뀔 때 갱신해야 한다는 걱정이 있었지만, 생성 열은 PostgreSQL이 값이 바뀔 때 계산한다. 갱신 코드가 없다. 서명과 키가 어긋날 수 없다.
  - 공식 서지(`books`)의 키는 서명의 자모일 뿐 기관이나 어린이를 모르므로 층 규칙에 어긋나지 않는다.
  - 시험(5,000권, 되돌린 트랜잭션): 포함 4ms, 오타 17ms, 문장 속 서명 4ms. 넣을 때 키 계산을 포함해 316ms.
- **판본·묶음 표기는 찾기 키에서 지운다** (9장에서 추가). 괄호·대괄호 부분, 닫히지 않은 괄호부터 끝까지, 공백을 둔 `+` 뒤(`+ 엽서 3종`)다. 이용자는 이 표기를 말하지 않는다. 지운 서명이 비면 원래 서명을 쓰고, `C++`처럼 공백 없는 `+`는 둔다. 화면의 서명은 그대로다. 질의에도 같은 규칙을 적용해 표기까지 쳐도 맞는다. 규칙을 바꾸는 새 리비전은 함수를 바꾸고 저장된 키를 다시 계산한다(생성 열은 행이 바뀔 때만 다시 계산된다).
- **대안: Python에서 기관 도서 전체를 메모리에 올려 비교** → 기관마다 캐시와 무효화(가져오기, 채움, 수정)가 필요하다. 생성 열은 늘 최신이다.
- **대안: 질의마다 함수로 계산하되 한 번씩만** → 5,000권 × 2번의 자모 계산만 약 300ms다.

### 3. 찾기 (`find_books`)

질의 `q`의 자모 키와 서명·저자 표시 값의 자모 키를 비교한다.

| 단계 | 조건 | 순위 |
| --- | --- | --- |
| 서명 전체 일치 | 키가 같음 | 1 |
| 서명 앞부분 | 서명 키가 `q`로 시작 | 2 |
| 서명 포함 | 서명 키가 `q`를 포함 | 3 |
| 저자 포함 | 저자 키가 `q`를 포함 | 4 |
| 유사 | 유사도(질의와 서명·저자의 일부) ≥ 기준 | 5 |

- 같은 단계 안에서는 유사도, 대출 가능 여부, 표시 서명 순이다. 결과는 10권이다.
- 유사도는 "질의가 대상의 일부와 얼마나 닮았는가"여야 한다. 서명 일부나 저자 이름만 입력하는 경우가 많기 때문이다. 기준값은 평가로 정한다.
- **유사도 방식은 측정으로 정한다(태스크 1.2).** 자모는 40개 정도라 관계없는 한글 문자열도 `ㅇㅏ`, `ㄴㅡ` 같은 조각을 쉽게 공유한다. 오타에는 강하지만 엉뚱한 책이 비슷하다고 나올 수 있다. 후보 셋을 표본의 오타 질의와 관계없는 질의로 비교한다.

| 후보 | 장점 | 걱정 |
| --- | --- | --- |
| `pg_trgm` `word_similarity` + 자모 키 | 오타·부분 질의에 강하다 | 자모 조각 잡음 |
| `pg_trgm` `word_similarity` + 음절 키 | 잡음이 적다 | 짧은 서명의 한 글자 오타에 약하다 |
| 자모 편집 거리(`fuzzystrmatch`의 `levenshtein`, 길이로 나눔) | "한 글자 안팎"의 뜻에 가장 가깝다 | 부분 질의에는 서명 낱말별로 비교해야 한다 |

  기준은 오타 5위 안 적중률과, 관계없는 질의의 결과가 비는 비율이다. 둘 다 PostgreSQL 기본 contrib라 이미지는 그대로다.

  **1.2 결과 (2026-11-10, 표본 87권, 오타 질의 250개, 관계없는 질의 29개, 서명 앞부분 비교)**

  | 방식 | 문턱 | 오타 5위 안 (모음/받침/자판) | 관계없는 질의 빈 결과 |
  | --- | --- | --- | --- |
  | `pg_trgm` + 자모 | 0.4 | 78% (72/88/73) | 90% |
  | `pg_trgm` + 자모 | 0.5 | 64% | 97% |
  | `pg_trgm` + 음절 | 0.3 | 46% | 97% |
  | 자모 편집 거리 | 0.6 | 92% (92/90/93) | 93% |
  | 자모 편집 거리 | 0.7 | 88% (92/80/93) | 97% |

  `pg_trgm`은 `en_US.utf8`에서 호환 자모로 trigram을 만든다(라틴 매핑은 필요 없다). 그래도 **자모 편집 거리를 고른다.** 같은 잡음 수준(빈 결과 97%)에서 오타 적중이 88%로 trigram(64%)보다 훨씬 높다. 음절 trigram은 한 글자 오타에 약하다는 걱정이 그대로 나왔다.

  - 유사도 = `1 - min(levenshtein(q, left(s, n-1)), levenshtein(q, left(s, n)), levenshtein(q, left(s, n+1))) / n` (`n = length(q)`)을 서명·저자의 낱말 시작 키 `s`마다 계산해 가장 높은 값이다. 길이 ±1은 글자가 빠지거나 더해진 오타를 위해서다. SQL에서 `unnest`와 C 함수 `levenshtein`으로 계산한다(plpgsql 루프는 느렸다). 1.2는 서명 앞부분만 비교했으므로 낱말 위치 확장은 평가(6.2)에서 다시 잰다.
  - 시작 문턱 0.7. 질의가 5자모(2음절)면 한 자모 차이가 0.8이라 통과하고, 두 자모 차이(0.6)는 떨어진다. 최종값은 6.2에서 정한다.
  - 확장은 `fuzzystrmatch` 하나만 켠다. `pg_trgm`은 쓰지 않는다.
  - 87권 30질의 trigram 계산이 43ms였다. 편집 거리는 3.4의 5,000권 테스트로 본다.
- 저자는 원문 그대로 비교한다. `앤디 위어 저/박아람 역`에 `앤디위어`가 포함으로 맞는다. 역자 이름으로도 맞는 것은 이번에는 허용한다.
- `%`, `_`는 지금 검색처럼 이스케이프한다.

### 4. 자동완성 (`suggest_books`)

서명 키 앞부분 → 서명 낱말 앞부분(낱말 시작 키 중 하나가 `q`로 시작) → 저자(낱말) 앞부분 순으로 8개다. 오타 유사는 쓰지 않는다. 입력하는 동안 결과가 출렁이지 않게 하기 위해서다. 응답은 id, 서명, 저자만 담아 가볍게 한다. 같은 서명의 기관 도서가 여럿이면 모두 나온다(판본·권차가 다를 수 있다).

### 5. 대화와 잇기

**요청**: `MessageRequest`에 `selected_library_book_id: int | None`을 더하고 `message`를 `str | None`으로 바꾼다. 둘 다 없으면 422다(모델 검증). 기존 클라이언트(문장만 보냄)는 그대로 동작한다.

**고른 책만** (`message` 없음)

1. `prepare_turn`: 세션·턴 상한·동시 요청 확인, `get_findable`로 고른 책 확인(아니면 404). 일일 실행 상한은 보지 않는다. 이용자 행을 `content=""`, `note="[고른 책: #12 데미안]"`으로 저장한다.
2. `stream_turn`: `session`, `found`, `done`(`run_id: null`, `status: "selected"`)을 보낸다. 실행기를 부르지 않으므로 `agent_runs` 행도 없다. `done`의 `run_id`가 null일 수 있다는 점은 스펙에 적는다.

**문장이 있는 턴**

1. `prepare_turn`: 지금 확인에 더해 고른 책을 확인한다. 문장을 가린 뒤 고른 책이 없으면 `found_in_text(가린 문장)`으로 찾은 책을 정한다.
2. 이용자 행: `content=가린 문장`, `note="[고른 책: …]"` 또는 `"[찾은 책: #12 데미안, #30 데미안 읽기]"`.
3. `stream_turn`: `session`, `found`(있으면), `status`…, `answer`, `done`.

**책 표시는 이용자 문장과 떼어 둔다**

- 처음에는 표시를 이용자 문장 끝에 덧붙이려 했다. 그런데 실행기는 `UserMessage`의 글을 모두 `user_texts`로 넘기고, 어린이 요청 판단이 이를 읽는다. 서명 `법 만드는 아이들`, `세금 내는 아이들`(표본에 있다)의 "아이"가 어른 요청을 어린이로 좁힌다.
- 그래서 `chat_messages.note`(nullable)에 따로 저장하고, LLM에게는 이용자 문장 바로 앞의 developer 메시지(`Instruction`)로 보낸다. 이전 턴도 같다: 대화 기록을 만들 때 `note`가 있으면 `Instruction(note)`, `content`가 비어 있지 않으면 `UserMessage(content)`를 차례로 넣는다.
- 실행기는 `user_texts`를 `UserMessage`에서만 모으므로 고치지 않아도 된다. `run()`의 `history` 타입만 `Instruction`을 받게 넓힌다. 이번 턴의 표시는 `history` 끝에 붙인다.
- 개인정보 가리기는 이용자 문장만 본다. 표시는 코드가 DB 값으로 쓴 글이다.
- 턴 상한은 지금처럼 이용자 행 수로 센다. 고른 책만 보낸 턴도 이용자 행이 하나 있어서 그대로 맞다.
- **대안: 역할 값에 `note`를 더함** → 턴 수 세기와 대화 기록 만들기가 행 두 개를 묶어야 해서 복잡해진다. 열 하나가 단순하다.
- **대안: 어린이 판단에서 표시 줄을 정규식으로 지움** → 어린이 기능이 대화 표시 형식을 알게 되고, 형식이 바뀌면 조용히 깨진다.

**찾은 책을 답에서 다시 추천하면**

`_finish`가 그 턴의 고른 책·찾은 책 id를 답 카드와 노출 기록에서 뺀다. 같은 책 카드가 두 번 보이지 않게 하기 위해서다. 프롬프트에도 "찾은 책은 화면에 이미 있으니 다시 추천하지 않는다"고 적는다. 빼고 남은 추천이 없어도 답 문장은 그대로 나간다("네, 2층 문학 서가에 있어요" 같은 답이 맞기 때문이다). 고정 문구로 바꾸는 소장 검사의 정리 규칙과는 다르다. 위반이 아니라 중복 제거이기 때문이다.

**찾은 책 판정** (`found_in_text`): 서명(`compact`)이 2글자 이상이고, 서명 키가 문장 키에 포함되거나, 자모 편집 거리 유사도(서명 키를 질의로, 문장의 낱말 시작 키를 대상으로. 문장의 키는 코드가 계산해 넘긴다)가 높은 기준(찾기보다 엄격하게, 시작 0.85) 이상인 책. 많으면 서명이 긴 책부터 3권이다. 짧은 서명(`모순`, `가호`)이 일반 문장에 우연히 들어가는 경우가 있다. 카드가 하나 더 뜨는 정도라 피해가 작고, 오탐 비율은 평가에서 잰다.

**프롬프트**: `[고른 책]`, `[찾은 책]` 안내는 이용자가 찾은 책이라는 뜻이고 화면에 이미 카드가 있다고 적는다. 서명·저자를 말하면 `find_book`, 주제·분위기는 `search_collection`을 쓰라고 적는다.

- 찾은 책 카드는 추천이 아니다. `recommendation_events`에 남기지 않고 어린이 검사를 거치지 않는다. 이용자가 제목으로 직접 찾은 책을 가리면 오히려 이상하다. 답의 추천에는 어린이 검사가 그대로 적용된다.
- `found` 카드는 LLM 답보다 먼저 나가지만 코드가 DB 값으로 만든 것이라, "검사 전의 LLM 답을 먼저 흘리지 않는다"는 원칙과 충돌하지 않는다.
- **대안: 문장을 검색 의도로 분류해 LLM을 건너뛰기** → 분류 규칙이 틀리면 "데미안 같은 책 추천해줘"에 추천 없이 카드만 나간다. 카드는 먼저 보내고 LLM은 늘 이어 가는 편이 안전하다. LLM을 건너뛰는 것은 이용자가 자동완성에서 책을 고른, 의도가 분명한 경우만이다.

### 6. `find_book` tool

입력은 `query: str`(100자)이고, 결과는 `search_collection`과 같은 형식이다. 어린이 기능의 프로필에도 그대로 들어간다(거르지 않음). `record_fields`는 두지 않는다(이용자 문장에서 나온 값일 수 있다).

### 7. 마이그레이션

`fuzzystrmatch` 확장(1.2에서 고름), `ko_jamo`·`ko_jamo_starts` 함수, `books`·`library_books`의 찾기 키 생성 열 4개, `chat_messages.note`(text, nullable) 열을 만든다. 되돌릴 때는 열, 함수, 확장 순으로 지운다. 기존 행의 키는 열을 더할 때 PostgreSQL이 계산한다. 새 테이블은 없다. 개발 DB를 백업한 뒤 `upgrade` → `downgrade -1` → `upgrade`, `alembic check`를 `&&`로 잇는다.

- **(1.2에서 확인함, `pg_trgm`은 쓰지 않음) 위험: `pg_trgm`이 한글 자모를 글자로 보지 않을 수 있다.** `pg_trgm`은 DB 로캘의 글자 판정으로 낱말을 나누고, 글자가 아닌 문자는 버린다. `postgres:16`의 기본 로캘(`en_US.utf8`)에서는 호환 자모가 글자로 판정될 것으로 보지만, 1번 태스크에서 실제 DB로 먼저 확인한다. 안 되면 자모를 라틴 글자로 바꾸는 매핑(`ㄱ`→`g` 등, 1:1)으로 키를 만든다. 비교 결과는 같고 규칙만 달라진다.

### 8. 검색 평가 (`evals/catalog_search/`)

YES24 표본 87권을 지금처럼 테스트 DB 트랜잭션 안에서 적재한다(`evals/librarian/catalog.py`의 적재와 되돌림 세션을 함께 쓴다). 추천 가능한 책마다 질의를 코드로 만든다. 같은 책에서 늘 같은 질의가 나오게 ISBN을 씨앗으로 쓴다.

| 질의 종류 | 만드는 방법 | 볼 지표 |
| --- | --- | --- |
| 정확 | 표시 서명 | 1위 |
| 공백 | 서명에서 공백 제거 또는 추가 | 1위, 5위 안 |
| 일부 | 서명 앞 절반, 가운데 낱말 | 5위 안, MRR |
| 저자 | 저자 원문의 첫 이름(` 저`, `/` 앞) | 5위 안 |
| 모음 오타 | 음절 하나의 중성을 이웃 모음으로(`ㅏ↔ㅑ`, `ㅓ↔ㅕ`, `ㅐ↔ㅔ`, `ㅗ↔ㅛ`) | 5위 안, MRR |
| 받침 오타 | 받침 하나 빼기 또는 더하기 | 5위 안 |
| 자판 오타 | 두벌식 이웃 자판의 자모로 하나 바꾸기 | 5위 안 |
| 자동완성 | 서명 자모 앞부분 2, 4, 6자 | 8개 안 |
| 찾은 책 | `{서명} 있어요?` 같은 문장 틀 3개 | 찾음 비율 |
| 찾은 책 오탐 | 주제·기분 문장 30개(어느 서명도 담지 않음) | 카드가 뜬 비율 |

- 기준선은 지금 `search_collection(session, library_id, [q])`다. 같은 질의로 두 방식의 표를 나란히 낸다.
- 목표(튜닝 기준, 스펙 아님): 정확 1위 100%, 공백·일부·저자 5위 안 95% 이상, 오타 5위 안 80% 이상, 찾은 책 오탐 5% 이하. 기준값(유사도 문턱)은 이 표로 정하고 README에 적는다.
- 결과는 `evals/catalog_search/data/runs/`(저장소 밖)에 쓴다. 질의에 표본 서명이 들어 있어서다.
- **6.2 결과 (2026-11-11, 찾을 수 있는 책 79권, 질의 1,098개)**: 정확 1위 100%, 공백·일부·저자 5위 안 100%, 오타 5위 안 97~99%(기준선 0%), 자동완성 8개 안 100%, 찾은 책 88.6%, 찾은 책 오탐 0%. 목표를 모두 채웠다. 문턱은 오타 0.7, 찾은 책 0.85로 둔다. 표와 근거는 `evals/catalog_search/README.md`에 있다.
- 찾은 책이 놓친 27건은 모두 판본·묶음 표기(`[예스리커버]`, `(완전판)`, `(2026년)`)가 붙은 서명이었다. 사람 요청으로 표기 무시를 더한 뒤(9장) 찾은 책은 100%가 됐다. 대가로 `+ 그림책 특별판`처럼 묶음 표기로 지워진 낱말로는 그 책을 찾지 못한다(표본 2권). 표기를 지우면 같아지는 판본은 원래 서명이 질의와 같은 책을 먼저 둔다.
- 속도: 테스트에서 가짜 기관 도서 5,000권으로 찾기·자동완성·문장 속 서명이 각각 200ms 안에 끝나는지 본다(2절의 생성 열로 맞춤).
- LLM과 YES24를 부르지 않는다. 비용이 없다.

### 9. 추적 테스트 수정

추적 테스트는 `openspec/specs/`와 archive되지 않은 `openspec/changes/*/specs/`를 함께 읽는다. 진행 중인 change의 평가 시나리오도 archive 전에 확인하기 위해서다.

### 10. 다음 change로 넘기는 것

**`add-library-guide` (9번)**

- 기관 안내 정보: 운영 시간, 휴관일, 대표 연락처, 시설 위치(화장실, 열람실 등), 이용 규칙(권수, 기간). 관리자가 등록하고 키오스크는 읽는다.
- AI 사서 tool: 안내 정보 조회, "오늘 빌리면 언제까지" 반납 예정일 계산. 날짜는 코드가 기관 시간대의 오늘 + 대출 기간으로 계산하고, 휴관일 처리는 기관 설정을 따른다.
- 등록된 정보로만 답한다. 없으면 지어내지 않고 대표 연락처를 안내한다.
- 연락처는 기관 대표 번호만 둔다. 자원봉사자 개인 번호를 넣지 않게 관리 화면과 문서에 적는다.
- 책 위치는 카드의 서가 위치·청구기호를 LLM이 풀어 말한다. 서가 배치도는 나중에 둔다.
- "내 책 언제까지"는 회원번호가 필요해 `add-librarian-actions`에서 다룬다. 가져오기 기관은 대출 기록이 없다.

**`add-related-books` (10번)**

- 고른 책·찾은 책 아래에 붙는 비슷한 책: 같은 저자 → 같은 분류 → 소개 임베딩. 점수는 하이브리드로 합친다(예: 서명 4, 저자 2, 소개 임베딩 1, 소개가 없으면 임베딩 0). 키워드 점수와 유사도의 크기가 달라 정규화나 순위 합치기가 필요하다.
- 마음에 드는 후보가 없을 때 임베딩 쪽으로 무게를 옮기는 방법(tool 인자 `match: exact | similar` 등).
- 담은 책 신호. 이번의 "고른 책"과 같은 통로로 대화에 넘긴다.
- 저자 구조화(`저`, `역`, `글`, `그림` 나누기). "같은 저자"에 역자가 섞이지 않게 한다.
- 자동으로 붙는 비슷한 책은 LLM을 부르지 않는다. 이유는 코드가 근거 표시로 붙인다(`같은 저자`, `같은 분류`, `소개가 비슷해요`). 문장형 이유는 대화로 받은 추천에만 둔다.
- 자동 추천은 카드 아래 한 줄처럼 조용히 보여 주고, 이용자가 말을 걸 때만 LLM이 이어 간다. 아는 책만 찾으러 온 이용자를 방해하지 않기 위해서다.
- 기준 책이 어린이 도서이면 비슷한 책도 어린이 도서로 거른다. 지금 어린이 요청 판단은 문장 기준이라, 기준 책에서 출발하는 경우의 규칙을 새로 정해야 한다.
- pgvector 이미지, `book_embeddings`(기관 도서 기준, 소장 도서만, 벡터·모델·입력 해시만 저장), YES24 소개글을 임베딩 제공자에 보내는 것의 이용 조건 확인.

## Risks / Trade-offs

- [자모 비교의 잡음으로 엉뚱한 책이 나온다] → 유사도 방식을 세 후보 중 측정으로 고르고, 관계없는 질의의 빈 결과 비율을 함께 본다.
- [책 표시가 어린이 판단이나 개인정보 가리기에 섞인다] → 표시를 `note` 열과 developer 메시지로 떼어 두고, `법 만드는 아이들` 시나리오로 테스트한다.
- [자동완성은 한 글자마다 요청이 간다] → 화면에서 입력이 멈춘 뒤 보내기(debounce, 예: 150ms)를 `add-web-ui` 메모로 남긴다. API는 가볍게(id, 서명, 저자) 둔다.
- [함수 계산 때문에 느려질 수 있다] → 5,000권 속도 테스트로 보고, 넘으면 인덱스를 둔다.
- [짧은 서명의 찾은 책 오탐] → 2음절 이상, 높은 문턱, 3권 상한. 평가의 오탐 비율로 문턱을 정한다.
- [역자 이름으로도 맞는다] → 저자 구조화 전까지의 한계로 둔다. 찾기 결과에 원문이 그대로 보여 이용자가 구분할 수 있다.
- [표본 87권은 작은도서관 장서와 다르다] → 검색 평가는 서명·저자 표기 다양성을 보는 것이라 영향이 작다. 수치를 실제 서비스 성능으로 쓰지 않는다.
- [대화 API 변경] → 필드를 더하고 `message`를 선택으로 바꿀 뿐이라 기존 요청은 그대로 동작한다. 사건 `found`는 모르는 클라이언트가 무시하면 된다.
- [change가 1주를 넘을 수 있다] → 순서는 찾기·API(1~3) → 대화 잇기(4~5) → 평가(6)다. 대화 잇기가 늦어지면 범위를 줄이지 않고 알린다.

## Migration Plan

1. 개발 DB를 백업한다.
2. `uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head && uv run alembic check`
3. 되돌릴 때는 `downgrade -1`. 함수와 확장만 지워지고 데이터는 그대로다.
