## Goals / Non-Goals

**Goals:**

- 질문 14개(아래 결정 1)를 tool 네 개로 답하고, 숫자는 모두 pytest로 정답과 대조한다.
- LLM이 정하는 값은 enum과 상한 있는 정수뿐이다. 날짜, 기관, 분야 코드를 LLM이 쓰지 않는다.
- 어린이 기능을 빼도 운영 에이전트가 돈다.
- 못 하는 질문의 종류가 쌓여 자연어 SQL을 열지 판단할 근거가 된다.

**Non-Goals:**

- 분석 REST API. service는 REST로 열 수 있는 모양(입력·출력 Pydantic 스키마)으로 두되 라우터는 `add-web-ui`에서 연다.
- 답 화면용 표·차트 사건. 이번 `answer`는 문장과 종류뿐이다. 화면이 표를 원하면 `add-web-ui`에서 tool 결과를 코드가 사건으로 내는 방식을 정한다.
- 외부 대출 기관용 안내 문구 다듬기. 프로필에서 대출 tool을 빼는 것까지만 한다.
- 분석 쿼리 성능 최적화(인덱스). 작은도서관 장서(수천 권)에서 재고 필요할 때만.

### 2. 정해진 분석 tool, 겉 넷 속 하나

후보는 셋이었다.

| 후보 | 장점 | 버린 이유 |
| --- | --- | --- |
| 자연어 SQL | 질문 범위가 가장 넓음 | 안전장치(읽기 전용 role, view, sqlglot, 시간 제한, `set_config` 구멍)가 change 하나 분량이고, 숫자 정답을 질문마다 대조하기 어려움 |
| 기본 연산 tool을 LLM이 조합(조회·필터·묶기) | 조합이 유연함 | 중간 결과가 LLM을 거치면 LLM이 숫자를 다루고(원칙 7), 서버에 두면 사실상 질의 언어라 SQL의 문제가 돌아옴 |
| `aggregate(metric, …)` 하나 | tool 수가 적음 | 맞지 않는 조합(장서 + 기간)을 막는 코드가 늘고 tool 설명이 흐려져 고르기가 어려움 |

그래서 tool은 넷이고 속은 **필터·묶기 빌더 하나**(`app/library/analytics/`)다. 분야 결정, 축 배정, 제적 제외 같은 업무 규칙은 빌더에만 있다. tool은 입력 스키마와 결과 모양만 다르다. 비교 질문(#11)은 LLM이 같은 tool을 두 번 부른다.

### 3. 분야는 코드가 정한다

- 순서: `books.kdc` → `library_books.kdc` → 사본 `call_number`(앞 세 자리 숫자) → `분류 없음`. 표시 값의 `coalesce(공식, 기관)`과 같은 방향에 청구기호 한 단계를 더한다. 청구기호는 사본마다 다를 수 있어 그 기관 도서의 사본 중 제적이 아닌 것의 가장 작은 id 사본을 쓴다(값이 다른 경우는 실측 0건).
- 주류 이름은 `app/core/kdc.py`의 `KDC_MAIN_CLASSES`를 쓴다. enum 값은 한국어 이름 그대로다(LLM이 "자연과학"을 바로 고름).
- 키워드·벡터 검색으로 세지 않는다. 같은 질문에 같은 숫자가 나와야 하고, 경계(소개에 "과학"이 있는 소설)가 흔들린다. 주제 개수는 `topic_count`로 안내한다.
- "과학" → 자연과학, 공학·의학·요리·육아 → 기술과학 같은 말 대응은 프롬프트의 짧은 표로 두고, 답에 쓴 분야를 밝힌다. 분야 필터가 여러 개라 "과학 전부"는 둘을 함께 고를 수 있다.

### 4. 분석 축 훅

```
 app/features/children/                 app/library/analytics/
 AdminExtension(                        AnalysisAxis(name, values, default, label,
   axes=(AUDIENCE_AXIS,),   ------->      assign: (library_id) -> Select[(library_book_id, value)])
   prompt_note=...)                     빌더: 필터 = id IN (배정에서 그 값)
                                              (기본값이면 NOT IN 다른 값)
                                        묶기 = LEFT JOIN 배정, COALESCE(값, 기본값)
```

- 공통 코드는 축 이름을 부르지 않는다. AI 사서의 `LibrarianExtension`과 같은 조립 방식이다(`AdminExtension`).
- 축은 기능이 등록한 만큼이고 이번엔 하나다. 축끼리 교차 묶기는 만들지 않는다(묶기는 하나, 필터로 교차).
- tool 입력 모델은 조립 때 만든다. 등록된 축 이름이 `group_by`의 값과 필터 필드가 된다(Pydantic `create_model`, 값은 `Literal`). 축이 없으면 필드 자체가 없다.
- strict 스키마는 모든 필드를 필수로 요구하므로 필터·월 같은 선택 값은 `X | None`으로 둔다(기존 tool과 같음).
- 어린이 배정은 기존 `children_book_ids(library_id)`를 쓴다. `general` 행이 저장된 책도 있지만 기본값과 같아 배정에서 빼도 결과가 같다.

### 5. 기간

- 입력은 `period`(프리셋 7개) 또는 `month`(1~12) 중 정확히 하나(모델 검증). 오늘은 `app/core/clock.today()`(기관 시간대)다.
- 결과에 `period: {start, end, label, in_progress}`를 넣는다. `label`은 코드가 만든 한국어 표기(`2026년 11월 1일~19일`)이고 평가의 숫자 충실도가 이 표기의 숫자를 허용한다.
- 대출은 `loaned_on`이 기간 안이면 센다. "기간 중 대출 중이었던" 정의는 쓰지 않는다(설명하기 어렵고 담당자 질문과 덜 맞음).
- 임의 날짜, "작년 9월"은 받지 않는다. 필요해지면 `year_offset` 하나를 더하는 작은 변경이다.

### 6. 한도, 정렬, 잘림

- 순위 `top_n` 10/상한 20, 목록 `limit` 20/상한 50. 넘으면 입력 오류다(실행기가 이미 LLM에 돌려줘 다시 부르게 한다). 몰래 깎지 않는 이유는 결과가 LLM의 요청과 달라지는 것을 숨기지 않기 위해서다.
- 목록·순위 결과는 `total`, `shown`, `truncated`를 담는다. 그룹 결과(최대 11개)는 자르지 않는다.
- 정렬: 순위는 건수 내림차순 → `korean_order`(표시 서명) → 기관 도서 id. 목록은 표시 서명 → id.

### 7. 제적 사본

| 값 | 제적 | 이유 |
| --- | --- | --- |
| 장서 사본·서명 수와 그룹 | 뺌, `withdrawn` 따로 | 용어집의 소장 권수와 같음 |
| 대출 건수 | 넣음 | 대출 기록은 남고 실제로 일어남 |
| 권당 대출 분모 | 뺌(분모 0이면 null) | "지금 부족한가"를 본다 |
| 책 순위 | 넣고 `in_collection=false` | 많이 빌렸는데 제적된 책은 다시 살 후보 |
| 안 빌린 책 | 제적만 남은 서명은 뺌 | 없는 책을 보일 이유 없음 |

"기간 전 등록"은 `library_books.created_at`이다. 오래된 서명에 새 사본을 더해도 새 책이 아니다.

### 8. 개인정보

- 분석 쿼리는 `members`를 읽지 않는다. 연체 건수는 `loans`만으로 센다. `holdings.donor`는 SELECT 목록에 넣지 않는다.
- 결과 필드 **허용 목록** 테스트: tool마다 결과 스키마의 필드 경로 집합을 테스트에 적고 정확히 같은지 본다. 금지 목록은 새 이름(`donor_name`)을 놓친다.
- **심은 값** 테스트: 회원 이름·번호·기증자에 표시 값을 넣고 모든 묶기·필터 조합의 직렬화 결과에서 찾는다.
- tool 입력은 모두 `record_fields`로 남긴다. 입력이 enum과 정수뿐이라 문장이 섞이지 않는다. 평가의 tool 선택 판정도 이 기록을 쓴다.
- 연체한 회원은 기존 관리자 화면(`GET /loans?status=overdue`)으로 안내하고, 이 change는 LLM에 회원을 보내지 않는다. 안내문 초안은 `add-approval-flow`에서 LLM은 틀만, 코드가 회원별 값을 채우는 방식으로 한다.

### 9. 최종 답 기록

- `AnswerTool`에 `record_fields`를 더한다(tool과 같은 이름·뜻). 운영 에이전트 답은 `("unsupported",)`, AI 사서는 비운다.
- `agent_runs.answer_record`(JSONB, null 가능)에 상태가 `completed`·`repaired`일 때만 쓴다. 단계(`agent_steps.detail`) 대신 실행 행에 두는 이유는 "종류별로 몇 번"을 실행 단위로 바로 세기 위해서다.
- 질문 문장을 따로 저장하지 않는다. 이름은 코드로 가릴 수 없다. 원문이 필요하면 이미 가려 저장된 대화(만료 전)를 본다.

### 10. 대화 경로와 세션 종류

- `chat_sessions.kind`(`SessionKind`: `librarian`, `admin`, 기본 `librarian`)를 더한다. 세션 조회는 늘 기관 + 종류로 건다. 다른 종류는 404다.
- `services/chat.py`에서 세션·가리기·상한·저장 부분을 종류를 받는 공통 함수로 두고, 찾은 책·카드·노출 기록은 AI 사서 쪽에만 둔다. 운영 에이전트의 턴은 `services/admin_chat.py`(가칭)가 이 공통 함수와 운영 에이전트 프로필로 돌린다. 사건은 `session`, `status`, `answer`(`message`, `unsupported`), `done`.
- 설정: `admin_session_idle_minutes`(30), `admin_daily_run_limit`(200). 턴 상한은 같은 값을 쓴다. 관리자는 자리에 앉아 몇 번 이어 묻는다고 보고 만료를 길게 둔다. 관리자 경로는 공용 PC의 앞사람 문제가 덜하다.
- 경로: `app/library/api/admin_agent.py`, 의존성 `require_admin`(키오스크 403).

### 11. 운영 에이전트 프로필

- `app/library/admin_agent.py`: `build_admin_profiles(extensions) -> dict[LoanMode, Profile]`, 이름 `admin`, 버전 `v1`. `app.state.admin_profiles`에 둔다.
- 프롬프트(고정): 할 수 있는 분석 목록, 분야 대응표, 기간 고르기("오늘"을 몰라도 프리셋·월로 고름), 숫자는 결과 값만, 기간·분야·잘림을 밝힘, 못 하는 분석의 종류 고르기와 안내 문구, 연체한 회원은 연체 목록 안내. 외부 대출 기관 문구는 "대출 기록이 없다, 대출 중 상태는 마지막 가져오기 기준".
- 최종 검사는 두지 않는다. 숫자 충실도를 코드로 막으려면 답 문장의 숫자를 tool 결과와 맞춰야 하는데, 날짜·순위 번호 등 허용할 숫자가 많아 잘못 막을 위험이 크다. 평가로 먼저 재고, 지어낸 숫자가 자주 나오면 검사로 올린다.

### 12. 평가

- `evals/admin_agent/`: `evals/librarian`의 모양(시나리오 데이터클래스, 테스트 DB 트랜잭션, 결과 폴더, `summary.md`)을 따른다.
- 평가 기관은 코드(`fixture.py`)로 만든다. 약 40개 서명, 분야 6~7개 + 분류 없음 4권, 어린이 배정, 기증, 분실·훼손·제적, 2026-09~11 대출, 연체 2건. 실험 장서는 대출이 없고 분포를 정할 수 없어 쓰지 않는다.
- 시나리오 23개: 질문 14, 바꿔 말하기 4(과학, 9월, 아동, 작년), 못 하는 분석 4(`topic_count`, `patron_info`, `time_of_day`, `no_data`의 최근 들어온 책), 외부 대출 기관 1. 라벨은 Claude가 쓰고 사람이 전부 본다(약 10분).
- 숫자 추출: 답 문장의 정수·소수를 뽑아, 그 턴의 tool 결과(JSON의 모든 숫자), 질문의 숫자, `period.label`의 숫자에 있는지 본다. 쉼표·"권"·"건" 붙은 표기를 정규화한다.
- 통과 문턱은 첫 측정 뒤 정한다. 비교할 이전 값이 없다.

### 13. 분량과 나누는 자리

| 묶음 | 일 |
| --- | --- |
| 빌더·분야·기간·축 + 네 service 테스트 | 1.5 |
| tool·프로필·프롬프트 | 0.5 |
| 실행기 답 기록 + 마이그레이션 | 0.5 |
| 세션 종류·대화 경로·공통 함수 정리 | 1 |
| 평가 기관·시나리오·채점·실행 | 1.5 |
| 문서 | 0.5 |

약 5.5일이다. 1주 안이지만 빠듯하다. 넘칠 것 같으면 **평가(tasks 7·8)를 다음 change로 나눈다**. 나누면 이 change의 완료 기준은 "가짜 LLM으로 시나리오 틀이 돈다"로 바꾸고 알린다.

## Risks / Trade-offs

- [분류 없는 책이 많은 기관은 분야 숫자가 작게 나옴] → `분류 없음`을 늘 결과에 넣고, 프롬프트가 그 크기를 함께 말하게 한다.
- ["과학"을 자연과학으로만 해석] → 답에 기준을 밝히고 분야 필터를 여러 개 받는다. 평가 바꿔 말하기 시나리오로 잰다.
- [조립 때 만드는 입력 모델이 strict 스키마와 안 맞음] → 기존 strict 변환을 통과하는지 첫 태스크에서 축 있음·없음 두 스키마로 확인한다.
- [숫자 추출이 허용 숫자를 놓쳐 거짓 실패] → 시나리오별 결과 파일에 걸린 숫자를 남겨 사람이 보고, 규칙을 고치면 같은 실행 결과로 다시 채점한다(LLM 다시 부르지 않음).
- [chat service 정리가 AI 사서 동작을 바꿈] → 기존 대화·세션 테스트를 그대로 통과해야 하고, SSE 사건 순서와 저장 내용은 바꾸지 않는다.
- [운영 에이전트 세션 30분 동안 관리자 PC가 열려 있음] → 직접 끝내기 경로가 있고, 관리자 토큰 자체의 만료가 따로 있다.

## Migration Plan

- 마이그레이션 하나: `chat_sessions.kind`(enum `session_kind`, `server_default 'librarian'`, 기존 행은 AI 사서), `agent_runs.answer_record`(JSONB, null). 되돌리기는 두 칸과 enum을 지운다.
- 적용 전에 개발 DB를 백업하고, 백업·업그레이드는 `&&`로 잇는다.
- 기존 API는 바뀌지 않는다. 새 경로만 더한다.

- KDC 강목(100개)이 필요한지는 못 한 질문 기록(`other`)을 보고 정한다.
