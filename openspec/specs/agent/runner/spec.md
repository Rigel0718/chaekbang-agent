# agent/runner Specification

## Purpose

모든 에이전트가 쓰는 공통 실행기의 동작을 정한다. tool 호출 루프, 기관 범위, 최종 답 검사, 한도와 오류, 실행 기록을 에이전트마다 다시 만들지 않고 코드로 지키게 한다.

## Requirements

### Requirement: tool 정의
tool은 이름, 설명, 입력 스키마, 실행 함수로 SHALL 정의한다. 입력 스키마는 JSON Schema로 내보낼 수 있어야 하고 정의되지 않은 입력 값을 받지 않는다. tool은 실행기와 같은 프로세스에서 실행한다.

#### Scenario: LLM에 넘기는 tool 정의
- **WHEN** 프로필로 실행을 시작하면
- **THEN** LLM은 그 프로필의 tool마다 이름, 설명, JSON Schema를 받는다

### Requirement: 프로필의 tool만 실행
실행기는 실행 중인 프로필에 있는 tool만 MUST 실행한다. 없는 tool을 호출하면 실행하지 않고 오류 결과를 LLM에 돌려준다.

#### Scenario: 프로필에 없는 tool 호출
- **WHEN** LLM이 프로필에 없는 이름의 tool을 호출하면
- **THEN** 어떤 tool도 실행되지 않고 LLM은 오류 결과를 받는다

### Requirement: 입력 검증
실행기는 tool을 실행하기 전에 입력을 스키마로 MUST 검증한다. 맞지 않으면 실행하지 않고 오류 결과를 LLM에 돌려준다.

#### Scenario: 형식이 틀린 입력
- **WHEN** LLM이 필수 값이 빠진 입력으로 tool을 호출하면
- **THEN** 실행 함수는 불리지 않고 LLM은 오류 결과를 받는다

### Requirement: 기관 범위 주입
tool과 최종 검사는 실행을 시작한 코드가 정한 기관 범위 안에서 MUST 동작한다. LLM은 기관을 정할 수 없다.

#### Scenario: 실행 기관 전달
- **WHEN** A 기관으로 실행을 시작해 tool이 호출되면
- **THEN** 실행 함수는 A 기관의 범위를 받는다

#### Scenario: LLM이 기관을 넣은 입력
- **WHEN** LLM이 입력에 B 기관의 `library_id`를 넣어 tool을 호출하면
- **THEN** 정의되지 않은 입력으로 거부되고 실행 함수는 불리지 않는다

### Requirement: 호출 루프
실행기는 LLM이 요청한 tool을 실행하고 결과를 돌려주는 일을 최종 답 tool이 호출될 때까지 SHALL 반복한다. 한 번에 여러 tool을 요청하면 요청 순서대로 실행하고 결과를 함께 돌려준다.

#### Scenario: tool을 거쳐 최종 답
- **WHEN** LLM이 조회 tool을 호출한 뒤 결과를 받고 최종 답 tool을 호출하면
- **THEN** 조회 tool이 한 번 실행되고 실행은 그 최종 답으로 끝난다

#### Scenario: 여러 tool 동시 요청
- **WHEN** LLM이 한 응답에서 tool 두 개를 요청하면
- **THEN** 요청 순서대로 실행되고 다음 LLM 호출에 두 결과가 함께 전달된다

#### Scenario: 이전 대화 전달
- **WHEN** 이전 대화 내용을 넘겨 실행을 시작하면
- **THEN** LLM은 이전 대화 뒤에 이번 이용자 문장을 받는다

### Requirement: 최종 답 tool
최종 답은 프로필이 정한 최종 답 tool로만 SHALL 나간다. 다른 tool과 함께 호출되면 다른 tool만 실행하고 최종 답 tool에는 단독으로 다시 호출하라는 오류 결과를 준다. LLM이 tool 없이 글만 내고 끝내면 한 번 다시 요청하고, 그래도 없으면 프로필의 고정 답으로 끝낸다.

#### Scenario: 다른 tool과 함께 호출
- **WHEN** LLM이 한 응답에서 조회 tool과 최종 답 tool을 함께 호출하면
- **THEN** 조회 tool만 실행되고 최종 답은 나가지 않으며 LLM은 오류 결과를 받는다

#### Scenario: 글만 내고 끝남
- **WHEN** LLM이 최종 답 tool 없이 글만 내고 끝내면
- **THEN** 그 글은 나가지 않고 LLM에 최종 답 tool을 쓰라고 한 번 다시 요청한다

#### Scenario: 다시 요청해도 글만 냄
- **WHEN** 다시 요청한 뒤에도 LLM이 글만 내고 끝내면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `fallback`이다

### Requirement: 최종 검사
실행기는 최종 답을 내보내기 전에 프로필의 최종 검사를 모두 MUST 실행한다. 위반이 하나라도 있으면 그 답은 나가지 않고 위반 내용을 LLM에 돌려줘 다시 받는다. 최종 검사가 없는 프로필은 최종 답을 그대로 내보낸다.

#### Scenario: 검사 통과
- **WHEN** 최종 답이 모든 검사를 통과하면
- **THEN** 그 답이 나가고 실행 상태는 `completed`다

#### Scenario: 위반 후 고친 답
- **WHEN** 최종 답이 검사를 위반하고 LLM이 고친 답을 다시 내어 통과하면
- **THEN** 위반한 답은 나가지 않고 고친 답만 나간다

#### Scenario: 검사 없는 프로필
- **WHEN** 최종 검사가 없는 프로필의 실행에서 최종 답이 나오면
- **THEN** 그 답이 그대로 나간다

#### Scenario: 검사의 실행 정보
- **WHEN** 최종 검사가 실행되면
- **THEN** 검사는 기관 범위, 이번 실행까지의 이용자 문장, 이번 실행에서 호출한 tool 이름을 받는다

### Requirement: 검사 재시도 초과
다시 받는 횟수는 프로필의 한도를 MUST 넘지 않는다. 한도를 넘으면 프로필의 정리 규칙으로 위반 항목을 뺀 답을 다시 검사해 통과할 때만 내보내고, 정리 규칙이 없거나 통과하지 못하면 프로필의 고정 답으로 끝낸다. 위반한 답은 어느 경우에도 나가지 않는다.

#### Scenario: 위반 항목을 빼고 통과
- **WHEN** 한도까지 위반이 계속되고 정리한 답이 검사를 통과하면
- **THEN** 위반 항목이 빠진 답이 나가고 실행 상태는 `repaired`다

#### Scenario: 정리해도 위반
- **WHEN** 한도까지 위반이 계속되고 정리한 답도 검사를 통과하지 못하면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `fallback`이다

#### Scenario: 정리 규칙 없음
- **WHEN** 정리 규칙이 없는 프로필에서 한도까지 위반이 계속되면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `fallback`이다

### Requirement: 실행 한도
한 실행의 LLM 호출 횟수는 프로필의 한도를 MUST 넘지 않는다. 넘으면 더 호출하지 않고 프로필의 고정 답으로 끝낸다.

#### Scenario: 호출 한도 초과
- **WHEN** LLM이 한도까지 최종 답 없이 tool을 계속 호출하면
- **THEN** 더 호출하지 않고 프로필의 고정 답이 나가며 실행 상태는 `fallback`이다

### Requirement: tool 오류 처리
tool이 도메인 오류를 내면 실행기는 실행을 멈추지 않고 그 메시지를 오류 결과로 LLM에 SHALL 돌려준다. 그 밖의 예외는 실행을 실패로 끝내고 고정 답을 낸다. 내부 오류 내용은 사건과 기록에 MUST NOT 남긴다.

#### Scenario: 도메인 오류
- **WHEN** tool이 찾을 수 없음 오류를 내면
- **THEN** LLM은 그 메시지를 오류 결과로 받고 실행은 이어진다

#### Scenario: 예상하지 못한 예외
- **WHEN** tool이 예상하지 못한 예외를 내면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `failed`이며 예외 내용은 사건과 기록에 없다

### Requirement: LLM 오류 처리
LLM 호출이 실패하거나 응답을 거절하거나 출력이 잘리면 실행기는 tool을 더 실행하지 않고 프로필의 고정 답으로 SHALL 끝낸다.

#### Scenario: LLM 호출 실패
- **WHEN** LLM 호출이 재시도 뒤에도 실패하면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `failed`다

#### Scenario: 응답 거절
- **WHEN** LLM이 응답을 거절하면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `refused`다

#### Scenario: 출력 잘림
- **WHEN** LLM의 출력이 최대 길이에서 잘리면
- **THEN** 잘린 tool 호출은 실행되지 않고 프로필의 고정 답이 나가며 실행 상태는 `failed`다

### Requirement: 진행 사건
실행기는 실행 중 사건을 순서대로 SHALL 내보낸다. tool을 실행하기 전에 그 tool의 진행 문구를, 끝날 때 최종 답이나 고정 답을 한 번 내보낸다. tool 입력과 결과, 검사를 통과하지 못한 답은 사건에 MUST NOT 넣는다.

#### Scenario: 사건 순서
- **WHEN** tool 하나를 거쳐 최종 답이 나오면
- **THEN** 사건은 진행 문구, 최종 답, 끝 순서로 나온다

#### Scenario: 위반한 답은 사건에 없음
- **WHEN** 최종 답이 위반한 뒤 고친 답이 통과하면
- **THEN** 사건에는 고친 답만 있다

### Requirement: 중단
실행을 소비하는 쪽이 중간에 멈추면 실행기는 더 호출하지 않고 실행 상태를 `cancelled`로 SHALL 끝낸다.

#### Scenario: 소비자가 중단
- **WHEN** 사건을 받던 쪽이 최종 답 전에 멈추면
- **THEN** 이후 LLM과 tool이 호출되지 않고 실행 상태는 `cancelled`다

### Requirement: 실행 기록
실행기는 실행마다 기관, 프로필 이름과 버전, 모델, 상태, 시작·종료 시각, 입력·캐시 입력·캐시 쓰기·출력 토큰 수를 SHALL 기록한다. 단계마다 순서, 종류, tool 이름, 오류 여부, 걸린 시간을 기록한다. 최종 검사 단계에는 검사 이름과 위반 항목 값을 기록한다.

#### Scenario: 성공한 실행의 기록
- **WHEN** tool 하나를 거쳐 실행이 끝나면
- **THEN** 실행 행의 상태는 `completed`이고 LLM 호출, tool 호출, 최종 검사 단계가 순서대로 있다

#### Scenario: 위반 기록
- **WHEN** 최종 검사가 위반을 내면
- **THEN** 그 단계에 검사 이름과 위반 항목 값이 있다

#### Scenario: 진행 중 기록
- **WHEN** tool이 실행되는 시점에 다른 연결에서 기록을 읽으면
- **THEN** 실행 행은 상태 `running`으로 있고 앞선 단계가 저장돼 있다

### Requirement: 기록의 개인정보
실행 기록에 이용자 문장, 모델이 쓴 글, tool 결과 원문을 MUST NOT 저장한다. tool 입력은 tool이 기록해도 된다고 고른 값만 저장하고, 고르지 않으면 저장하지 않는다.

#### Scenario: 원문이 저장되지 않음
- **WHEN** 이용자 문장에 회원번호가 있고 tool 결과에 소개 문구가 있는 실행이 끝나면
- **THEN** 실행과 단계 행 어디에도 그 값이 없다

#### Scenario: 입력 기록을 고른 tool
- **WHEN** 입력 중 `keywords`만 기록하도록 고른 tool이 호출되면
- **THEN** 단계에는 `keywords`만 있다

#### Scenario: 입력 기록을 고르지 않은 tool
- **WHEN** 입력 기록을 고르지 않은 tool이 호출되면
- **THEN** 단계에 입력 값이 없다

### Requirement: 기록의 기관 범위
실행 기록은 그 기관 범위로만 MUST 조회한다.

#### Scenario: 다른 기관의 실행 조회
- **WHEN** B 기관 범위로 A 기관의 실행을 조회하면
- **THEN** 찾을 수 없음 오류가 난다

### Requirement: 외부 호출 중 트랜잭션 없음
실행기는 LLM을 호출하는 동안 DB 트랜잭션을 MUST NOT 잡는다.

#### Scenario: LLM 호출 시점
- **WHEN** LLM 호출이 시작되면
- **THEN** 실행의 DB 세션에는 열린 트랜잭션이 없다

### Requirement: LLM 설정
모델, 생각 수준, 출력 길이, 호출 제한 시간은 설정에서 SHALL 읽고 API 키는 `.env`에서만 읽는다. 키가 없어도 서버는 시작하고, 키가 없을 때 실행하면 LLM 호출 실패와 같이 끝난다. 키 값은 출력과 기록에 MUST NOT 남긴다.

#### Scenario: 키 없이 서버 시작
- **WHEN** API 키 없이 앱을 불러오면
- **THEN** 오류가 나지 않는다

#### Scenario: 키 없이 실행
- **WHEN** API 키 없이 실행을 시작하면
- **THEN** 프로필의 고정 답이 나가고 실행 상태는 `failed`다

#### Scenario: 모델 설정 적용
- **WHEN** `LLM_MODEL`을 바꿔 실행하면
- **THEN** 그 모델로 호출되고 실행 기록에 그 모델이 남는다

### Requirement: 실행 안 대화 유지
한 실행 안에서 LLM이 낸 응답은 고치거나 빼지 않고 그대로 다음 호출에 MUST 보낸다. 시스템 프롬프트와 tool 정의는 실행 중에 바뀌지 않는다.

#### Scenario: 응답 내용 재전송
- **WHEN** LLM 응답에 추론 항목과 tool 호출이 함께 있으면
- **THEN** 다음 호출의 대화에 그 항목이 순서 그대로 들어 있다

### Requirement: 제공자 저장 없음
실행기는 LLM 제공자에게 대화 내용을 저장하도록 MUST NOT 요청한다. 제공자가 응답 저장을 끌 수 있으면 끄고, 대화는 호출마다 직접 보낸다.

#### Scenario: 저장 끔
- **WHEN** LLM을 호출하면
- **THEN** 요청의 응답 저장 값이 꺼져 있고 이전 응답 id를 쓰지 않는다

### Requirement: 모델 가격표
시스템은 모델별 입력, 캐시 입력, 출력의 1M 토큰당 가격과 확인한 날, 제거 예정일을 설정에 SHALL 둔다. 금액은 부동소수를 쓰지 않는다. 기본 모델은 가격표에 MUST 있다.

#### Scenario: 기본 모델 가격
- **WHEN** 가격표에서 기본 모델을 찾으면
- **THEN** 입력, 캐시 입력, 출력 가격과 확인한 날이 있다
