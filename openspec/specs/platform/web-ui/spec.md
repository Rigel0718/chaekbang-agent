# platform/web-ui Specification

## Purpose
이용자·관리자 화면을 같은 서버의 정적 파일로 내주는 방식과, 화면 코드가 지켜야 할 계약(기존 API만 쓰기, 브라우저 저장 규칙, 서버 값의 안전한 표시, 응답 스키마와의 일치)을 정한다. 화면의 세부 동작은 design의 화면 규칙과 브라우저 확인 항목이 맡는다.

## Requirements

### Requirement: 이용자 화면 내주기
시스템은 `/ui/librarian/`에서 이용자 화면 HTML을 SHALL 내준다. 화면이 쓰는 스타일과 스크립트는 같은 서버의 `/ui/` 아래에서 빌드 없이 내준다. 화면 파일에는 비밀 값이 없으므로 토큰 없이도 내준다. 기관 데이터는 화면 파일이 아니라 토큰을 붙인 API 호출로만 받는다.

#### Scenario: 화면 HTML
- **WHEN** 토큰 없이 `GET /ui/librarian/`을 호출하면
- **THEN** 200이고 본문은 HTML이다

#### Scenario: 화면이 참조하는 파일
- **WHEN** 이용자 화면 HTML이 참조하는 스타일과 스크립트, 그리고 그 스크립트가 불러오는 모듈을 모두 호출하면
- **THEN** 모두 200이다

#### Scenario: 없는 화면 파일
- **WHEN** `/ui/` 아래의 없는 파일을 호출하면
- **THEN** 404다

#### Scenario: 화면 패키지 문서는 내주지 않음
- **WHEN** `GET /ui/README.md`나 `GET /ui/CLAUDE.md`를 호출하면
- **THEN** 404다

### Requirement: 화면 경로가 API를 가리지 않음
화면 경로는 기존 API와 문서 경로를 MUST NOT 가린다. 화면을 내준 뒤에도 기존 API는 이전과 같은 응답을 준다.

#### Scenario: AI 사서 대화 경로
- **WHEN** 화면을 내주는 상태에서 토큰 없이 `POST /librarian/messages`를 호출하면
- **THEN** 401이다

#### Scenario: 검색 경로
- **WHEN** 화면을 내주는 상태에서 토큰 없이 `GET /catalog/suggest?q=데`를 호출하면
- **THEN** 401이다

#### Scenario: API 문서
- **WHEN** `GET /docs`를 호출하면
- **THEN** 200이다

### Requirement: 기존 API만 사용
화면은 화면 전용 API 없이 기존 API만 MUST 쓴다. 화면이 부르는 경로는 다른 클라이언트도 쓰는 일반 API이고, 화면 때문에 `/ui` 아래에 API 경로를 두지 않는다.
- 로그인 화면: 로그인, 내 정보
- 이용자 화면: 내 정보, 자동완성, 검색, 주제 검색, 비슷한 책, AI 사서 대화, 대화 종료, 도서관 안내, 회원 로그인·로그아웃, 대출, 반납, 희망도서 신청
- 관리자 화면: 내 정보, 로그아웃, 기관 정보, 운영 에이전트 대화와 대화 종료, 큐레이션·연체 안내문 틀·구매 요청서의 목록·상세·승인·반려(큐레이션은 내리기도), 희망도서 목록과 닫기, 오늘의 연체 안내 목록

#### Scenario: 서버 경로
- **WHEN** 서버의 경로 목록을 읽으면
- **THEN** `/ui` 아래에는 정적 파일 경로 하나만 있고 API 경로가 없다

#### Scenario: 화면이 부르는 경로
- **WHEN** 화면 스크립트에서 서버에 요청하는 경로를 모두 모으면
- **THEN** 모두 `/auth/login`, `/auth/me`, `/auth/logout`, `/auth/member-login`, `/auth/member-logout`, `/catalog/suggest`, `/catalog/search`, `/catalog/topic`, `/catalog/books/{id}/similar`, `/librarian/messages`, `/librarian/sessions/{id}`, `/library`, `/library/guide`, `/loans`, `/loans/return`, `/book-requests`, `/book-requests/{id}`, `/admin-agent/messages`, `/admin-agent/sessions/{id}`, `/curations`, `/curations/{id}`, `/curations/{id}/approve`, `/curations/{id}/reject`, `/curations/{id}/unpublish`, `/overdue-notice-templates`, `/overdue-notice-templates/{id}`, `/overdue-notice-templates/{id}/approve`, `/overdue-notice-templates/{id}/reject`, `/purchase-requests`, `/purchase-requests/{id}`, `/purchase-requests/{id}/approve`, `/purchase-requests/{id}/reject`, `/overdue-notices/today` 중 하나다

#### Scenario: 부르는 경로가 서버에 있음
- **WHEN** 화면 스크립트가 요청하는 경로와 메서드를 서버의 경로 목록과 맞춰 보면
- **THEN** 모두 서버에 있는 경로와 메서드다

### Requirement: 브라우저 저장
화면은 브라우저에 직원 토큰 말고 아무것도 MUST NOT 저장한다. 토큰은 화면마다 키 하나다. 키오스크 토큰은 `localStorage`에, 관리자 토큰은 `sessionStorage`에 둔다. 관리자 토큰은 탭을 닫으면 사라지고 키오스크 토큰을 덮어쓰지 않는다. 대화, 검색어, 담은 책, 회원 토큰, 관리자 화면의 목록은 화면 메모리에만 두고, 새로 고치거나 화면을 비우면 사라진다. 회원 토큰은 새로 고치면 로그아웃된다는 뜻이다. 공용 PC에서 다음 사람이 앞사람의 기록을 보지 않게 하기 위해서다.

#### Scenario: 저장소 사용
- **WHEN** 화면 스크립트에서 브라우저 저장소(`localStorage`, `sessionStorage`, `indexedDB`, 쿠키)를 쓰는 곳을 모두 모으면
- **THEN** `localStorage`의 키오스크 토큰 키 하나와 `sessionStorage`의 관리자 토큰 키 하나를 읽고 쓰고 지우는 곳뿐이다

#### Scenario: 회원 토큰은 저장소에 없음
- **WHEN** 회원 로그인에 성공한 뒤 브라우저 저장소를 보면
- **THEN** 회원 토큰이 어느 저장소에도 없고, 새로 고치면 로그아웃된 상태다(브라우저 확인)

#### Scenario: 두 토큰이 섞이지 않음
- **WHEN** 같은 브라우저에서 키오스크로 로그인해 둔 뒤 새 탭에서 관리자로 로그인하면
- **THEN** 키오스크 토큰 키는 그대로이고, 관리자 토큰은 다른 키에 있다

#### Scenario: 옛 토큰 키
- **WHEN** 화면 스크립트를 검사하면
- **THEN** 옛 키 `chaekbang.token`과 주소의 `#token=`을 읽는 곳이 없다

### Requirement: 서버 값의 안전한 표시
화면은 서버가 준 값을 글자로만 MUST 넣고 HTML로 해석하지 않는다. 서명, 답 문장, 추천 이유, 근거 문구, 안내 문구, 큐레이션 소개, 안내문 틀, 반려 사유, 회원 값, 서버 오류 문구가 모두 그렇다. 표지와 상품 링크는 서버가 준 원본 URL을 그대로 쓰고, `http`·`https` 주소만 쓴다.

#### Scenario: HTML 해석 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`이 없다

#### Scenario: 주소 형식
- **WHEN** 화면 스크립트에서 표지·상품 링크 주소를 요소에 넣는 곳을 검사하면
- **THEN** 모두 `http`·`https` 주소만 통과시키는 같은 함수를 거친다

### Requirement: 카드 필드와 응답 스키마 일치
책 카드가 읽는 필드는 카드에 쓰는 응답 스키마(찾기 결과, 추천 카드, 비슷한 책)의 필드에 MUST 있다. 백엔드가 필드 이름을 바꾸면 테스트가 깨져 화면과 API가 어긋난 것을 알린다.

#### Scenario: 카드 필드
- **WHEN** 카드 스크립트가 책 값에서 읽는 필드 이름을 모두 모으면
- **THEN** 모두 찾기 결과, 추천 카드, 비슷한 책 스키마의 필드 중 하나다

#### Scenario: 필드 이름이 바뀜
- **WHEN** 카드 스크립트가 스키마에 없는 필드 이름을 읽으면
- **THEN** 카드 필드 테스트가 실패하고 그 이름을 알린다

### Requirement: 운영 방식에 따른 대출 버튼
이용자 화면은 도서관 안내 응답의 운영 방식이 `internal`일 때만 [대출·반납] 버튼을 MUST 보인다. 외부 대출 기관이거나 안내를 읽지 못하면 숨긴다. [희망도서 신청] 버튼은 두 방식 모두 보인다. 대출·반납의 최종 판단은 서버가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** [대출·반납] 버튼은 숨김 상태로 시작하고 [희망도서 신청] 버튼은 숨김이 아니다

#### Scenario: 버튼을 보이는 조건
- **WHEN** 화면 스크립트에서 [대출·반납] 버튼을 보이게 하는 곳을 검사하면
- **THEN** 안내 응답의 `loan_mode`가 `internal`인지 보는 한 곳뿐이다

### Requirement: 대출·희망도서 입력칸 비우기
이용자 화면은 로그인·대출·반납·희망도서 입력칸의 값을 화면 메모리에만 두고, 칸을 닫을 때와 화면을 비울 때(새 대화, 무입력, 로그아웃, 세션 끝) 모든 입력을 MUST 지운다. 로그인에 성공하면 번호 칸을, 희망도서 신청이 성공하면 모든 입력을, 빌리기·반납이 성공하면 등록번호를 지운다. 입력칸은 브라우저 자동 완성을 끈다. 이 요구사항은 브라우저 확인 항목으로 확인한다.

#### Scenario: 화면 비우기
- **WHEN** 휴대폰 번호나 서명을 적은 채 무입력 시간이 지나거나 [새 대화]를 누르면
- **THEN** 입력칸이 닫히고 다시 열면 모든 칸이 비어 있다

#### Scenario: 칸 닫기
- **WHEN** 휴대폰 번호를 적은 뒤 칸을 닫았다 다시 열면
- **THEN** 번호 칸이 비어 있다

#### Scenario: 로그인 성공
- **WHEN** 로그인에 성공하면
- **THEN** 번호 칸이 비고 번호는 어디에도 남지 않는다

#### Scenario: 입력칸 자동 완성
- **WHEN** 이용자 화면 HTML의 로그인·대출·희망도서 입력칸을 읽으면
- **THEN** 모두 `autocomplete="off"`다

### Requirement: 로그인·관리자 화면 내주기
시스템은 `/ui/login/`에서 로그인 화면을, `/ui/admin/`에서 관리자 화면을 SHALL 내준다. 이용자 화면과 같이 빌드 없는 정적 파일이고 토큰 없이 내준다. 기관 데이터는 토큰을 붙인 API 호출로만 받는다.

#### Scenario: 화면 HTML
- **WHEN** 토큰 없이 `GET /ui/login/`과 `GET /ui/admin/`을 호출하면
- **THEN** 둘 다 200이고 본문은 HTML이다

#### Scenario: 화면이 참조하는 파일
- **WHEN** 로그인·관리자 화면 HTML이 참조하는 스타일과 스크립트, 그리고 그 스크립트가 불러오는 모듈을 모두 호출하면
- **THEN** 모두 200이다

### Requirement: 로그인과 역할별 행선지
로그인 화면은 아이디와 비밀번호로 `POST /auth/login`을 SHALL 부르고, 응답의 역할로 행선지를 정한다. 키오스크는 이용자 화면으로, 관리자는 관리자 화면으로 간다. 토큰은 역할에 맞는 키에 저장한다. 로그인 실패(401)는 서버 문구를 글자로 보이고 아무것도 저장하지 않는다. 입력칸은 브라우저 자동 완성을 끄고, 공용 PC에서 비밀번호를 저장하지 말라는 안내를 보인다.

#### Scenario: 역할별 행선지
- **WHEN** 로그인 화면 스크립트에서 로그인 뒤 이동하는 곳을 검사하면
- **THEN** 역할 `kiosk`는 `/ui/librarian/`, 역할 `admin`은 `/ui/admin/`이고 그 밖의 역할은 이동하지 않는다

#### Scenario: 로그인 입력칸
- **WHEN** 로그인 화면 HTML을 읽으면
- **THEN** 아이디와 비밀번호 칸은 `autocomplete="off"`이고 비밀번호 저장 안내 문구가 있다

#### Scenario: 틀린 비밀번호
- **WHEN** 브라우저에서 틀린 비밀번호로 로그인하면
- **THEN** 서버 문구가 보이고 화면은 로그인 화면에 머물며 두 토큰 키 모두 비어 있다(브라우저 확인)

### Requirement: 화면의 역할 확인
이용자 화면과 관리자 화면은 열 때 자기 키의 토큰으로 `GET /auth/me`를 불러 역할을 MUST 확인한다. 이용자 화면은 `kiosk`, 관리자 화면은 `admin`만 받는다. 토큰이 없거나, 응답이 401이거나, 역할이 다르면 그 화면의 키만 지우고 로그인 화면으로 보낸다. 쓰는 중에 어떤 요청이든 401이면 똑같이 한다. 관리자 화면은 [로그아웃]으로 `POST /auth/logout`을 부르고 키를 지운 뒤 로그인 화면으로 간다. 뒤로 가기 캐시에서 다시 보인 관리자 화면은 토큰을 다시 확인한다. 이용자 화면에는 로그아웃 버튼이 없다.

#### Scenario: 받는 역할
- **WHEN** 이용자·관리자 화면 스크립트에서 `GET /auth/me` 응답의 역할을 맞춰 보는 곳을 검사하면
- **THEN** 이용자 화면은 `kiosk`, 관리자 화면은 `admin`과만 맞춰 본다

#### Scenario: 이용자 화면에 관리자 토큰
- **WHEN** 관리자 토큰을 키오스크 키에 넣고 이용자 화면을 열면
- **THEN** 키오스크 키가 지워지고 로그인 화면으로 간다(브라우저 확인)

#### Scenario: 로그아웃
- **WHEN** 관리자 화면에서 [로그아웃]을 누른 뒤 [뒤로]로 돌아오면
- **THEN** 관리자 화면 내용이 보이지 않고 로그인 화면으로 간다(브라우저 확인)

#### Scenario: 이용자 화면의 로그아웃
- **WHEN** 이용자 화면 HTML과 스크립트를 검사하면
- **THEN** 로그아웃 버튼과 `/auth/logout` 호출이 없다

### Requirement: 이용자 화면의 무입력·이용 상한 비우기
이용자 화면은 두 시계로 화면을 MUST 비운다. 시계가 하는 일은 로그인 여부에 따라 다르다.
- **무입력**: 마지막 입력에서 1분이다. 45초에 알림을 띄우고, 입력하면 알림을 닫고 다시 센다. 답을 받는 동안에는 세지 않는다. 로그인하지 않았으면 화면을 비우고 시작 화면을 보인다(대화 종료, 담은 책·입력칸 지움). 로그인 중이면 **회원만 로그아웃**한다(키오스크 토큰은 그대로).
- **이용 상한**: **로그인한 순간부터** 3분이다. 2분 30초에 알림을 띄운다. 입력해도 늘어나지 않고, 답을 받는 중에도 멈추지 않는다. 끝나면 회원만 로그아웃한다. 로그인하지 않았으면 이용 상한은 없다.

회원 로그아웃은 서버 회원 세션을 끊고 **대화(대화 종료, 검색 결과, 자동완성), 담은 책, 입력칸을 모두 비운다.** 시작 화면은 보이지 않는다. 버튼, 무입력, 이용 상한, 서버 회원 세션 오류(403)가 모두 같다. 답을 받는 중이었으면 그 답은 끊긴다. 로그아웃한 뒤에는 익명 무입력 시계가 처음부터 다시 센다. 알림은 화면 아래 띠에 문구와 남은 초를 글자로 보인다. 로그인 중의 문구는 "N초 뒤 로그아웃해요"와 "N초 뒤 이용 시간이 끝나 로그아웃해요"다. 두 시계 모두 서버 AI 사서 세션의 무입력 시간(5분)보다 짧다.

익명 상태에서 시간이 다 돼 비우면 **시작 화면**("화면을 눌러 시작하세요")을 보이고, 누르면 대화 화면으로 간다. 시작 화면은 화면을 처음 열 때도 보인다. 두 시계 모두 키오스크 토큰은 그대로 두고 로그아웃하지 않는다(다음 이용자가 직원 계정 없이 쓸 수 있어야 한다). [새 대화]와 세션 끝(404)은 시작 화면 없이 대화만 비운다.

#### Scenario: 시간 값
- **WHEN** 이용자 화면 스크립트의 시간 값을 읽으면
- **THEN** 무입력은 60초·알림 45초, 이용 상한은 180초·알림 150초이고, 둘 다 서버 설정 `librarian_session_idle_minutes`(5분)보다 짧다. 서버 회원 세션 수명은 이용 상한과 같은 3분이다

#### Scenario: 무입력 비우기
- **WHEN** 로그인하지 않은 채 45초 동안 입력하지 않으면 알림이 뜨고, 입력 없이 1분이 되면
- **THEN** 화면이 비워지고 시작 화면이 보인다(브라우저 확인)

#### Scenario: 익명은 이용 상한이 없음
- **WHEN** 로그인하지 않은 채 3분이 넘도록 계속 입력하며 쓰면
- **THEN** 화면은 비워지지 않고 이용 상한 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 무입력 알림과 연장
- **WHEN** 이용 중 45초 동안 입력하지 않으면 알림이 뜨고, 그때 화면을 누르면
- **THEN** 알림이 닫히고 다시 1분을 센다. 로그인 중의 알림 문구는 "N초 뒤 로그아웃해요"다(브라우저 확인)

#### Scenario: 로그인 중 무입력 로그아웃
- **WHEN** 로그인한 뒤 알림에도 입력하지 않아 1분이 되면
- **THEN** 회원만 로그아웃되어 대화와 담은 책과 입력칸이 비고, 시작 화면은 보이지 않는다(브라우저 확인)

#### Scenario: 이용 상한
- **WHEN** 로그인한 뒤 계속 입력하며 쓰다가 2분 30초가 되면 알림이 뜨고, 입력을 이어 가도 3분이 되면
- **THEN** 회원만 로그아웃되어 대화가 비워지고, 답을 받는 중이었으면 그 답은 끊긴다(브라우저 확인)

#### Scenario: 쓰지 않는 화면
- **WHEN** 비운 화면에 아무도 입력하지 않으면
- **THEN** 어떤 시계도 시작하지 않고 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 로그아웃 뒤 익명 시계
- **WHEN** 회원 로그아웃 뒤 1분 동안 입력하지 않으면
- **THEN** 익명 무입력으로 화면이 비워지고 시작 화면이 보인다(브라우저 확인)

#### Scenario: 시작 화면
- **WHEN** 시작 화면을 누르면
- **THEN** 시작 화면이 사라지고 대화 화면이 보인다(브라우저 확인)

#### Scenario: 처음 열 때
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** 시작 화면이 숨김이 아닌 상태로 있다

#### Scenario: 로그아웃하지 않음
- **WHEN** 시간이 다 돼 비우거나 회원을 로그아웃하는 길(시계가 부르는 함수와 시작 화면을 보이는 함수)을 검사하면
- **THEN** 키오스크 토큰을 지우거나 로그인 화면으로 보내거나 `/auth/logout`을 부르는 곳이 없다

#### Scenario: 새 대화는 시작 화면 없이
- **WHEN** [새 대화]를 누르면
- **THEN** 대화가 비워지고 시작 화면은 보이지 않는다(브라우저 확인)

### Requirement: 관리자 화면의 탭과 운영 방식
관리자 화면은 한 페이지에 탭 넷(운영 대화, 승인 목록, 희망도서, 오늘의 연체)을 SHALL 둔다. 열린 탭은 주소 hash로 기억한다. 기관 정보(`GET /library`)의 `loan_mode`가 `internal`일 때만 [오늘의 연체] 탭과 승인 목록의 연체 안내문 틀 묶음을 보인다. 외부 대출 기관이거나 기관 정보를 읽지 못하면 숨긴다. 최종 판단은 서버(409)가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 관리자 화면 HTML을 읽으면
- **THEN** [오늘의 연체] 탭과 연체 안내문 틀 묶음은 숨김 상태로 시작한다

#### Scenario: 보이는 조건
- **WHEN** 관리자 화면 스크립트에서 [오늘의 연체] 탭과 연체 안내문 틀 묶음을 보이게 하는 곳을 검사하면
- **THEN** 기관 정보의 `loan_mode`가 `internal`인지 보는 한 곳뿐이다

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관의 관리자로 관리자 화면을 열면
- **THEN** [오늘의 연체] 탭과 연체 안내문 틀 묶음이 보이지 않는다(브라우저 확인)

### Requirement: 운영 대화 화면
관리자 화면의 운영 대화는 `POST /admin-agent/messages`의 사건을 읽어 답 문장을 글자로 SHALL 보인다. `status`는 답이 오기 전까지 한 줄로 보이고, `unsupported`인 답에는 못 하는 분석이라는 표시를 붙인다. [새 대화]는 대화 종료를 부르고 화면을 비운다. 세션이 끝나 404면 세션을 버리고 안내하며, 보낸 문장을 입력칸에 되돌린다. 답이 끝나면 승인 대기 수를 다시 세어 [승인 목록] 탭에 보인다.

#### Scenario: 대화 요청의 본문
- **WHEN** 관리자 화면 스크립트에서 운영 에이전트 대화 요청 본문을 만드는 곳을 검사하면
- **THEN** 본문의 키는 `session_id`, `message`뿐이다

#### Scenario: 답과 승인 대기 수
- **WHEN** 운영 대화에서 큐레이션 초안을 만들어 달라고 하고 답이 끝나면
- **THEN** 답 문장이 보이고 [승인 목록] 탭의 승인 대기 수가 하나 는다(브라우저 확인)

### Requirement: 승인 목록
관리자 화면의 승인 목록은 큐레이션, 연체 안내문 틀, 구매 요청서를 묶음별로 SHALL 보이고, 기본으로 승인 대기만 보인다. 줄을 누르면 상세를 보이고 상태에 맞는 동작만 보인다.
- 승인 대기: [승인](확인 한 번)과 [반려](사유 필수, 비어 있으면 요청하지 않음)
- 게시한 큐레이션: [게시 내리기]
- 그 밖의 상태: 동작 없음. 반려된 것은 반려 사유를 보인다

구매 요청서의 확정 전 상세는 항목별 추정 단가·금액, 추정 총액과 조회 시각을 보인다. 가격 없는 항목은 "가격 없음"으로, 조회할 수 없으면 그렇다고 보인다. 확정본은 기록한 단가·금액·총액·조회 시각·출처를 보인다. 승인·반려·내리기가 409나 503이면 서버 문구를 상세 안에 글자로 보이고 상태를 바꾼 것처럼 보이지 않는다. 성공하면 상세와 목록을 서버에서 다시 읽는다. 초안 만들기·고치기·지우기·다시 제출은 화면에 두지 않는다.

#### Scenario: 상태별 동작
- **WHEN** 승인 대기, 게시, 반려 상태의 큐레이션 상세를 차례로 열면
- **THEN** 각각 [승인]·[반려], [게시 내리기], 반려 사유만 보인다(브라우저 확인)

#### Scenario: 빈 반려 사유
- **WHEN** 반려 사유를 비운 채 [반려]를 누르면
- **THEN** 요청을 보내지 않고 사유를 적으라고 보인다(브라우저 확인)

#### Scenario: 가격 없는 구매 요청서 승인
- **WHEN** 가격 없는 항목이 있는 구매 요청서를 승인하면
- **THEN** 서버의 409 문구(ISBN 포함)가 상세 안에 보이고 요청서는 승인 대기로 남는다(브라우저 확인)

#### Scenario: 확정본 표시
- **WHEN** 확정된 구매 요청서 상세를 열면
- **THEN** 기록한 단가·금액·총액·조회 시각·출처가 보이고 동작 버튼이 없다(브라우저 확인)

### Requirement: 관리자 화면의 회원 값
관리자 화면은 회원 값(회원번호, 이름, 전화번호, 채운 안내 문안)을 [희망도서]와 [오늘의 연체] 탭에서만 MUST 보인다. 그 탭에 들어올 때마다 서버에서 다시 읽는다(연체·신청은 그사이 바뀌므로 지난 목록을 다시 쓰지 않는다). 회원 값을 복사·출력·내려받는 버튼을 두지 않고, 브라우저 콘솔에 쓰지 않는다. 확정한 안내문 틀이 없어 오늘의 연체 목록이 409면 서버 문구와 함께 운영 대화에서 틀을 만들어 승인하라고 안내한다.

#### Scenario: 회원 값을 읽는 곳
- **WHEN** 관리자 화면 스크립트에서 `member_number`, `phone`을 읽는 곳을 모두 모으면(이름 `name`은 기관 이름과 겹쳐 브라우저 확인으로 본다)
- **THEN** 희망도서 목록과 오늘의 연체 목록을 그리는 곳뿐이다

#### Scenario: 콘솔 출력 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `console.` 호출이 없다

#### Scenario: 탭에 돌아오면 다시 읽음
- **WHEN** [오늘의 연체] 탭을 연 뒤 다른 탭에서 대출을 반납하고 돌아오면
- **THEN** 서버에서 다시 읽은 목록이 보이고 반납한 줄은 없다(브라우저 확인)

### Requirement: 이용자 화면의 Enter 갈림
이용자 화면은 입력칸에서 Enter를 누르면(자동완성 후보를 고른 때는 빼고) 먼저 서명·저자 찾기를 SHALL 부른다. 한 권 이상 찾으면 AI 사서 대화를 보내지 않고 두 단계 결과를 보인다. 찾은 책이 없거나, 입력이 서버의 질의 상한(100자)을 넘거나, 찾기가 실패하면(401은 빼고 로그인 화면으로 간다) 지금처럼 같은 글을 AI 사서 대화로 보낸다. 찾기 응답을 기다리는 동안의 Enter는 무시한다.

#### Scenario: 찾은 책이 있음
- **WHEN** 실험 기관 키오스크 화면에서 `채식`을 치고 Enter를 누르면
- **THEN** 두 단계 결과가 보이고 `/librarian/messages` 요청이 없다

#### Scenario: 찾은 책이 없음
- **WHEN** 서명·저자로 걸리는 책이 없는 문장을 치고 Enter를 누르면
- **THEN** 지금처럼 그 문장이 AI 사서 대화로 간다

#### Scenario: 긴 입력
- **WHEN** 100자를 넘는 글을 치고 Enter를 누르면
- **THEN** `/catalog/search` 요청 없이 AI 사서 대화로 간다. 화면의 이 상한은 서버 검색 API의 질의 상한과 같은 값이다

#### Scenario: 찾기 실패
- **WHEN** `/catalog/search`가 401이 아닌 오류로 실패하면
- **THEN** 같은 글이 AI 사서 대화로 간다

#### Scenario: 자동완성 후보 고르기
- **WHEN** 자동완성 후보를 화살표로 고르고 Enter를 누르면
- **THEN** 지금처럼 그 책 카드가 나오고 `/catalog/search`·`/catalog/topic` 요청이 없다

#### Scenario: 찾는 중 Enter
- **WHEN** 찾기 응답이 오기 전에 Enter를 다시 누르면
- **THEN** 두 단계 결과는 하나만 생긴다

### Requirement: 두 단계 결과
두 단계 결과는 위 단 "이 책을 찾으시나요?"(서명·저자 찾기 결과의 앞 2권), 아래 단 "'질의'와 관련된 책"(같은 질의의 주제 검색 결과에서 위 단의 책을 뺀 것), [사서에게 물어보기]로 SHALL 이루어진다. 위 단은 주제 검색을 기다리지 않고 먼저 보인다. 아래 단이 비거나 주제 검색이 실패하면 아래 단을 제목째 숨긴다. 카드는 다른 찾기 결과와 같은 카드다. [사서에게 물어보기]는 같은 글을 AI 사서 대화로 한 번 보내고 꺼진다. 두 단계 결과는 서버 대화 세션을 만들거나 바꾸지 않는다.

#### Scenario: 위 단과 아래 단
- **WHEN** `채식`으로 두 단계 결과가 보이면
- **THEN** 위 단에 채식주의자를 포함한 2권 이하가 있고, 아래 단에는 위 단의 책이 없다

#### Scenario: 위 단 권수
- **WHEN** 화면 스크립트의 위 단 권수를 읽으면
- **THEN** 2다

#### Scenario: 아래 단이 비거나 실패
- **WHEN** 주제 검색 요청이 실패하면
- **THEN** 아래 단과 그 제목이 보이지 않고 위 단과 [사서에게 물어보기]는 남는다

#### Scenario: 사서에게 물어보기
- **WHEN** [사서에게 물어보기]를 누르면
- **THEN** 같은 글이 AI 사서 대화로 한 번 가고 버튼이 꺼져 다시 눌러도 요청이 없다

#### Scenario: 화면 비우기
- **WHEN** 두 단계 결과가 있는 화면을 [새 대화]나 무입력으로 비우면
- **THEN** 두 단계 결과도 지워진다

### Requirement: 회원 토큰의 행선지
이용자 화면은 회원 토큰을 대출(`POST /loans`), 희망도서 신청(`POST /book-requests`), 회원 로그아웃(`POST /auth/member-logout`) 요청의 `X-Member-Token` 헤더에만 MUST 붙인다. 대화, 대화 종료, 검색, 자동완성, 안내 요청에는 붙이지 않는다. 이용자 화면은 요청 본문에 회원번호를 넣지 않고, 어떤 응답의 회원번호·이름·전화번호도 표시하지 않는다. 관리자 화면은 회원 값을 읽어 보이기만 하고 어떤 요청에도 넣지 않는다.

#### Scenario: 회원 토큰을 보내는 곳
- **WHEN** 화면 스크립트에서 `X-Member-Token` 헤더를 붙이는 곳을 모두 모으면
- **THEN** 대출, 희망도서 신청, 회원 로그아웃 요청을 만드는 곳뿐이다

#### Scenario: 이용자 화면의 회원번호
- **WHEN** 이용자 화면 스크립트에서 `member_number`를 쓰는 곳을 모두 모으면
- **THEN** 없다

#### Scenario: 대화 요청의 본문
- **WHEN** 화면 스크립트에서 AI 사서 대화 요청 본문을 만드는 곳을 검사하면
- **THEN** 본문의 키는 `session_id`, `message`, `selected_library_book_id`뿐이다

### Requirement: 이용자 화면의 회원 로그인
이용자 화면은 휴대폰 번호로 `POST /auth/member-login`을 불러 회원으로 SHALL 로그인한다. 검색·대화·반납은 로그인 없이 되고, 담기·빌리기·희망도서 신청은 로그인한 회원만 할 수 있다.
- 로그인 칸은 입력칸의 한 모드다. 번호 칸 하나(숫자 키패드)이고 성공하면 번호를 지운다. 실패하면 서버 문구를 글자로 보인다.
- 로그인 중에는 위 띠에 이름·번호 없이 "로그인 중"과 [로그아웃]만 보이고, 담은 책 표시는 로그인한 동안에만 보인다.
- 운영 방식과 상관없이 로그인 칸을 보인다. 외부 대출 기관에서는 대출·반납이 지금처럼 숨겨진다.

#### Scenario: 익명의 띠
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** [회원 로그인]은 숨김이 아니고 담은 책 표시와 [로그아웃]은 숨김 상태로 시작한다

#### Scenario: 로그인 중 표시
- **WHEN** 로그인에 성공하면
- **THEN** 위 띠에 "로그인 중"이 보이고 이름·번호는 어디에도 보이지 않는다(브라우저 확인)

#### Scenario: 로그아웃 버튼
- **WHEN** [로그아웃]을 누르면
- **THEN** 대화와 담은 책과 입력칸이 비고 [회원 로그인]이 다시 보인다(브라우저 확인)

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관에서 이용자 화면을 열면
- **THEN** [대출·반납]은 숨겨지고 [회원 로그인]은 보이며, 로그인한 뒤 담기와 희망도서 신청이 된다(브라우저 확인)

### Requirement: 로그인이 필요한 동작은 로그인 뒤에 이어서 함
이용자 화면은 로그인이 필요한 동작을 로그인 전에 누르면 로그인 칸을 열고, 성공하면 그 동작을 MUST 이어서 한다(기다리는 동작 하나만 기억한다). 담기는 그 책을 담고, 빌리기·희망도서는 그 칸으로 돌아오며 이미 적은 등록번호·서명은 남긴다. 빌리기·희망도서 칸에는 회원번호 칸이 없다.

#### Scenario: 로그인 전 담기
- **WHEN** 로그인하지 않은 채 카드의 [담기]를 누르고 번호로 로그인하면
- **THEN** 그 책이 담긴다(브라우저 확인)

#### Scenario: 로그인 전 빌리기
- **WHEN** 로그인하지 않은 채 등록번호를 적고 [빌리기]를 눌러 로그인하면
- **THEN** 빌리기 칸으로 돌아오고 등록번호는 남아 있다(브라우저 확인)

#### Scenario: 회원번호 칸 없음
- **WHEN** 이용자 화면 HTML의 입력칸을 읽으면
- **THEN** 회원번호를 받는 입력 요소가 없고 휴대폰 번호를 받는 입력 요소 하나가 있다

### Requirement: 회원 세션 오류와 새 대화
이용자 화면은 요청이 403(회원 로그인이 필요)이면 화면도 MUST 로그아웃 처리하고 로그인 칸을 연다. 401이면 지금처럼 키오스크 로그인 화면으로 간다. [새 대화]는 대화만 비우고 로그인과 담은 책은 남긴다.

#### Scenario: 끝난 세션으로 빌리기
- **WHEN** 서버 회원 세션이 끝난 뒤 [빌리기]를 누르면
- **THEN** 로그인 칸이 열리고 키오스크 로그인 화면으로 가지 않는다(브라우저 확인)

#### Scenario: 새 대화는 로그인을 남김
- **WHEN** 로그인해 책을 담은 뒤 [새 대화]를 누르면
- **THEN** 대화는 비워지고 로그인과 담은 책은 그대로다(브라우저 확인)

### Requirement: 이용자 화면의 직원 로그인 이동
이용자 화면은 위 띠에 로그인 화면(`/ui/login/`)으로 가는 [직원 로그인] 링크를 항상 MUST 보인다. 키오스크·관리자 직원이 다른 계정으로 로그인하는 길이다. 링크는 이동만 하고 키오스크 토큰을 지우거나 직원 로그아웃(`/auth/logout`)을 부르지 않는다. 로그인 화면은 로그인한 상태로 열려도 넘기지 않는다.

#### Scenario: 직원 로그인 링크
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** `/ui/login/`을 가리키는 [직원 로그인] 링크가 숨김 없이 있다

#### Scenario: 링크는 로그아웃하지 않음
- **WHEN** 링크를 눌러 로그인 화면으로 갔다가 이용자 화면으로 돌아오면
- **THEN** 키오스크 토큰이 그대로라 다시 로그인하지 않아도 쓸 수 있다(브라우저 확인)
