# platform/web-ui Specification

## Purpose
이용자·관리자 화면을 같은 서버의 정적 파일로 내주는 방식과, 화면 코드가 지켜야 할 계약(기존 API만 쓰기, 브라우저 저장 규칙, 서버 값의 안전한 표시, 응답 스키마와의 일치)을 정한다. 화면의 세부 동작은 design의 화면 규칙과 브라우저 확인 항목이 맡는다.

## Requirements

### Requirement: 이용자 화면 내주기
시스템은 `/ui/librarian/`에서 이용자 화면 HTML을 SHALL 내준다. 화면이 쓰는 스타일과 스크립트는 같은 서버의 `/ui/` 아래에서 빌드 없이 내준다. 화면 파일에는 비밀 값이 없으므로 토큰 없이도 내준다. 기관 데이터는 화면 파일이 아니라 토큰을 붙인 API 호출로만 받는다.

#### Scenario: 화면 HTML
- **WHEN** 토큰 없이 `GET /ui/librarian/`을 호출하면
- **THEN** 200이고 본문은 HTML이다

#### Scenario: 화면이 참조하는 파일
- **WHEN** 이용자 화면 HTML이 참조하는 스타일과 스크립트, 그리고 그 스크립트가 불러오는 모듈을 모두 호출하면
- **THEN** 모두 200이다

#### Scenario: 없는 화면 파일
- **WHEN** `/ui/` 아래의 없는 파일을 호출하면
- **THEN** 404다

#### Scenario: 화면 패키지 문서는 내주지 않음
- **WHEN** `GET /ui/README.md`나 `GET /ui/CLAUDE.md`를 호출하면
- **THEN** 404다

### Requirement: 화면 경로가 API를 가리지 않음
화면 경로는 기존 API와 문서 경로를 MUST NOT 가린다. 화면을 내준 뒤에도 기존 API는 이전과 같은 응답을 준다.

#### Scenario: AI 사서 대화 경로
- **WHEN** 화면을 내주는 상태에서 토큰 없이 `POST /librarian/messages`를 호출하면
- **THEN** 401이다

#### Scenario: 검색 경로
- **WHEN** 화면을 내주는 상태에서 토큰 없이 `GET /catalog/suggest?q=데`를 호출하면
- **THEN** 401이다

#### Scenario: API 문서
- **WHEN** `GET /docs`를 호출하면
- **THEN** 200이다

### Requirement: 기존 API만 사용
화면은 화면 전용 API 없이 기존 API만 MUST 쓴다. 화면이 부르는 경로는 다른 클라이언트도 쓰는 일반 API이고, 화면 때문에 `/ui` 아래에 API 경로를 두지 않는다.
- 로그인 화면: 로그인, 내 정보
- 이용자 화면: 내 정보, 자동완성, 검색, 주제 검색, 비슷한 책, AI 사서 대화, 대화 종료, 도서관 안내, 회원 로그인·로그아웃, 담은 책(불러오기·담기·빼기·비우기), 대출, 반납, 희망도서 신청
- 관리자 화면: 내 정보, 로그아웃, 기관 정보, 운영 에이전트 대화와 대화 종료, 큐레이션·연체 안내문 틀·구매 요청서의 목록·상세·승인·반려(큐레이션은 내리기도), 희망도서 목록과 닫기, 오늘의 연체 안내 목록, 장서 가져오기(올리기, 기록 목록·단건, 행 목록, 적용, 미리 보기 삭제), 장서(사본 찾기·상태 바꾸기, 반납, ISBN으로 기관 도서 확인, 기관 도서·사본 등록), 회원(목록·찾기, 등록, 고치기, 삭제), 임시 휴관일(목록, 더하기, 지우기)

#### Scenario: 서버 경로
- **WHEN** 서버의 경로 목록을 읽으면
- **THEN** `/ui` 아래에는 정적 파일 경로 하나만 있고 API 경로가 없다

#### Scenario: 화면이 부르는 경로
- **WHEN** 화면 스크립트에서 서버에 요청하는 경로를 모두 모으면
- **THEN** 모두 `/auth/login`, `/auth/me`, `/auth/logout`, `/auth/member-login`, `/auth/member-logout`, `/catalog/suggest`, `/catalog/search`, `/catalog/topic`, `/catalog/books/{id}/similar`, `/librarian/messages`, `/librarian/sessions/{id}`, `/library`, `/library/guide`, `/library/closures`, `/library/closures/{id}`, `/basket`, `/basket/{id}`, `/loans`, `/loans/return`, `/book-requests`, `/book-requests/{id}`, `/admin-agent/messages`, `/admin-agent/sessions/{id}`, `/curations`, `/curations/{id}`, `/curations/{id}/approve`, `/curations/{id}/reject`, `/curations/{id}/unpublish`, `/overdue-notice-templates`, `/overdue-notice-templates/{id}`, `/overdue-notice-templates/{id}/approve`, `/overdue-notice-templates/{id}/reject`, `/purchase-requests`, `/purchase-requests/{id}`, `/purchase-requests/{id}/approve`, `/purchase-requests/{id}/reject`, `/overdue-notices/today`, `/holding-imports`, `/holding-imports/{id}`, `/holding-imports/{id}/rows`, `/holding-imports/{id}/apply`, `/holdings`, `/holdings/{id}`, `/library-books`, `/members`, `/members/{id}` 중 하나다

#### Scenario: 부르는 경로가 서버에 있음
- **WHEN** 화면 스크립트가 요청하는 경로와 메서드를 서버의 경로 목록과 맞춰 보면
- **THEN** 모두 서버에 있는 경로와 메서드다

### Requirement: 브라우저 저장
화면은 브라우저에 직원 토큰 말고 아무것도 MUST NOT 저장한다. 토큰은 화면마다 키 하나다. 키오스크 토큰은 `localStorage`에, 관리자 토큰은 `sessionStorage`에 둔다. 관리자 토큰은 탭을 닫으면 사라지고 키오스크 토큰을 덮어쓰지 않는다. 대화, 검색어, 회원 토큰, 관리자 화면의 목록은 화면 메모리에만 두고, 새로 고치거나 화면을 비우면 사라진다. 담은 책도 화면에는 메모리의 사본만 두고 브라우저 저장소에는 두지 않는다(회원별 보관은 서버가 맡는다. `circulation/member-basket`). 회원 토큰은 새로 고치면 로그아웃된다는 뜻이다. 공용 PC에서 다음 사람이 앞사람의 기록을 보지 않게 하기 위해서다.

#### Scenario: 저장소 사용
- **WHEN** 화면 스크립트에서 브라우저 저장소(`localStorage`, `sessionStorage`, `indexedDB`, 쿠키)를 쓰는 곳을 모두 모으면
- **THEN** `localStorage`의 키오스크 토큰 키 하나와 `sessionStorage`의 관리자 토큰 키 하나를 읽고 쓰고 지우는 곳뿐이다

#### Scenario: 회원 토큰은 저장소에 없음
- **WHEN** 회원 로그인에 성공한 뒤 브라우저 저장소를 보면
- **THEN** 회원 토큰이 어느 저장소에도 없고, 새로 고치면 로그아웃된 상태다(브라우저 확인)

#### Scenario: 두 토큰이 섞이지 않음
- **WHEN** 같은 브라우저에서 키오스크로 로그인해 둔 뒤 새 탭에서 관리자로 로그인하면
- **THEN** 키오스크 토큰 키는 그대로이고, 관리자 토큰은 다른 키에 있다

#### Scenario: 옛 토큰 키
- **WHEN** 화면 스크립트를 검사하면
- **THEN** 옛 키 `chaekbang.token`과 주소의 `#token=`을 읽는 곳이 없다

#### Scenario: 담은 책은 저장소에 없음
- **WHEN** 책을 담은 뒤 브라우저 저장소를 보면
- **THEN** 담은 책이 어느 저장소에도 없고, 새로 고친 뒤 다시 로그인하면 서버에서 불러와 나온다(브라우저 확인)

### Requirement: 서버 값의 안전한 표시
화면은 서버가 준 값을 글자로만 MUST 넣고 HTML로 해석하지 않는다. 서명, 답 문장, 추천 이유, 근거 문구, 안내 문구, 큐레이션 소개, 안내문 틀, 반려 사유, 회원 값, 서버 오류 문구가 모두 그렇다. 표지와 상품 링크는 서버가 준 원본 URL을 그대로 쓰고, `http`·`https` 주소만 쓴다.

#### Scenario: HTML 해석 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `eval`, `new Function`이 없다

#### Scenario: 주소 형식
- **WHEN** 화면 스크립트에서 표지·상품 링크 주소를 요소에 넣는 곳을 검사하면
- **THEN** 모두 `http`·`https` 주소만 통과시키는 같은 함수를 거친다

### Requirement: 카드 필드와 응답 스키마 일치
책 카드가 읽는 필드는 카드에 쓰는 응답 스키마(찾기 결과, 추천 카드, 비슷한 책)의 필드에 MUST 있다. 백엔드가 필드 이름을 바꾸면 테스트가 깨져 화면과 API가 어긋난 것을 알린다.

#### Scenario: 카드 필드
- **WHEN** 카드 스크립트가 책 값에서 읽는 필드 이름을 모두 모으면
- **THEN** 모두 찾기 결과, 추천 카드, 비슷한 책 스키마의 필드 중 하나다

#### Scenario: 필드 이름이 바뀜
- **WHEN** 카드 스크립트가 스키마에 없는 필드 이름을 읽으면
- **THEN** 카드 필드 테스트가 실패하고 그 이름을 알린다

### Requirement: 운영 방식에 따른 대출 버튼
이용자 화면은 도서관 안내 응답의 운영 방식이 `internal`일 때만 [대출·반납] 버튼을 MUST 보인다. 외부 대출 기관이거나 안내를 읽지 못하면 숨긴다. [희망도서 신청] 버튼은 두 방식 모두 보인다. 대출·반납의 최종 판단은 서버가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** [대출·반납] 버튼은 숨김 상태로 시작하고 [희망도서 신청] 버튼은 숨김이 아니다

#### Scenario: 버튼을 보이는 조건
- **WHEN** 화면 스크립트에서 [대출·반납] 버튼을 보이게 하는 곳을 검사하면
- **THEN** 안내 응답의 `loan_mode`가 `internal`인지 보는 한 곳뿐이다

### Requirement: 대출·희망도서 입력칸 비우기
이용자 화면은 로그인·대출·반납·희망도서 입력칸의 값을 화면 메모리에만 두고, 칸을 닫을 때와 화면을 비울 때(새 대화, 무입력, 로그아웃, 세션 끝) 모든 입력을 MUST 지운다. 로그인에 성공하면 번호 칸을, 희망도서 신청이 성공하면 모든 입력을, 빌리기·반납이 성공하면 등록번호를 지운다. 입력칸은 브라우저 자동 완성을 끈다. 이 요구사항은 브라우저 확인 항목으로 확인한다.

#### Scenario: 화면 비우기
- **WHEN** 휴대폰 번호나 서명을 적은 채 무입력 시간이 지나거나 [새 대화]를 누르면
- **THEN** 입력칸이 닫히고 다시 열면 모든 칸이 비어 있다

#### Scenario: 칸 닫기
- **WHEN** 휴대폰 번호를 적은 뒤 칸을 닫았다 다시 열면
- **THEN** 번호 칸이 비어 있다

#### Scenario: 로그인 성공
- **WHEN** 로그인에 성공하면
- **THEN** 번호 칸이 비고 번호는 어디에도 남지 않는다

#### Scenario: 입력칸 자동 완성
- **WHEN** 이용자 화면 HTML의 로그인·대출·희망도서 입력칸을 읽으면
- **THEN** 모두 `autocomplete="off"`다

### Requirement: 로그인·관리자 화면 내주기
시스템은 `/ui/login/`에서 로그인 화면을, `/ui/admin/`에서 관리자 화면을 SHALL 내준다. 이용자 화면과 같이 빌드 없는 정적 파일이고 토큰 없이 내준다. 기관 데이터는 토큰을 붙인 API 호출로만 받는다.

#### Scenario: 화면 HTML
- **WHEN** 토큰 없이 `GET /ui/login/`과 `GET /ui/admin/`을 호출하면
- **THEN** 둘 다 200이고 본문은 HTML이다

#### Scenario: 화면이 참조하는 파일
- **WHEN** 로그인·관리자 화면 HTML이 참조하는 스타일과 스크립트, 그리고 그 스크립트가 불러오는 모듈을 모두 호출하면
- **THEN** 모두 200이다

### Requirement: 로그인과 역할별 행선지
로그인 화면은 아이디와 비밀번호로 `POST /auth/login`을 SHALL 부르고, 응답의 역할로 행선지를 정한다. 키오스크는 이용자 화면으로, 관리자는 관리자 화면으로 간다. 토큰은 역할에 맞는 키에 저장한다. 로그인 실패(401)는 서버 문구를 글자로 보이고 아무것도 저장하지 않는다. 입력칸은 브라우저 자동 완성을 끄고, 공용 PC에서 비밀번호를 저장하지 말라는 안내를 보인다.

#### Scenario: 역할별 행선지
- **WHEN** 로그인 화면 스크립트에서 로그인 뒤 이동하는 곳을 검사하면
- **THEN** 역할 `kiosk`는 `/ui/librarian/`, 역할 `admin`은 `/ui/admin/`이고 그 밖의 역할은 이동하지 않는다

#### Scenario: 로그인 입력칸
- **WHEN** 로그인 화면 HTML을 읽으면
- **THEN** 아이디와 비밀번호 칸은 `autocomplete="off"`이고 비밀번호 저장 안내 문구가 있다

#### Scenario: 틀린 비밀번호
- **WHEN** 브라우저에서 틀린 비밀번호로 로그인하면
- **THEN** 서버 문구가 보이고 화면은 로그인 화면에 머물며 두 토큰 키 모두 비어 있다(브라우저 확인)

### Requirement: 화면의 역할 확인
이용자 화면과 관리자 화면은 열 때 자기 키의 토큰으로 `GET /auth/me`를 불러 역할을 MUST 확인한다. 이용자 화면은 `kiosk`, 관리자 화면은 `admin`만 받는다. 토큰이 없거나, 응답이 401이거나, 역할이 다르면 그 화면의 키만 지우고 로그인 화면으로 보낸다. 쓰는 중에 어떤 요청이든 401이면 똑같이 한다. 관리자 화면은 [로그아웃]으로 `POST /auth/logout`을 부르고 키를 지운 뒤 로그인 화면으로 간다. 뒤로 가기 캐시에서 다시 보인 관리자 화면은 토큰을 다시 확인한다. 이용자 화면에는 로그아웃 버튼이 없다.

#### Scenario: 받는 역할
- **WHEN** 이용자·관리자 화면 스크립트에서 `GET /auth/me` 응답의 역할을 맞춰 보는 곳을 검사하면
- **THEN** 이용자 화면은 `kiosk`, 관리자 화면은 `admin`과만 맞춰 본다

#### Scenario: 이용자 화면에 관리자 토큰
- **WHEN** 관리자 토큰을 키오스크 키에 넣고 이용자 화면을 열면
- **THEN** 키오스크 키가 지워지고 로그인 화면으로 간다(브라우저 확인)

#### Scenario: 로그아웃
- **WHEN** 관리자 화면에서 [로그아웃]을 누른 뒤 [뒤로]로 돌아오면
- **THEN** 관리자 화면 내용이 보이지 않고 로그인 화면으로 간다(브라우저 확인)

#### Scenario: 이용자 화면의 로그아웃
- **WHEN** 이용자 화면 HTML과 스크립트를 검사하면
- **THEN** 로그아웃 버튼과 `/auth/logout` 호출이 없다

### Requirement: 이용자 화면의 무입력·이용 상한 비우기
이용자 화면은 두 시계로 화면을 MUST 비운다. 시계가 하는 일은 로그인 여부에 따라 다르다.
- **무입력**: 마지막 입력에서 1분이다. 45초에 알림을 띄우고, 입력하면 알림을 닫고 다시 센다. 답을 받는 동안에는 세지 않는다. 로그인하지 않았으면 화면을 비우고 시작 화면을 보인다(대화 종료, 담은 책·입력칸 지움). 로그인 중이면 **회원만 로그아웃하고 바로 시작 화면**을 보인다(키오스크 토큰은 그대로).
- **이용 상한**: **로그인한 순간부터** 3분이다. 2분 30초에 알림을 띄운다. 입력해도 늘어나지 않고, 답을 받는 중에도 멈추지 않는다. 끝나면 회원만 로그아웃하고 바로 시작 화면을 보인다. 로그인하지 않았으면 이용 상한은 없다.

회원 로그아웃은 서버 회원 세션을 끊고 **대화(대화 종료, 검색 결과, 자동완성), 화면의 담은 책, 입력칸을 모두 비운다.** 서버에 보관한 담은 책은 지우지 않는다(다시 로그인하면 나온다). 그리고 **바로 시작 화면**을 보인다(로그아웃을 알리는 문구도, 대화 화면으로 돌아오는 일도 없다). 버튼, 무입력, 이용 상한이 모두 같다. 서버 회원 세션 오류(403)만 시작 화면 없이 화면을 로그아웃하고 로그인 칸을 연다. 답을 받는 중이었으면 그 답은 끊긴다. 시작 화면에서는 어떤 시계도 세지 않는다(시작 화면을 누른 뒤 첫 입력부터 익명 무입력 시계가 센다). 알림은 화면 아래 띠에 문구와 남은 초를 글자로 보인다. 로그인 중의 문구는 "N초 뒤 로그아웃해요"와 "N초 뒤 이용 시간이 끝나 로그아웃해요"다. 두 시계 모두 서버 AI 사서 세션의 무입력 시간(5분)보다 짧다.

익명 상태에서 시간이 다 돼 비우거나 회원이 로그아웃하면 **시작 화면**("화면을 눌러 시작하세요")을 보이고, 누르면 대화 화면으로 간다. 시작 화면은 화면을 처음 열 때도 보인다. 두 시계 모두 키오스크 토큰은 그대로 두고 로그아웃하지 않는다(다음 이용자가 직원 계정 없이 쓸 수 있어야 한다). [새 대화]와 세션 끝(404)은 시작 화면 없이 대화만 비운다.

#### Scenario: 시간 값
- **WHEN** 이용자 화면 스크립트의 시간 값을 읽으면
- **THEN** 무입력은 60초·알림 45초, 이용 상한은 180초·알림 150초이고, 둘 다 서버 설정 `librarian_session_idle_minutes`(5분)보다 짧다. 서버 회원 세션 수명은 이용 상한과 같은 3분이다

#### Scenario: 무입력 비우기
- **WHEN** 로그인하지 않은 채 45초 동안 입력하지 않으면 알림이 뜨고, 입력 없이 1분이 되면
- **THEN** 화면이 비워지고 시작 화면이 보인다(브라우저 확인)

#### Scenario: 익명은 이용 상한이 없음
- **WHEN** 로그인하지 않은 채 3분이 넘도록 계속 입력하며 쓰면
- **THEN** 화면은 비워지지 않고 이용 상한 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 무입력 알림과 연장
- **WHEN** 이용 중 45초 동안 입력하지 않으면 알림이 뜨고, 그때 화면을 누르면
- **THEN** 알림이 닫히고 다시 1분을 센다. 로그인 중의 알림 문구는 "N초 뒤 로그아웃해요"다(브라우저 확인)

#### Scenario: 로그인 중 무입력 로그아웃
- **WHEN** 로그인한 뒤 알림에도 입력하지 않아 1분이 되면
- **THEN** 회원만 로그아웃되어 대화와 화면의 담은 책과 입력칸이 비고, 바로 시작 화면이 보인다(로그아웃 문구 없음). 같은 번호로 다시 로그인하면 담은 책이 나온다(브라우저 확인)

#### Scenario: 이용 상한
- **WHEN** 로그인한 뒤 계속 입력하며 쓰다가 2분 30초가 되면 알림이 뜨고, 입력을 이어 가도 3분이 되면
- **THEN** 회원만 로그아웃되어 대화가 비워지고 바로 시작 화면이 보이며, 답을 받는 중이었으면 그 답은 끊긴다(브라우저 확인)

#### Scenario: 쓰지 않는 화면
- **WHEN** 비운 화면에 아무도 입력하지 않으면
- **THEN** 어떤 시계도 시작하지 않고 알림도 뜨지 않는다(브라우저 확인)

#### Scenario: 로그아웃 뒤 익명 시계
- **WHEN** 회원 로그아웃으로 시작 화면이 보이는 채 아무도 입력하지 않으면
- **THEN** 시계가 다시 시작하지 않고 시작 화면 그대로다. 시작 화면을 눌러 입력하면 그때부터 익명 무입력 시계가 센다(브라우저 확인)

#### Scenario: 시작 화면
- **WHEN** 시작 화면을 누르면
- **THEN** 시작 화면이 사라지고 대화 화면이 보인다(브라우저 확인)

#### Scenario: 처음 열 때
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** 시작 화면이 숨김이 아닌 상태로 있다

#### Scenario: 로그아웃하지 않음
- **WHEN** 시간이 다 돼 비우거나 회원을 로그아웃하는 길(시계가 부르는 함수와 시작 화면을 보이는 함수)을 검사하면
- **THEN** 키오스크 토큰을 지우거나 로그인 화면으로 보내거나 `/auth/logout`을 부르는 곳이 없다

#### Scenario: 새 대화는 시작 화면 없이
- **WHEN** [새 대화]를 누르면
- **THEN** 대화가 비워지고 시작 화면은 보이지 않는다(브라우저 확인)

### Requirement: 관리자 화면의 탭과 운영 방식
관리자 화면은 한 페이지에 탭 여덟(운영 대화, 승인 목록, 희망도서, 오늘의 연체, 장서 가져오기, 장서, 회원, 휴관일)을 SHALL 둔다. 열린 탭은 주소 hash로 기억한다. 기관 정보(`GET /library`)의 `loan_mode`가 `internal`일 때만 [오늘의 연체] 탭, 승인 목록의 연체 안내문 틀 묶음, [장서] 탭을 보이고, `external`일 때만 [장서 가져오기] 탭을 보인다. 기관 정보를 읽지 못하면 운영 방식에 따른 것을 모두 숨긴다. [회원]과 [휴관일]은 두 방식 모두 보인다. 숨긴 탭의 주소로 열면 운영 대화를 연다. 최종 판단은 서버(409)가 한다.

#### Scenario: 처음 그린 화면
- **WHEN** 관리자 화면 HTML을 읽으면
- **THEN** [오늘의 연체] 탭, 연체 안내문 틀 묶음, [장서 가져오기] 탭, [장서] 탭은 숨김 상태로 시작하고 [회원]·[휴관일] 탭은 숨기지 않는다

#### Scenario: 보이는 조건
- **WHEN** 관리자 화면 스크립트에서 위 네 가지를 보이게 하는 곳을 검사하면
- **THEN** 기관 정보의 `loan_mode`를 한 곳에서 읽고, 연체 탭·틀 묶음·[장서] 탭은 `internal`일 때만, [장서 가져오기] 탭은 `external`일 때만 보인다

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관의 관리자로 관리자 화면을 열면
- **THEN** [장서 가져오기]·[회원]·[휴관일] 탭이 보이고 [오늘의 연체]·[장서] 탭과 연체 안내문 틀 묶음은 보이지 않는다(브라우저 확인)

#### Scenario: 자체 대출 기관
- **WHEN** 자체 대출 기관의 관리자로 `#imports` 주소를 열면
- **THEN** [장서 가져오기] 탭은 보이지 않고 운영 대화가 열린다(브라우저 확인)

#### Scenario: 외부 대출 기관의 장서 주소
- **WHEN** 외부 대출 기관의 관리자로 `#collection` 주소를 열면
- **THEN** [장서] 탭은 보이지 않고 운영 대화가 열린다(브라우저 확인)

### Requirement: 운영 대화 화면
관리자 화면의 운영 대화는 `POST /admin-agent/messages`의 사건을 읽어 답 문장을 글자로 SHALL 보이고, 답 아래에 결과 사건의 표와 [초안 보기]를 보인다(운영 대화의 표, 초안 보기). `status`는 답이 오기 전까지 한 줄로 보이고, `unsupported`인 답에는 못 하는 분석이라는 표시를 붙인다. [새 대화]는 대화 종료를 부르고 화면을 비운다. 세션이 끝나 404면 세션을 버리고 안내하며, 보낸 문장을 입력칸에 되돌린다. 답이 끝나면 승인 대기 수를 다시 세어 [승인 목록] 탭에 보인다.

#### Scenario: 대화 요청의 본문
- **WHEN** 관리자 화면 스크립트에서 운영 에이전트 대화 요청 본문을 만드는 곳을 검사하면
- **THEN** 본문의 키는 `session_id`, `message`뿐이다

#### Scenario: 답과 승인 대기 수
- **WHEN** 운영 대화에서 큐레이션 초안을 만들어 달라고 하고 답이 끝나면
- **THEN** 답 문장이 보이고 [승인 목록] 탭의 승인 대기 수가 하나 는다(브라우저 확인)

#### Scenario: 새 대화는 표도 비움
- **WHEN** 표가 보이는 대화에서 [새 대화]를 누르면
- **THEN** 답 문장과 표가 모두 사라진다(브라우저 확인)

### Requirement: 승인 목록
관리자 화면의 승인 목록은 큐레이션, 연체 안내문 틀, 구매 요청서를 묶음별로 SHALL 보이고, 기본으로 승인 대기만 보인다. 줄을 누르면 상세를 보이고 상태에 맞는 동작만 보인다.
- 승인 대기: [승인](확인 한 번)과 [반려](사유 필수, 비어 있으면 요청하지 않음)
- 게시한 큐레이션: [게시 내리기]
- 그 밖의 상태: 동작 없음. 반려된 것은 반려 사유를 보인다

구매 요청서의 확정 전 상세는 항목별 추정 단가·금액, 추정 총액과 조회 시각을 보인다. 가격 없는 항목은 "가격 없음"으로, 조회할 수 없으면 그렇다고 보인다. 확정본은 기록한 단가·금액·총액·조회 시각·출처를 보인다. 승인·반려·내리기가 409나 503이면 서버 문구를 상세 안에 글자로 보이고 상태를 바꾼 것처럼 보이지 않는다. 성공하면 상세와 목록을 서버에서 다시 읽는다. 초안 만들기·고치기·지우기·다시 제출은 화면에 두지 않는다.

#### Scenario: 상태별 동작
- **WHEN** 승인 대기, 게시, 반려 상태의 큐레이션 상세를 차례로 열면
- **THEN** 각각 [승인]·[반려], [게시 내리기], 반려 사유만 보인다(브라우저 확인)

#### Scenario: 빈 반려 사유
- **WHEN** 반려 사유를 비운 채 [반려]를 누르면
- **THEN** 요청을 보내지 않고 사유를 적으라고 보인다(브라우저 확인)

#### Scenario: 가격 없는 구매 요청서 승인
- **WHEN** 가격 없는 항목이 있는 구매 요청서를 승인하면
- **THEN** 서버의 409 문구(ISBN 포함)가 상세 안에 보이고 요청서는 승인 대기로 남는다(브라우저 확인)

#### Scenario: 확정본 표시
- **WHEN** 확정된 구매 요청서 상세를 열면
- **THEN** 기록한 단가·금액·총액·조회 시각·출처가 보이고 동작 버튼이 없다(브라우저 확인)

### Requirement: 관리자 화면의 회원 값
관리자 화면은 회원 값(회원번호, 이름, 전화번호, 채운 안내 문안)을 [희망도서], [오늘의 연체], [회원] 탭에서만 MUST 보인다. 그 탭에 들어올 때마다 서버에서 다시 읽는다(연체·신청·회원은 그사이 바뀌므로 지난 목록을 다시 쓰지 않는다). 회원 값을 복사·출력·내려받는 버튼을 두지 않고, 브라우저 콘솔에 쓰지 않는다. 확정한 안내문 틀이 없어 오늘의 연체 목록이 409면 서버 문구와 함께 운영 대화에서 틀을 만들어 승인하라고 안내한다.

#### Scenario: 회원 값을 읽는 곳
- **WHEN** 관리자 화면 스크립트에서 `member_number`, `phone`을 읽는 곳을 모두 모으면(이름 `name`은 기관 이름과 겹쳐 브라우저 확인으로 본다)
- **THEN** 희망도서 목록, 오늘의 연체 목록, 회원 목록·입력을 그리는 곳뿐이다

#### Scenario: 콘솔 출력 없음
- **WHEN** 로그인·이용자·관리자 화면 스크립트를 검사하면
- **THEN** `console.` 호출이 없다

#### Scenario: 탭에 돌아오면 다시 읽음
- **WHEN** [오늘의 연체] 탭을 연 뒤 다른 탭에서 대출을 반납하고 돌아오면
- **THEN** 서버에서 다시 읽은 목록이 보이고 반납한 줄은 없다(브라우저 확인)

### Requirement: 이용자 화면의 Enter 갈림
이용자 화면은 입력칸에서 Enter를 누르면(자동완성 후보를 고른 때는 빼고) 먼저 서명·저자 찾기를 SHALL 부른다. 한 권 이상 찾으면 AI 사서 대화를 보내지 않고 두 단계 결과를 보인다. 찾은 책이 없거나, 입력이 서버의 질의 상한(100자)을 넘거나, 찾기가 실패하면(401은 빼고 로그인 화면으로 간다) 지금처럼 같은 글을 AI 사서 대화로 보낸다. 찾기 응답을 기다리는 동안의 Enter는 무시한다.

#### Scenario: 찾은 책이 있음
- **WHEN** 실험 기관 키오스크 화면에서 `채식`을 치고 Enter를 누르면
- **THEN** 두 단계 결과가 보이고 `/librarian/messages` 요청이 없다

#### Scenario: 찾은 책이 없음
- **WHEN** 서명·저자로 걸리는 책이 없는 문장을 치고 Enter를 누르면
- **THEN** 지금처럼 그 문장이 AI 사서 대화로 간다

#### Scenario: 긴 입력
- **WHEN** 100자를 넘는 글을 치고 Enter를 누르면
- **THEN** `/catalog/search` 요청 없이 AI 사서 대화로 간다. 화면의 이 상한은 서버 검색 API의 질의 상한과 같은 값이다

#### Scenario: 찾기 실패
- **WHEN** `/catalog/search`가 401이 아닌 오류로 실패하면
- **THEN** 같은 글이 AI 사서 대화로 간다

#### Scenario: 자동완성 후보 고르기
- **WHEN** 자동완성 후보를 화살표로 고르고 Enter를 누르면
- **THEN** 지금처럼 그 책 카드가 나오고 `/catalog/search`·`/catalog/topic` 요청이 없다

#### Scenario: 찾는 중 Enter
- **WHEN** 찾기 응답이 오기 전에 Enter를 다시 누르면
- **THEN** 두 단계 결과는 하나만 생긴다

### Requirement: 두 단계 결과
두 단계 결과는 위 단 "이 책을 찾으시나요?"(서명·저자 찾기 결과의 앞 2권), 아래 단 "'질의'와 관련된 책"(같은 질의의 주제 검색 결과에서 위 단의 책을 뺀 것), [사서에게 물어보기]로 SHALL 이루어진다. 위 단은 주제 검색을 기다리지 않고 먼저 보인다. 아래 단이 비거나 주제 검색이 실패하면 아래 단을 제목째 숨긴다. 카드는 다른 찾기 결과와 같은 카드다. [사서에게 물어보기]는 같은 글을 AI 사서 대화로 한 번 보내고 꺼진다. 두 단계 결과는 서버 대화 세션을 만들거나 바꾸지 않는다.

#### Scenario: 위 단과 아래 단
- **WHEN** `채식`으로 두 단계 결과가 보이면
- **THEN** 위 단에 채식주의자를 포함한 2권 이하가 있고, 아래 단에는 위 단의 책이 없다

#### Scenario: 위 단 권수
- **WHEN** 화면 스크립트의 위 단 권수를 읽으면
- **THEN** 2다

#### Scenario: 아래 단이 비거나 실패
- **WHEN** 주제 검색 요청이 실패하면
- **THEN** 아래 단과 그 제목이 보이지 않고 위 단과 [사서에게 물어보기]는 남는다

#### Scenario: 사서에게 물어보기
- **WHEN** [사서에게 물어보기]를 누르면
- **THEN** 같은 글이 AI 사서 대화로 한 번 가고 버튼이 꺼져 다시 눌러도 요청이 없다

#### Scenario: 화면 비우기
- **WHEN** 두 단계 결과가 있는 화면을 [새 대화]나 무입력으로 비우면
- **THEN** 두 단계 결과도 지워진다

### Requirement: 회원 토큰의 행선지
이용자 화면은 회원 토큰을 대출(`POST /loans`), 희망도서 신청(`POST /book-requests`), 담은 책(`/basket`) 요청, 회원 로그아웃(`POST /auth/member-logout`) 요청의 `X-Member-Token` 헤더에만 MUST 붙인다. 대화, 대화 종료, 검색, 자동완성, 안내 요청에는 붙이지 않는다. 이용자 화면은 요청 본문에 회원번호를 넣지 않고, 어떤 응답의 회원번호·이름·전화번호도 표시하지 않는다. 관리자 화면은 회원 값을 읽어 보이기만 하고 어떤 요청에도 넣지 않는다.

#### Scenario: 회원 토큰을 보내는 곳
- **WHEN** 화면 스크립트에서 `X-Member-Token` 헤더를 붙이는 곳을 모두 모으면
- **THEN** 대출, 희망도서 신청, 담은 책, 회원 로그아웃 요청을 만드는 곳뿐이다

#### Scenario: 이용자 화면의 회원번호
- **WHEN** 이용자 화면 스크립트에서 `member_number`를 쓰는 곳을 모두 모으면
- **THEN** 없다

#### Scenario: 대화 요청의 본문
- **WHEN** 화면 스크립트에서 AI 사서 대화 요청 본문을 만드는 곳을 검사하면
- **THEN** 본문의 키는 `session_id`, `message`, `selected_library_book_id`뿐이다

### Requirement: 이용자 화면의 회원 로그인
이용자 화면은 휴대폰 번호로 `POST /auth/member-login`을 불러 회원으로 SHALL 로그인한다. 검색·대화·반납은 로그인 없이 되고, 담기·빌리기·희망도서 신청은 로그인한 회원만 할 수 있다.
- 로그인 칸은 입력칸의 한 모드다. 번호 칸 하나(숫자 키패드)이고 성공하면 번호를 지운다. 실패하면 서버 문구를 글자로 보인다.
- 로그인 중에는 위 띠에 이름·번호 없이 "로그인 중"과 [로그아웃]만 보이고, 담은 책 표시와 카드의 [담기]는 로그인한 동안에만 보인다.
- 운영 방식과 상관없이 로그인 칸을 보인다. 외부 대출 기관에서는 대출·반납이 지금처럼 숨겨진다.

#### Scenario: 익명의 띠
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** [회원 로그인]은 숨김이 아니고 담은 책 표시와 [로그아웃]은 숨김 상태로 시작한다

#### Scenario: 로그인 중 표시
- **WHEN** 로그인에 성공하면
- **THEN** 위 띠에 "로그인 중"이 보이고 이름·번호는 어디에도 보이지 않는다(브라우저 확인)

#### Scenario: 로그아웃 버튼
- **WHEN** [로그아웃]을 누르면
- **THEN** 대화와 화면의 담은 책과 입력칸이 비고 바로 시작 화면이 보이며(그 위 띠의 [회원 로그인]이 다시 보인다), 서버의 담은 책은 남는다(브라우저 확인)

#### Scenario: 외부 대출 기관
- **WHEN** 외부 대출 기관에서 이용자 화면을 열면
- **THEN** [대출·반납]은 숨겨지고 [회원 로그인]은 보이며, 로그인한 뒤 담기와 희망도서 신청이 된다(브라우저 확인)

### Requirement: 로그인이 필요한 동작은 로그인 뒤에 이어서 함
이용자 화면은 로그인이 필요한 동작을 로그인 전에 누르면 로그인 칸을 열고, 성공하면 그 동작을 MUST 이어서 한다(기다리는 동작 하나만 기억한다). 빌리기·희망도서는 그 칸으로 돌아오며 이미 적은 등록번호·서명은 남긴다. 빌리기·희망도서 칸에는 회원번호 칸이 없다.

#### Scenario: 로그인 전 담기
- **WHEN** 로그인하지 않은 채 카드를 보면
- **THEN** [담기]가 없어 로그인 칸을 여는 담기 동작이 없다(브라우저 확인)

#### Scenario: 로그인 전 빌리기
- **WHEN** 로그인하지 않은 채 등록번호를 적고 [빌리기]를 눌러 로그인하면
- **THEN** 빌리기 칸으로 돌아오고 등록번호는 남아 있다(브라우저 확인)

#### Scenario: 회원번호 칸 없음
- **WHEN** 이용자 화면 HTML의 입력칸을 읽으면
- **THEN** 회원번호를 받는 입력 요소가 없고 휴대폰 번호를 받는 입력 요소 하나가 있다

### Requirement: 회원 세션 오류와 새 대화
이용자 화면은 요청이 403(회원 로그인이 필요)이면 화면도 MUST 로그아웃 처리하고 로그인 칸을 연다. 401이면 지금처럼 키오스크 로그인 화면으로 간다. [새 대화]는 대화만 비우고 로그인과 담은 책은 남긴다.

#### Scenario: 끝난 세션으로 빌리기
- **WHEN** 서버 회원 세션이 끝난 뒤 [빌리기]를 누르면
- **THEN** 로그인 칸이 열리고 키오스크 로그인 화면으로 가지 않는다(브라우저 확인)

#### Scenario: 새 대화는 로그인을 남김
- **WHEN** 로그인해 책을 담은 뒤 [새 대화]를 누르면
- **THEN** 대화는 비워지고 로그인과 담은 책은 그대로다(브라우저 확인)

### Requirement: 이용자 화면의 직원 로그인 이동
이용자 화면은 위 띠에 로그인 화면(`/ui/login/`)으로 가는 [직원 로그인] 링크를 항상 MUST 보인다. 키오스크·관리자 직원이 다른 계정으로 로그인하는 길이다. 링크는 이동만 하고 키오스크 토큰을 지우거나 직원 로그아웃(`/auth/logout`)을 부르지 않는다. 로그인 화면은 로그인한 상태로 열려도 넘기지 않는다.

#### Scenario: 직원 로그인 링크
- **WHEN** 이용자 화면 HTML을 읽으면
- **THEN** `/ui/login/`을 가리키는 [직원 로그인] 링크가 숨김 없이 있다

#### Scenario: 링크는 로그아웃하지 않음
- **WHEN** 링크를 눌러 로그인 화면으로 갔다가 이용자 화면으로 돌아오면
- **THEN** 키오스크 토큰이 그대로라 다시 로그인하지 않아도 쓸 수 있다(브라우저 확인)

### Requirement: 담은 책 화면
이용자 화면은 로그인한 회원의 담은 책을 서버(`/basket`)에 MUST 보관하고 불러온다. 카드의 [담기]는 로그인한 동안에만 있고, 로그인하면 담은 책을 자동으로 불러온다. 담기·빼기·비우기는 서버가 성공한 뒤에 화면에 반영한다. 로그아웃(버튼, 무입력, 이용 상한, 403)은 화면의 담은 책만 비우고 서버에는 남긴다. 성공이나 불러오기에는 문구를 띄우지 않고, 실패 문구는 둘뿐이다.
- 10권 상한(409): "담은 책은 10권까지예요". 그 밖의 실패(404, 연결 오류): "잠시 뒤 다시 눌러 주세요".
- 401은 키오스크 로그인 화면으로, 403은 회원 로그아웃과 로그인 칸으로 간다. 불러오기가 실패하면 문구 없이 빈 목록으로 시작한다.
- 담은 책 칸에 [모두 빼기]가 있고(담은 책이 없으면 숨김), 줄에는 서명·서가·대출 상태가 있으며 외부 대출 기관에서는 "대출 상태 … 기준"을 함께 보인다.
- [새 대화]는 담은 책을 건드리지 않는다.

#### Scenario: 로그인 전에는 담기가 없음
- **WHEN** 로그인하지 않고 카드를 보면
- **THEN** 카드에 [담기]가 없고 위 띠에 담은 책 표시가 없다(브라우저 확인)

#### Scenario: 로그인·로그아웃이 카드에 바로 적용됨
- **WHEN** 카드가 떠 있는 채 로그인하면, 이어서 로그아웃하면
- **THEN** 이미 떠 있던 카드에 [담기]가 바로 나타나고, 로그아웃하면 바로 사라진다(브라우저 확인)

#### Scenario: 담고 빼기
- **WHEN** 카드의 [담기]를 누르면
- **THEN** 서버에 저장된 뒤 버튼이 [담김]으로 바뀌고 담은 책 숫자가 늘며, 다시 누르거나 줄의 ×를 누르면 빠지고 버튼이 [담기]로 돌아온다(브라우저 확인)

#### Scenario: 모두 빼기
- **WHEN** 담은 책 칸에서 [모두 빼기]를 누르면
- **THEN** 담은 책이 모두 비고 카드 버튼은 [담기]로 돌아오며, 담은 책이 없으면 [모두 빼기]는 보이지 않는다(브라우저 확인)

#### Scenario: 로그아웃하고 다시 로그인
- **WHEN** 책을 담고 로그아웃한 뒤 같은 번호로 다시 로그인하면
- **THEN** 담은 책이 문구 없이 숫자와 목록으로 그대로 나온다. 이 확인은 버튼, 이용 상한, 무입력, 새로 고침 네 경우에 한다(브라우저 확인)

#### Scenario: 10권 상한
- **WHEN** 10권을 담은 뒤 다른 책의 [담기]를 누르면
- **THEN** 담지 않고 "담은 책은 10권까지예요"를 보인다(브라우저 확인)

#### Scenario: 실패하면 화면이 바뀌지 않음
- **WHEN** 담기 요청이 연결 오류로 실패하면
- **THEN** 버튼은 [담기]로 남고 "잠시 뒤 다시 눌러 주세요"를 보인다(브라우저 확인)

#### Scenario: 외부 대출 기관의 담은 책 줄
- **WHEN** 외부 대출 기관에서 책을 담으면
- **THEN** 담은 책 줄에 대출 상태 기준 시각이 보인다(브라우저 확인)

#### Scenario: 회원 토큰 헤더와 저장소 검사
- **WHEN** 화면 스크립트에서 담은 책 요청을 만드는 곳을 검사하면
- **THEN** 모두 회원 토큰 헤더를 붙이고, 담은 책을 브라우저 저장소에 쓰는 곳이 없다

### Requirement: 장서 가져오기 화면
관리자 화면의 [장서 가져오기]는 파일(xlsx, CSV)을 올려 미리 보기를 만들고, 요약(전체·새로·바뀜·그대로·건너뜀 행 수, 파일에서 빠진 사본 수, 인식한 열)과 확인할 행을 SHALL 보인다. 확인할 행은 건너뛴 행과 표기 넷(`invalid_isbn`, `unknown_status`, `purchased_without_isbn`, `purchased_without_price`)이고 20줄씩 더 본다. 표기와 열 이름은 한국어로 보인다. 탭에 들어올 때마다 지난 가져오기 목록을 다시 읽고, 기록을 누르면 그 요약을 연다.

필수 열을 찾지 못한 응답(422)에 파일 머리글이 있으면 못 찾은 필수 열마다 머리글에서 고르게 하고, 고른 열을 `column_mapping`으로 같은 파일과 다시 보낸다.

#### Scenario: 화면이 읽는 값
- **WHEN** 가져오기 화면 스크립트가 읽는 기록과 행의 필드를 응답 스키마와 맞춰 보면
- **THEN** 모두 `HoldingImportRead`와 `HoldingImportRow`에 있는 필드다

#### Scenario: 열과 표기의 이름
- **WHEN** 가져오기 화면 스크립트의 열 이름·표기 이름 표를 서버의 열 정의·표기와 맞춰 보면
- **THEN** 열 키와 한국어 이름이 서버와 같고 표기 넷이 모두 있다

#### Scenario: 미리 보기 요약
- **WHEN** 정상 파일을 올리면
- **THEN** 행 수, 파일에서 빠진 사본 수, 인식한 열이 보이고 장서는 바뀌지 않는다(브라우저 확인)

#### Scenario: 열 고르기
- **WHEN** 저자 열의 머리글이 인식되지 않는 파일을 올리고, 보이는 목록에서 그 머리글을 골라 다시 올리면
- **THEN** 처음에는 저자 열을 고르는 칸이 보이고, 다시 올리면 미리 보기 요약이 보인다(브라우저 확인)

#### Scenario: 읽을 수 없는 파일
- **WHEN** 예전 `.xls` 파일이나 빈 파일을 올리면
- **THEN** 열 고르기 없이 서버 문구가 보인다(브라우저 확인)

#### Scenario: 확인할 행
- **WHEN** 미리 보기에서 확인할 행의 종류를 누르면
- **THEN** 그 행의 행 번호, 등록번호, 서명, 저자, 사유가 20줄까지 보이고 더 있으면 [더 보기]가 있다(브라우저 확인)

#### Scenario: 기증처
- **WHEN** 기증처 열이 있는 파일을 올려 요약과 행 목록을 보면
- **THEN** 화면에 기증처 값이 없다(브라우저 확인)

### Requirement: 장서 가져오기의 적용
[적용]은 가장 최근 기록이 미리 보기일 때 그 기록에만 MUST 보인다. 확인 한 번 뒤 적용한다. 대량 제적 409면 파일에서 빠진 사본이 절반 이상이라고 알리고 한 번 더 확인한 뒤에만 `confirm_withdraw=true`로 다시 적용한다. 성공은 문구 없이 목록과 요약을 다시 읽어 보이고, 실패는 서버 문구를 글자로 보인다. 처음 요청에는 `confirm_withdraw`를 붙이지 않는다.

#### Scenario: 대량 제적 응답의 구분
- **WHEN** 화면이 대량 제적 409를 알아보는 낱말을 서버의 대량 제적 문구와 맞춰 보면
- **THEN** 서버 문구에 그 낱말이 있다

#### Scenario: 적용 취소
- **WHEN** [적용]의 확인 창에서 취소하면
- **THEN** 요청을 보내지 않고 기록은 미리 보기로 남는다(브라우저 확인)

#### Scenario: 적용
- **WHEN** [적용]을 확인하면
- **THEN** 성공 문구 없이 기록이 "적용함"이 되고 [적용]이 사라진다(브라우저 확인)

#### Scenario: 대량 제적 확인
- **WHEN** 가져온 사본의 절반 이상이 빠진 파일을 적용하면
- **THEN** 두 번째 확인이 뜨고, 취소하면 장서가 그대로이며 확인하면 적용된다(브라우저 확인)

#### Scenario: 오래된 미리 보기
- **WHEN** 미리 보기를 두 번 만든 뒤 앞의 기록을 열면
- **THEN** 요약은 보이고 [적용]은 없다(브라우저 확인)

### Requirement: 장서 가져오기의 파일 선택과 기록 정리
올려서 미리 보기가 생기면 파일 선택을 SHALL 비운다. 열 고르기가 필요한 경우처럼 미리 보기가 생기지 않으면 파일 선택을 남긴다. 지난 가져오기 목록은 적용한 기록과 미리 보기를 색과 글자로 나누어 보이고, 지금 연 기록을 표시한다. 미리 보기 기록의 요약에는 [삭제]가 있고 확인 한 번 뒤 지운다. 적용한 기록에는 [삭제]가 MUST NOT 있다.

#### Scenario: 같은 파일을 두 번 올리지 않음
- **WHEN** 파일을 올려 미리 보기가 생긴 뒤 [올리기]를 다시 누르면
- **THEN** 파일 선택이 비어 있어 새 기록이 생기지 않는다(브라우저 확인)

#### Scenario: 삭제 버튼의 자리
- **WHEN** 화면 스크립트에서 [삭제]를 만드는 곳을 검사하면
- **THEN** 미리 보기 기록에만 만들고, 확인 창 뒤에만 삭제 요청을 보낸다

#### Scenario: 미리 보기 삭제
- **WHEN** 미리 보기의 [삭제]를 누르고 확인하면
- **THEN** 그 기록이 목록에서 사라지고 요약이 닫힌다. 취소하면 그대로다(브라우저 확인)

#### Scenario: 기록의 구분
- **WHEN** 적용한 기록과 미리 보기가 함께 있는 목록을 보면
- **THEN** 두 상태의 색이 다르고 연 기록이 표시된다(브라우저 확인)

### Requirement: 운영 대화의 표
운영 대화는 `result` 사건의 표를 모았다가 `answer`가 오면 답 말풍선 아래에 받은 순서대로 SHALL 보인다. `answer` 없이 끝나면 모은 표를 보이지 않는다. 표는 제목, 설명 줄, 열 이름과 행이다. 막대 열이 있으면 그 칸에 숫자와 함께 그 열의 가장 큰 값에 맞춘 막대를 그린다. 잘린 표에는 아래에 전체 수와 보인 수를 보인다. 빈 칸은 `-`다. 넓은 표는 그 표만 가로로 스크롤된다. 모르는 `kind`의 결과는 건너뛴다. 칸 값은 글자로만 넣는다.

#### Scenario: 사건 처리
- **WHEN** 관리자 화면의 운영 대화 스크립트를 검사하면
- **THEN** `result` 사건을 받아 `answer`를 받은 뒤에만 그리고, 표는 `table`, 초안은 `draft` 종류만 처리한다

#### Scenario: 분야별 표와 막대
- **WHEN** 자체 대출 기관 관리자가 "분야별로 책이 몇 권씩 있어?"라고 물으면
- **THEN** 답 아래에 분야마다 한 줄인 표가 보이고 사본 칸에 막대가 있다(브라우저 확인)

#### Scenario: 목록 표
- **WHEN** "분실된 책 보여줘"라고 물으면
- **THEN** 서명, 저자, 등록번호, 청구기호 표가 막대 없이 보인다(브라우저 확인)

#### Scenario: 합계만인 답
- **WHEN** "우리 도서관 책이 모두 몇 권이야?"라고 물으면
- **THEN** 표 없이 답 문장만 보인다(브라우저 확인)

#### Scenario: 좁은 창
- **WHEN** 열이 넷인 표가 보일 때 창을 좁히면
- **THEN** 그 표만 가로로 스크롤되고 대화 화면은 가로로 넘치지 않는다(브라우저 확인)

### Requirement: 초안 보기
운영 대화는 초안 결과마다 답 아래에 [초안 보기] 버튼을 SHALL 둔다. 누르면 [승인 목록] 탭으로 바꾸고 그 종류 묶음에서 그 초안을 펼쳐 보이게 스크롤한다. 승인 대기 보기에 없으면 전체 보기로 바꿔 찾고, 그래도 없으면 승인 목록에 찾지 못했다는 짧은 문구를 보인다. 운영 대화의 내용은 탭을 바꿔도 남는다. 초안 종류 이름은 결과 사건의 값(`curation`, `template`, `purchase`)을 승인 목록의 묶음(큐레이션, 연체 안내문 틀, 구매 요청서)에 맞춘다.

#### Scenario: 종류 이름 맞춤
- **WHEN** 운영 대화 스크립트의 초안 종류 표를 서버의 초안 결과 종류 값과 맞춰 보면
- **THEN** 셋이 모두 같고 각각 승인 목록의 묶음 하나로 간다

#### Scenario: 방금 만든 초안
- **WHEN** 큐레이션 초안을 만든 답 아래의 [초안 보기]를 누르면
- **THEN** [승인 목록] 탭의 큐레이션 묶음에서 그 초안이 펼쳐져 화면에 보인다(브라우저 확인)

#### Scenario: 대화로 돌아오기
- **WHEN** [초안 보기]로 승인 목록을 본 뒤 [운영 대화] 탭을 누르면
- **THEN** 대화와 표가 그대로 있다(브라우저 확인)

#### Scenario: 이미 승인한 초안
- **WHEN** 승인한 초안의 [초안 보기]를 누르면
- **THEN** 승인 목록이 전체 보기로 바뀌고 그 초안이 펼쳐진다(브라우저 확인)

### Requirement: 장서 화면의 사본 찾기
관리자 화면의 [장서]는 들어오면 `GET /holdings`(찾기 글자 없음)로 최근에 등록한 사본부터 표로 SHALL 보인다. 찾기 칸 하나(서명·저자·등록번호)로 `GET /holdings?q=`를 불러 찾은 사본을 같은 표로 보이고, 찾은 동안에는 [전체 보기]가 있어 누르면 칸을 비우고 처음 목록으로 돌아간다. 칸을 비우고 [찾기]를 눌러도 처음 목록이다. 열은 등록번호, 서명, 저자, 청구기호, 상태이고 20줄씩 [더 보기]로 더 읽는다. 찾은 사본이 없으면 짧게 알린다. 탭에 다시 들어오면 지난 화면(처음 목록이나 찾기)을 서버에서 다시 읽는다. 서명·저자 같은 서버 값은 글자로만 넣는다.

#### Scenario: 찾기 요청
- **WHEN** 장서 화면 스크립트를 검사하면
- **THEN** 사본 목록과 찾기는 `GET /holdings`에 `q`(찾을 때만), `limit`, `offset`만 보내고 `status`를 보내지 않는다

#### Scenario: 처음 목록과 전체 보기
- **WHEN** 자체 대출 기관 관리자가 [장서] 탭을 열고, 서명으로 찾은 뒤 [전체 보기]를 누르면
- **THEN** 처음에는 최근에 등록한 사본부터 보이고, 찾으면 [전체 보기]가 생기며, 누르면 칸이 비고 처음 목록으로 돌아가 [전체 보기]가 사라진다(브라우저 확인)

#### Scenario: 읽는 필드
- **WHEN** 장서 화면 스크립트가 읽는 사본 필드를 응답 스키마와 맞춰 보면
- **THEN** 모두 `HoldingRead`에 있는 필드다

#### Scenario: 분실한 책 다시 찾기
- **WHEN** 자체 대출 기관 관리자가 한 권뿐인 책을 분실로 바꾼 뒤 그 서명으로 다시 찾으면
- **THEN** 그 사본이 분실 상태로 보인다(브라우저 확인)

#### Scenario: 등록번호로 찾기
- **WHEN** 등록번호를 그대로 쳐서 찾으면
- **THEN** 그 사본이 맨 위에 보인다(브라우저 확인)

### Requirement: 장서 화면의 상태 바꾸기
[장서]의 사본 줄은 대출 중이 아니면 상태 고르기(이용 가능, 분실, 훼손, 제적)를 SHALL 둔다. 고르면 `PATCH /holdings/{id}`에 상태만 보내고, 제적일 때만 확인을 한 번 더 받는다. 성공하면 문구 없이 응답 값으로 그 줄을 고친다. 실패하거나 확인을 취소하면 고르기를 이전 값으로 되돌리고, 실패는 서버 문구를 글자로 보인다. 대출 중인 줄은 고르기 대신 "대출 중"과 [반납]을 두고, 확인 한 번 뒤 그 등록번호로 `POST /loans/return`을 부른 다음 그 줄을 다시 읽는다.

#### Scenario: 고를 수 있는 상태
- **WHEN** 장서 화면 스크립트의 상태 고르기 값을 검사하면
- **THEN** `available`, `lost`, `damaged`, `withdrawn` 넷뿐이고 `on_loan`은 없다

#### Scenario: 제적만 한 번 더 묻기
- **WHEN** 장서 화면 스크립트의 상태 바꾸기를 검사하면
- **THEN** `withdrawn`을 보내기 전에만 확인을 받고 취소하면 요청하지 않는다

#### Scenario: 분실 처리와 되돌리기
- **WHEN** 이용 가능 사본을 분실로 고른 뒤 다시 이용 가능으로 고르면
- **THEN** 문구 없이 상태가 바뀌고 다시 찾아도 이용 가능이다(브라우저 확인)

#### Scenario: 대출 중인 사본 반납
- **WHEN** 대출 중인 줄의 [반납]을 누르고 확인하면
- **THEN** 그 줄이 이용 가능이 되고 상태 고르기가 생긴다(브라우저 확인)

### Requirement: 장서 화면의 책 등록
[장서]의 [책 등록]은 ISBN, 서명·저자, 사본 정보를 받아 기존 REST로 SHALL 등록한다. ISBN이 있으면 먼저 `GET /library-books?isbn=`으로 확인해, 있는 책이면 서명만 보이고 사본 칸만 받는다. 없거나 ISBN이 비면 `POST /library-books` 뒤에 `POST /holdings`를 부른다. 사본 칸은 등록번호(필수), 청구기호, 입수 구분(매입·기증), 매입이면 구입가(필수), 기증이면 기증처다. 필수 칸이 비면 요청하지 않는다. 실패는 서버 문구를 글자로 보인다. 성공하면 문구 없이 칸을 닫고 그 등록번호로 찾은 결과를 보인다.

#### Scenario: 이미 있는 책
- **WHEN** 장서 화면 스크립트의 책 등록을 검사하면
- **THEN** ISBN이 있으면 기관 도서 등록 전에 `GET /library-books`를 `isbn`으로 부르고, 찾은 책이 있으면 `POST /library-books` 없이 `POST /holdings`만 부른다

#### Scenario: 사본 등록이 실패한 뒤 다시 누르기
- **WHEN** 기관 도서는 만들어지고 사본 등록이 실패한 뒤 같은 칸에서 [등록]을 다시 누르면
- **THEN** 화면은 만든 기관 도서로 `POST /holdings`만 부른다(스크립트 검사와 브라우저 확인)

#### Scenario: 보내는 값
- **WHEN** 장서 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 기관 도서는 `LibraryBookCreate`, 사본은 `HoldingCreate`에 있는 키만 보낸다

#### Scenario: 새 책 등록
- **WHEN** 자체 대출 기관 관리자가 새 ISBN, 서명, 저자, 등록번호, 매입, 구입가로 등록하면
- **THEN** 칸이 닫히고 그 사본이 이용 가능으로 보이며, 이용자 화면에서 그 서명을 찾을 수 있다(브라우저 확인)

#### Scenario: 겹친 등록번호
- **WHEN** 이미 쓰는 등록번호로 사본을 등록하면
- **THEN** 서버 문구가 보이고 칸은 입력한 값과 함께 열려 있다(브라우저 확인)

### Requirement: 회원 화면
관리자 화면의 [회원]은 회원 목록을 SHALL 보이고 등록·고치기·삭제를 한다. 들어오면 `GET /members` 첫 20명(회원번호 순)을 읽고, 찾기 칸(이름·회원번호)으로 거르며, [더 보기]로 더 읽는다. 열은 회원번호, 이름, 휴대폰 번호(없는 기존 회원은 `-`)다. 등록은 회원번호·이름·휴대폰 번호(셋 다 필수)다. [고치기]는 이름과 휴대폰 번호만 바꾼다. 번호가 있는 회원의 번호 칸을 비우면 요청하지 않고 번호를 넣으라고 알린다. 번호 없는 기존 회원은 번호 칸을 비운 채 이름만 고칠 수 있다(번호를 보내지 않는다). [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패는 서버 문구를 글자로 보인다. 입력칸은 브라우저 자동 완성을 끈다.

#### Scenario: 보내는 값
- **WHEN** 회원 화면 스크립트가 보내는 본문의 키를 요청 스키마와 맞춰 보면
- **THEN** 등록은 `MemberCreate`, 고치기는 `MemberUpdate`에 있는 키만 보낸다

#### Scenario: 번호는 필수
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** 등록은 번호 칸이 비면 요청하지 않고, 고치기는 번호를 `null`로 보내지 않는다

#### Scenario: 삭제는 확인 뒤
- **WHEN** 회원 화면 스크립트를 검사하면
- **THEN** `DELETE /members/{id}` 앞에 확인이 있고 취소하면 요청하지 않는다

#### Scenario: 입력칸
- **WHEN** 관리자 화면 HTML의 회원 입력칸을 검사하면
- **THEN** 모두 `autocomplete="off"`다

#### Scenario: 등록한 회원으로 로그인
- **WHEN** 자체 대출 기관 관리자가 휴대폰 번호와 함께 회원을 등록한 뒤 이용자 화면에서 그 번호로 로그인하면
- **THEN** 로그인되고 빌리기를 할 수 있다(브라우저 확인)

#### Scenario: 겹친 번호
- **WHEN** 다른 회원이 쓰는 휴대폰 번호로 고치면
- **THEN** "이미 쓰는 전화번호입니다"가 보이고 목록의 값은 그대로다(브라우저 확인)

### Requirement: 휴관일 화면
관리자 화면의 [휴관일]은 오늘부터 1년의 임시 휴관일을 SHALL 보이고 더하기와 지우기를 한다. 들어오면 `GET /library/closures`를 `from`(오늘)과 `to`(오늘부터 365일)로 읽는다. 줄은 날짜와 사유(없으면 비움)와 [삭제]다. 더하기는 날짜(필수)와 사유(100자까지)를 `POST /library/closures`로 보낸다. [삭제]는 확인 한 번 뒤 부른다. 성공은 문구 없이 목록을 다시 읽고, 실패(같은 날짜 409 등)는 서버 문구를 글자로 보인다.

#### Scenario: 읽는 기간
- **WHEN** 휴관일 화면 스크립트를 검사하면
- **THEN** 목록 요청에 `from`과 `to`를 보내고 `to`는 `from`부터 365일 뒤다

#### Scenario: 사유 길이
- **WHEN** 관리자 화면 HTML의 사유 칸을 검사하면
- **THEN** 최대 길이가 서버 스키마의 상한(100자)과 같다

#### Scenario: 휴관일 더하기
- **WHEN** 자체 대출 기관 관리자가 오늘 날짜를 사유 `소독`으로 더하면
- **THEN** 목록에 그 날짜가 보이고, 같은 관리자의 `GET /library/guide`에서 오늘이 임시 휴관이고 사유가 `소독`이다(브라우저 확인. 시드 기관은 안내를 등록하지 않아 이용자 화면 위 띠에는 나오지 않는다)

#### Scenario: 같은 날짜
- **WHEN** 이미 있는 날짜를 다시 더하면
- **THEN** 서버 문구가 보이고 목록은 그대로다(브라우저 확인)

### Requirement: 휴대폰 번호의 하이픈
화면은 휴대폰 번호를 하이픈을 넣어 SHALL 보인다. 관리자 화면의 회원 목록과 오늘의 연체 목록이 그렇고, 번호를 치는 칸(관리자 회원 등록·고치기, 이용자 화면 회원 로그인)은 치는 대로 하이픈을 넣는다. 규칙은 공통 스크립트 한 곳에 둔다: `02`로 시작하면 2-3-4(9자리)·2-4-4(10자리), 그 밖은 3-3-4(10자리)·3-4-4(11자리)이고, 이 꼴이 아닌 값은 받은 그대로 보인다. 서버는 하이픈을 지운 숫자로 저장하므로 요청에는 하이픈이 있어도 된다. 번호 칸은 숫자와 하이픈만 남기고 13자를 넘지 않는다.

#### Scenario: 보이는 꼴
- **WHEN** 하이픈 규칙 함수에 `01012345678`, `0101234567`, `021234567`, `0212345678`, `0311234567`, `12`를 넣으면
- **THEN** `010-1234-5678`, `010-123-4567`, `02-123-4567`, `02-1234-5678`, `031-123-4567`, `12`가 나온다

#### Scenario: 한 곳의 규칙
- **WHEN** 관리자 회원·연체 스크립트와 이용자 화면 로그인 스크립트를 검사하면
- **THEN** 번호를 보이거나 칸에 넣을 때 모두 공통 스크립트의 함수를 쓴다

#### Scenario: 치는 대로 하이픈
- **WHEN** 이용자 화면 회원 로그인 칸에 `01099990001`을 치면
- **THEN** 칸에 `010-9999-0001`로 보이고 그대로 로그인된다(브라우저 확인)

#### Scenario: 관리자 목록
- **WHEN** 자체 대출 기관 관리자가 [회원] 탭과 [오늘의 연체] 탭을 열면
- **THEN** 번호가 `010-1234-5678` 꼴로 보인다(브라우저 확인)
