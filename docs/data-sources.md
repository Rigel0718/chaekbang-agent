# 외부 데이터 API와 이용 조건

장서 등록과 추천 근거에 쓴다. 각 API의 키 발급 조건, 호출 제한, 캐시·이미지 사용 조건은 시작 전에 확인한다.

| API | 쓰임새 | 비고 |
| --- | --- | --- |
| 도서관 정보나루 API | 도서 상세(`srchDtlList`: KDC, KDC 분류명, 부가기호, 권, 출판사, 짧은 소개), 도서별 이용 분석(`usageAnalysisList`: 함께 대출·마니아·다독자 추천), 인기대출도서(`loanItemSrch`: 연령 묶음·기간별). 이후 도서 키워드 | 공식 서지 채움의 출처 하나. 키는 쿼리 파라미터로만 받는다(https, URL을 로그에 남기지 않음). 하루 500건을 넘으려면 서버 IP를 등록한다. 표지는 비영리 화면 표시만 허용이라 쓰지 않는다. 찾지 못한 책도 200에 오류(`isbnMpngErr`)로 온다 |
| 카카오 책 검색 API | ISBN 검색(`target=isbn`): 정가, 출간일, 다른 출처에 없는 책의 서지 | 공식 서지 채움의 출처 하나. 일일 30,000건. 소개는 약 250자에서 잘려 온다. 판매가·판매 상태는 저장하지 않는다 |
| YES24 API | 도서 검색·상세 조회, 카테고리·베스트셀러 등 제공 기능 전반 (예: GOODS API, CATEGORY API). 채움은 상품 상세 조회(`itemDetail`)를 쓴다 | 공식 서지 채움의 출처 하나(서명·저자, 소개, 목차, 시리즈, 분류 원문, 표지·상품 링크), 희망도서 안내 등. 표지는 저장하지 않고 원본 URL로 표시, 출처와 상품 링크 표기 |

**세 출처 합치기**(`add-bibliographic-sources`, 2026-11-17): 채움은 ISBN마다 세 출처를 한 번씩 부르고 필드마다 가장 잘 주는 출처를 먼저 쓴다. 서명·부제·저자는 YES24 → 정보나루 → 카카오(정보나루 서명은 권차를 빼고 대등 서명을 붙여 와 정리 규칙을 거친다), 소개는 YES24 → 정보나루 → 카카오, KDC·부가기호는 정보나루, 정가·출간일은 카카오 먼저다. 필드별 출처를 `books.field_sources`에 남긴다. 어느 출처든 멈춰야 하는 오류가 나면 채움을 멈춘다(빠진 출처의 값을 나중에 채울 수 없어서다).

외부 API는 위 세 개를 중심으로 쓴다. 표의 내용은 예시이며 두 API가 제공하는 기능을 여기에 적힌 것으로 한정하지 않는다. 쓸 기능은 각 change에서 API 문서를 보고 정한다.

**YES24 연동 구조**
- 호출 코드는 `app/central/external/yes24/`에 따로 둔다. 인증은 `X-Api-Key` 헤더이고 키 값은 `.env`의 `YES24_API_KEY`에만 둔다.
- 엔드포인트와 응답 필드는 코드 곳곳에 흩어 놓지 않고 정의 파일 한 곳에 모은다. 새 엔드포인트나 필드는 그 파일에 추가하는 것으로 끝나게 한다.
- API 묶음(GOODS, CATEGORY 등)별로 역할 함수를 나누고, 각 함수에 하는 일을 한국어로 적는다.
- 공식 서지는 운영자가 `scripts/enrich_books.py`로 채운다. 기관 API에는 실행 경로가 없고, 기관은 `GET /book-enrichment`로 처리 현황만 본다.
- 한도는 키 기준 하루 20,000회, 초당 10회다. 초당 5회 이하로 호출하고, 한도 초과나 외부 장애가 나면 실행을 멈춘다. 처리 상태가 기관 도서마다 저장돼서 다음 실행이 이어서 처리한다.

**YES24 이용 조건** (FAQ)
- 서비스 제공에 필요한 범위의 캐싱은 허용한다. 그래서 소장 도서의 ISBN만 조회해 저장한다.
- 전체 도서 정보의 자체 DB 축적과 제3자 재배포는 허용하지 않는다. 베스트셀러나 카테고리를 돌며 쌓지 않고, YES24 값을 내보내는 기능을 만들지 않는다. 예외는 둘이고 둘 다 서비스 경로가 아니며 한 번만 받아 저장소 밖에 둔다: 평가 표본 약 100권(상품 검색, 테스트 DB 트랜잭션에서만)과 실험 장서 525권(카테고리 스테디셀러, 2026-11-15, 개발 DB의 가상 기관에만). 실험 장서는 `add-bibliographic-sources`에서도 지우지 않았다(사용자 결정, YES24를 세 출처 중 하나로 계속 쓴다). 같은 ISBN의 정보나루·카카오 값은 따로 받은 파일에 둔다.
- 가격·재고 같은 변동 정보는 갱신 주기를 짧게 유지해야 한다. 판매가와 판매 상태는 저장하지 않는다.
- **구매 요청서의 정가 조회**(`add-purchase-request`, 예외): 구매 요청서 항목의 ISBN(희망도서처럼 소장하지 않은 책 포함)은 상품 상세로 조회하되 정가(`shopPrice`)만 읽는다. 조회한 값은 요청서 상세 응답에만 쓰고 저장하지 않으며, 승인할 때 그 요청서 항목의 단가·금액·총액·조회 시각으로만 기록한다(예산·공적 보고 기록). 공식 서지(`books.list_price`)나 다른 곳에 쓰지 않고 다른 요청서에 다시 쓰지 않는다. 관리자가 요청서를 열거나 승인할 때만 부르고 항목 수(최대 30)만큼이라 하루 한도에 비해 작다. 서명 검색(`search_items`)은 쓰지 않는다.

**저장소에 두는 예외** (코딩 규칙 "공식 서지는 소장 도서의 ISBN만 채운다"의 예외)
- 평가 표본 약 100권(`evals/librarian/data/`)과 실험 장서 525권(`evals/collection/data/`, 개발 DB의 가상 기관에만)만 예외다. 둘 다 한 번만 받고 저장소에 넣지 않는다.
- 실험 장서는 `add-bibliographic-sources`에서도 지우지 않았고, 같은 ISBN의 정보나루·카카오 값을 따로 받은 파일(`sources_collection.json`, 출처마다 이어 받기)을 함께 쓴다.
- `add-loan-signals`부터 같은 ISBN의 정보나루 대출 신호(함께 대출·마니아·다독자 ISBN 순위, 연령 묶음별 인기 ISBN 순위와 대출 수)를 받은 파일(`loan_signals.json`)도 쓴다. ISBN 순위와 수만 남기고 서명·표지는 남기지 않는다.
- 카카오 판매가·판매 상태와 정보나루 표지(비영리 화면 표시만 허용)는 저장하지 않는다.
